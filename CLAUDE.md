# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Le projet

**Vectis UI** (`@vectis/ui`) : design system Vue 3 + TypeScript distribué en librairie npm, compatible Nuxt 3 (SSR). Monorepo pnpm — `packages/ui` contient tout ; `apps/` est réservé à une future app de theming temps réel qui manipulera la source des tokens programmatiquement et importera `@vectis/ui` en `workspace:*`. Langue du projet : français (commentaires, stories, docs).

## Commandes

Tout se lance depuis la racine (pnpm activé via corepack) :

```bash
pnpm lint              # eslint (flat config racine)
pnpm format            # prettier --check   (format:fix pour corriger)
pnpm typecheck         # vue-tsc -r
pnpm test              # vitest run -r  → projet `unit` (jsdom) uniquement
pnpm test:stories      # play functions dans Chromium (Vitest browser mode)
pnpm build             # build lib (régénère les tokens en prebuild)
pnpm tokens            # régénère tokens.css + tokens.json depuis la source TS
pnpm icons             # régénère le registre d'icônes SVG (réseau ; à la demande, PAS en prebuild)
pnpm storybook         # dev server port 6006
pnpm build-storybook
```

Un seul test : `pnpm --filter @vectis/ui exec vitest run --project unit src/components/VButton/VButton.test.ts` (ou `-t 'nom du test'`).

Checkpoint avant de conclure une étape : `pnpm lint && pnpm typecheck && pnpm test && pnpm build && pnpm build-storybook` doivent tous passer. `pnpm test:stories` est **hors checkpoint** (il exige les binaires Playwright, ~115 Mo, via `pnpm --filter @vectis/ui exec playwright install chromium`) : à lancer dès qu'on touche à une play function ou au comportement navigateur.

## Philosophie (non négociable — vient du cahier des charges)

1. **HTML/CSS d'abord, JS en dernier recours.** Primitives natives : `<dialog>`+`showModal()`, Popover API, CSS Anchor Positioning, `<details>`, `:user-invalid`, `:has()`, `color-mix()`, `@starting-style`… Tout JS de comportement doit être **justifié par un commentaire** dans le composant (voir VMenuPanel.vue : le JS se limite au roving focus clavier et au pont v-model ↔ API impérative du popover).
2. **Zéro dépendance runtime hors Vue** (`peerDependencies: { vue }` uniquement). Pas de floating-ui : pour les flottants, anchor positioning CSS sous `@supports` + mini-fallback JS maison (~30 lignes) si nécessaire.
3. **Aucune valeur brute dans le CSS des composants** (couleur, radius, espacement, typo, ombre, durée) : uniquement des tokens sémantiques `var(--vectis-*)`. Les durées dérivées passent par `calc()` sur un token. Tolérés : bordures `1px`, opacités.
4. **SSR-safe (Nuxt 3)** : aucun accès `window`/`document`/API navigateur hors `onMounted`/`watch`/handlers. Détection de support (`CSS.supports`) côté client uniquement. IDs via `useId()` de Vue.

## Architecture des tokens (cœur du projet)

Chaîne : `src/tokens/*.ts` (source de vérité typée, format DTCG `{ $value, $type, $description? }`) → `scripts/build-tokens.ts` (via `pnpm tokens`, auto-lancé en `prebuild`/`prestorybook`) → `src/styles/tokens.css` + `src/tokens/tokens.json`. Un plugin Vite inline (`vite.config.ts`) émet aussi `dist/tokens.json`.

- **Deux espaces de noms, à ne jamais mélanger.** `--vectis-*` = les **tokens publics**, générés depuis la source TS, documentés, surchargeables au runtime par le consommateur. Tout le reste est **privé et non contractuel** : les variables locales d'un composant, qui n'ont plus d'underscore mais sont **qualifiées** — soit par leur composant (`--skeleton-w`, `--side-nav-level`, `--dial-radius`, `--calendar-cell`), soit par le contrat transverse qu'elles incarnent (`--tone-bg-solid` & co pour les tones, `--control-*` pour l'échelle de tailles, `--fill-fraction` partagée par les deux Progress et VSlider). **La qualification n'est pas cosmétique** : ces variables HÉRITENT (`.v-control` les pose, tous les descendants les lisent), donc un nom générique comme `--size`, `--radius` ou `--gap` serait capturé par n'importe quelle app hôte qui le définirait sur un ancêtre — et rien ici ne le verrait, jsdom n'évaluant pas les styles. Toute variable locale nouvelle porte donc un nom qualifié.
- **Les `--<composant>-anchor` ne sont PAS des tokens** : `--popover-anchor`, `--combobox-anchor`, `--datepicker-anchor`, `--timepicker-anchor`, `--tooltip-anchor` sont des dashed-idents d'`anchor-name`, absents de `tokens.css` et non surchargeables. Les nommer `--vectis-*` inviterait à croire le contraire. Chacun a exactement 3 sites (un `anchor-name`, un `anchor-scope`, au moins un consommateur) et **l'un d'eux est une valeur de prop TypeScript**, donc invisible à tout outil CSS : les faire diverger d'un caractère fait peindre le panneau à l'origine du viewport, sans erreur console.
- **Deux niveaux** : primitifs (`primitives.ts` — palettes OKLCH, échelles) et sémantiques (`semantic.ts` — seuls consommés par les composants). Les alias DTCG `{color.neutral.500}` sont résolus en `var(--vectis-color-neutral-500)` au build (`css.ts`, aussi exporté via `@vectis/ui/tokens` pour la future app de theming).
- **Thèmes** : `themes/dark.ts` ne peut surcharger QUE des clés sémantiques existantes (le build le vérifie et échoue sinon). Le CSS généré pose `:root` (tout) + `[data-theme='light']` et `[data-theme='dark']` (sémantiques seulement) → theming par sous-arbre DOM, surcharge runtime sans rebuild.
- **`src/styles/tokens.css` et `src/tokens/tokens.json` sont GÉNÉRÉS** : ne jamais les éditer à la main (ils sont dans .prettierignore ; toute modif passe par la source TS + `pnpm tokens`). **Second artefact généré du repo : `src/components/VIcon/icons.ts`** (`pnpm icons`) — même discipline, mais déclencheur différent : il n'est PAS branché sur `prebuild` (son script télécharge depuis `google/material-design-icons` à une révision épinglée, et le build ne doit pas dépendre du réseau).
- **Tokens de dimension dédiés** : jamais `--vectis-space-*` pour une taille de composant (track, thumb, hauteur de pastille…) — créer un token sémantique dédié. Un vrai espacement (gouttière, offset, delta compact, padding) reste légitime en `--vectis-space-*`.
- **Typo sémantique** : groupe `text` dans `semantic.ts` — un rôle = une recette complète `--vectis-text-<rôle>-size/weight/leading[/tracking]` (display, heading-1…4, subtitle, body-lg/md/sm, label, caption, overline, code) + `--vectis-text-family`/`-family-code` + rôle technique `control` (weight/leading des étiquettes de contrôles ; la size vient de `--control-font-size`). Le CSS des composants consomme ces recettes, jamais les primitifs `--vectis-font-*` — exceptions assumées et commentées : emphases d'état en `--vectis-font-weight-semibold` (th VDataTable, titre VToast, initiales VAvatar, sélection/aujourd'hui VCalendar), échelle contextuelle de VInputOTP, contrat police de VIcon.

## Cascade CSS

`src/styles/index.css` déclare l'ordre : `@layer vectis.reset, vectis.tokens, vectis.components, vectis.utilities;`. Tout style consommateur non-layerisé gagne — c'est le mécanisme de surcharge voulu.

**Les layers portent le nom LONG là où les classes portent `v-`**, et ce n'est pas une incohérence : un nom de layer est **global et non namespacé**. Un consommateur écrivant `@layer v { … }` verrait son bloc absorbé dans celui du DS et arbitré par l'ordre déclaré ici — bug de cascade silencieux, invisible en dev. Le raccourci se justifie pour une classe (elle s'écrit dans le HTML, se lit dans le devtools, se tape des centaines de fois) ; pas pour un identifiant tapé 56 fois dans des `<style>` et jamais par un utilisateur. **Un SFC qui garderait un layer non déclaré serait ordonné APRÈS tous les layers déclarés, donc gagnerait sur tout** : le garde-fou est `git grep -E "@layer\s+(?!vectis)"`.

- Chaque SFC a un `<style>` **non-scoped** dont tout le contenu est enveloppé dans `@layer vectis.components { … }`. Les tables de variables locales (tones + `[data-custom]`, tailles `data-size`/`data-compact`) y vivent aussi, juste avant les règles qui les consomment — **un seul `<style>` par SFC, jamais de fichier CSS voisin** — pas de `X.tokens.css` à côté. L'ordre interne reste significatif : `[data-custom]` après les tones, même spécificité, le dernier gagne.
- **L'ordre des exports dans `src/index.ts` fixe l'ordre du CSS bundlé** : à spécificité égale, le dernier gagne. Contraintes actuelles : VIconButton après VButton (surcharge padding/largeur), VSlider après VInput (surcharge la largeur des champs numériques `.v-slider-field`), VToaster après VButton (croix = VIconButton recoloré).
- **Feuilles partagées** (`src/styles/`, importées par `index.css` dans cet ordre : reset, tokens, floating, panel, control-size, utilities) : `floating.css` (`.v-overlay` — socle de TOUT popover ; `.v-floating` — ancrage et placements), `panel.css` (`.v-panel` — chrome commun des panneaux listant des rangées : VMenu, VCombobox ; posé par la prop `surface` de VPopover), `control-size.css` (`.v-control`), `utilities.css` (`.v-visually-hidden` + la keyframe globale `v-spin`, partagée par VSpinner et VProgressCircular : les `@keyframes` ne sont pas arbitrées comme des déclarations, donc hors layer et déclarées une seule fois). Règle pour `.v-panel` : n'y mettre QUE des déclarations qu'aucun panneau ne redéclare — `.v-panel` et `.v-menu`/`.v-combobox-panel` sont à spécificité égale (0,1,0), toute déclaration commune serait arbitrée par l'ordre du bundle. Les dimensions (`min/max-inline-size`, `max-block-size`, `overflow`) restent donc chez chaque panneau — `position-anchor` vient de `VPopover`, qui pose aussi `.v-panel` via sa prop `surface`. **Corollaire — VDatePicker et VTimePicker rendent leur VPopover en `surface`** : le premier depuis que le VCalendar a perdu son fond et son rayon propres ; le second pour ses DEUX panneaux (un seul `VPopover` sert le cadran et la liste), le panneau du cadran ne gardant que sa mise en colonne et son padding.
- Build : un seul `dist/styles.css` (reset + tokens + composants), jamais de CSS importé par le JS émis.

## Conventions composants

- **Nommage, trois étages.** `V` + PascalCase pour les **composants** (`VButton`, `VComboboxOption`, `VTimePickerDial`) : le préfixe lève l'ambiguïté d'un tag dans un template (`<VButton>` vs `<button>` natif vs le `Button` d'une autre lib). `Vectis` + PascalCase pour les types publics **transversaux**, qui portent la marque (`VectisMessages`, `VectisMessagesInput`, `VectisIconName`). **Aucun préfixe** pour les types **portés par un composant** (`ButtonTone`, `TabsVariant`, `ComboboxOption`, `DataTableColumn`, `CalendarSelection`…) : un type dans un `import type {}` n'a pas l'ambiguïté d'un tag, et surtout c'est ce qui garde `VComboboxOption.vue` et le type `ComboboxOption` dans deux espaces distincts. Les préfixer réintroduirait exactement la collision qui obligeait naguère `VCombobox.vue` à aliaser ses trois sous-composants en `OptionRow`/`OptionGroup`/`OptionSeparator`.
- Un dossier par composant : `src/components/VX/VX.vue` + `VX.stories.ts` + `VX.test.ts` + **`VX.mdx`** (doc Storybook — obligatoire, générée à chaque nouveau composant). Export nommé ajouté dans `src/index.ts`. Les fichiers ANNEXES gardent leur nom de rôle, sans préfixe : `context.ts`, `state.ts`, `resolver.ts`, `types.ts`, `iconProps.ts`, `icons.ts` — le `V` marque un tag, or un module TS n'en a pas.
- Classes `.v-<nom>` ; **variantes via `data-variant` / `data-tone` / `data-size`** (pas de prolifération de classes). Les tones définissent des variables locales `--tone-bg-solid`, `--tone-text-tinted`… que les variantes consomment (voir VButton.vue, le modèle de référence).
- API : `defineProps` typées + `withDefaults`, `defineSlots` typés, `defineModel` pour v-model, `defineEmits` typés seulement s'il y a des événements non natifs. Les attributs natifs passent par fallthrough (pas de re-déclaration).
- **Pattern wrapper-root** — un composant dont la racine est un wrapper (contrôles masqués VCheckbox/VRadio/VSwitch en `<label>` englobant ; champs VInput/VTextarea ; VChip) : `defineOptions({ inheritAttrs: false })` + `v-bind="$attrs"` sur l'élément fonctionnel (contrôle natif / action), en gardant `class`/`style` sur la racine. Sinon `name`/`required`/`aria-*` atterrissent sur le wrapper et cassent formulaires et accessibilité. Un input masqué l'est via `opacity: 0` (reste focusable/soumis), jamais `display: none`.
- Manipuler une propriété DOM sans attribut HTML (ex. `indeterminate`) : `watchEffect(..., { flush: 'post' })` — en flush `pre`, la ref template n'est pas encore posée au premier passage.
- Focus visible : `outline: var(--vectis-focus-ring-width) solid var(--vectis-focus-ring-color)` + offset token. `@media (prefers-reduced-motion: reduce)` pour toute transition/animation.
- **`src/composables/` et `src/utils/`** — voir la section « Code partagé » ci-dessous. Un helper dont un composant est le PROPRIÉTAIRE naturel reste dans son dossier même s'il est importé ailleurs : `VIcon/iconProps.ts` produit des props de `VIcon`, c'est VIcon qui en fixe le contrat (idem `VIcon/types.ts` et `VIcon/resolver.ts`).

## Code partagé (`src/composables/`, `src/utils/`)

Deux dossiers, une frontière nette : **`composables/`** = comportement Vue (`ref`/`computed`/`watch`/cycle de vie) ; **`utils/`** = helpers sans état Vue (calcul pur et DOM impératif). Rien n'est exporté publiquement — `index.ts` n'est pas touché, ce sont des modules internes. Règle d'admission : **≥2 consommateurs ET un corps réellement commun**.

**`utils/`** — `date.ts` et `time.ts` (logique de dates et d'heures : chaînes ISO `YYYY-MM-DD` et `HH:mm` 24 h, tout en heure locale, `Intl` sur des instants de référence UTC → SSR-safe ; consommés par VCalendar/VDatePicker et VTimePicker/VTimePickerDial) ; `number.clamp(n, min, max)` (sur intervalle vide, `min` gagne : `max` peut être dérivé d'une liste vide) ; `css.px(v)` (nombre ou chaîne numérique → `12px`, sinon `undefined` plutôt qu'une custom property invalide) ; `text.normalizeText(s)` (NFD, filtrage insensible aux accents — VCombobox, VDataTable), `text.pad2(n)` et `text.digitsOf(s)` (helper purement lexical : les masques de saisie de VDatePicker et VTimePicker ne connaissent que la suite de chiffres, jamais les séparateurs, qu'ils posent eux-mêmes — d'où sa place ici plutôt que dans `date.ts`) ; `array.toggleValue(list, v)` (jamais de mutation en place : la nouvelle référence est ce qui réveille les v-model consommateurs — VToggle, VCombobox, VCalendar, VDataTable) ; `matcher.resolveMatcher(tableau | prédicat)` (convention `disabledDates`/`disabledPages`, résolue UNE fois en `computed`, tableau → `Set`) ; `env.isDev` (garde-fous de dev, accès optionnel à `import.meta.env` pour rester inerte chez un consommateur non-Vite) ; `arrowNav` (ci-dessous).

**`utils/arrowNav.ts`** — `navigableItems(container, selector)` + `arrowNavigate(event, container, items, { vertical })`, incarnation UNIQUE de la navigation par flèches : découverte DOM (pas de registre), filtre `display !== 'none'` (un item masqué par une container query ou par le consommateur ne capte pas le focus), wrap modulo, inversion RTL sur l'axe inline seulement, `preventDefault` appliqué seulement si la touche est traitée. Contrat : **déplacer le focus, jamais activer** — l'activation au focus (VTabs `activation: 'automatic'`) est posée par le composant, dans son propre `@focus`. Adoptants : VPagination, VTabs, VToggle, et VMenuPanel qui passe sa PROPRE liste (elle exclut aussi les `aria-disabled` et confine le roving au panneau courant). Restent dehors, délibérément : VCalendar, VCombobox, VInputOTP, VTimePickerDial — ils naviguent un espace de **valeurs**, pas une liste DOM, et leur bord de liste est un clamp métier.

**`composables/`**

- **`usePopover(el)`** → `{ shown, syncShown, show, hide }`, plomberie d'état d'un `[popover]` (pendant JS de `floating.css`). Deux invariants : `shown` est alimentée **par le DOM** — câbler `syncShown` sur `@beforetoggle` ET `@toggle` du panneau (le premier est synchrone et capte le light dismiss, le second est le seul émis par le stub jsdom ; les ToggleEvent ne bubblent pas, donc toujours sur l'élément popover lui-même) — et **jamais posée à la main** ; les gardes d'idempotence évitent l'`InvalidStateError` de `hidePopover()` sur un popover déjà fermé. **Tous les popovers du DS y sont passés** : VMenuPanel et VToaster directement, tous les autres via le composant `VPopover` (VCombobox, VTooltip, VDatePicker, VTimePicker). Idiome : **une instance par popover** quand un composant en pilote plusieurs (VToaster : une par placement, indexée dans une `Map`, chacune portant sa propre ref d'élément).
- **`useFieldPanel({ rootEl, panelRef, fieldEl, disabled, focusInPanel, onOpen?, onClose? })`** → `{ open, openPanel, closePanel, onControlClick, onFocusout, onKeydown, onPanelMousedown }`. Coquille « champ + `VPopover` en `mode="manual"` » de VDatePicker et VTimePicker (le champ n'est en lecture seule que dans certains de leurs modes). Le panneau est **écrit impérativement** (`panelRef.show()/hide()`) et **lu par modèle** (`open`, à brancher en `v-model:open` sur le VPopover, qui l'alimente depuis le DOM) : l'écriture doit rester synchrone, le `rAF` qui déplace le focus supposant le panneau déjà ouvert quand il est armé. Un popover `manual` ne fait rien seul : ni light dismiss, ni déplacement du focus, ni retour du focus au champ. `onOpen`/`onClose` portent le propre de chaque composant (brouillon et étape du VTimePicker, vidage de sa live region). Le `onKeydown` garde `!event.defaultPrevented` sur ArrowDown/Entrée : **une Entrée consommée dans le panneau vient de le fermer et le rouvrirait en remontant à la racine** (couvert par un test unitaire). **`onPanelMousedown` (à câbler en `@mousedown` sur le VPopover)** annule le mousedown sur les zones NON interactives du panneau : cliquer un pixel non focusable (padding, gouttière entre cellules) rend le focus au `<body>`, le `focusout` de la racine part avec un `relatedTarget` nul et ferme un panneau sur lequel on vient de cliquer — au VTimePicker, cela abandonnait le brouillon en cours. Le filtre (`closest('button, a, input, select, textarea, [tabindex]')`) est essentiel : le `preventDefault` inconditionnel du VCombobox, dont le focus ne quitte jamais le champ, priverait ici les jours et les flèches de navigation de leur focus et désynchroniserait le roving du VCalendar. **Invisible en jsdom** (pas de focus au clic) → play functions `ClicDansLeVide` des deux composants, vérifiées rouges sans le handler.
- **`useFocusoutDismiss(root, close)`** → handler `@focusout` de racine. Un popover reste un descendant DOM même peint en top layer, donc `contains` suffit ; `relatedTarget` nul = sortie aussi. Adoptants : VCombobox, et VDatePicker/VTimePicker via `useFieldPanel`.
- **`useRootAttrs()`** → `{ attrs, rootClass, rootStyle, forwardedAttrs }`, plomberie du **pattern wrapper-root** (7 adoptants : VInput, VTextarea, VTabs, VCombobox, VDataTable, VDatePicker, VTimePicker). `defineOptions({ inheritAttrs: false })` reste dans le SFC (c'est une option de compilation). `rootClass` est typée `ClassBinding` (redéclarée localement : `@vue/runtime-dom` exporte `ClassValue`, le paquet `vue` ne la réexporte pas, et `unknown` est refusé par le template).
- **`useAriaLabel(() => props.label)`** → précédence `aria-labelledby` > `aria-label` > prop `label`. Indispensable dès qu'un composant en `inheritAttrs: false` rend à la fois `v-bind="forwardedAttrs"` et `:aria-label` (VTabs, VToggle) — sans arbitrage les deux s'appliquent. Ailleurs (VPagination, VBreadcrumb, VToaster, VInputOTP) le fallthrough Vue fait déjà gagner l'attribut du consommateur : le composable n'y retire que le défaut devenu redondant. Ne PAS l'appliquer à VIcon/VIconButton, où `label` est le nom accessible d'un contrôle icône seule.
- **`useTimer()`** → `{ start(fn, delay), cancel() }`, `setTimeout` réarmable annulé au démontage ; `delay ≤ 0` exécute **synchroniquement** (convention du DS : 0 désarme le report ; `setTimeout(…, 0)` ne serait pas synchrone). Adoptants : VTooltip (délai d'apparition), VMenuItem (délai d'intention du survol — UNE instance, ouverture et fermeture s'excluant), VCombobox et VDataTable (leurs debounces, chacun gardant sa sémantique propre : dédoublonnage par terme d'un côté, commit vers un `ref` de l'autre). VToaster reste dehors : sa `Map<id, timeout>` est une autre structure.
- **`useFieldIds(attrs, hasHint)`**, **`useIconClickHandlers({ name, iconStartLabel, iconEndLabel })`**, **`useTextLimit({ el, text, maxlength, softLimit })`** — partagés par VInput et VTextarea. Respectivement : ids et agrégation d'`aria-describedby` (un `id` du consommateur PRIME sur le `useId()` interne) ; détection des listeners `@click:icon-*` dans `vnode.props` (les emits déclarés sont retirés de `$attrs`) avec le garde-fou a11y ; compteur, dépassement et limite souple par `setCustomValidity`.
- **`useProgressValue(value, max)`** → `{ clamped, fraction }` (VProgressLinear, VProgressCircular).

**Fusions à ne pas tenter** (analysées, sans corps réellement commun) : un IntersectionObserver partagé VTabs/VCombobox ; la fusion de `utils/date.ts` et `utils/time.ts` ; une interface partagée pour `defineExpose({ …, el })` ; `onClear()` de VInput/VTextarea.

## Internationalisation (`src/i18n/`)

**Aucun littéral de texte utilisateur dans un SFC** : tout passe par le dictionnaire. Les messages DÉVELOPPEUR (`[Composant] …`) restent en dur — ils s'adressent à l'intégrateur, pas à l'utilisateur.

Chaîne : `i18n/types.ts` (contrat `VectisMessages`) → `fr.ts` (socle, toujours embarqué) + `en.ts` (opt-in) → `state.ts` (registre + `setLocale`/`registerMessages` publics, `useMessages`/`useLocale` internes). Dossier de premier niveau, au même rang que `tokens/` : ni `utils/` (le dictionnaire courant est un état réactif), ni `composables/` (c'est de la configuration, pas un comportement).

- **État module-level** en `shallowRef` (précédents `VIcon/resolver.ts` et `VToast/state.ts` — **3e état global du repo**), pas de provide/inject ni de plugin Vue : c'est de la configuration, posable depuis un `.ts` quelconque. Le `shallowRef` est ce qui fait re-rendre les composants DÉJÀ MONTÉS quand `setLocale` est appelé après coup. **Piège** : `useMessages().value.x` lu dans le corps d'un `setup()` FIGE la valeur — toujours dans un `computed` ou le template.
- **LIMITE ASSUMÉE : une seule locale par processus.** Le SSR multi-locale PAR REQUÊTE n'est pas couvert (un même processus Node servant /fr et /en doit passer les props texte explicitement) ; un `setLocale` client-only fait diverger serveur et client → mismatch d'hydratation. Porte de sortie prévue : `useMessages` a une forme de composable, son seul CORPS deviendrait `inject(messagesKey, null) ?? currentMessages` sans toucher aux ~20 SFC consommateurs (il faudrait alors un garde `getCurrentInstance()`, la fonction restant appelable hors composant).
- **Profondeur EXACTEMENT 2** (`namespace.clé` → feuille). Ce n'est pas décoratif : c'est ce qui rend le merge des surcharges partielles NON RÉCURSIF, donc structurellement incapable de descendre dans une valeur fonction (un `DeepPartial<T>` récursif transformerait `(n: number) => string` en `{}`).
- **Messages paramétrés = fonctions TS typées**, aucun moteur de pluriel ni ICU : le pluriel anglais est un ternaire dans la fonction. `fr` et `en` sont ANNOTÉS `: VectisMessages` → la parité des clés et des signatures est acquise à la COMPILATION ; le test de parité ne couvre que le reste (arité, `as` glissé plus tard).
- **`fr` embarqué, `en` opt-in par import.** L'argument n'est pas le poids (~0,8 Ko gzip) mais l'unicité du mécanisme : activer l'anglais fourni et ajouter une langue absente sont le MÊME geste (`registerMessages`), au lieu de deux catégories de dictionnaires. Le tree-shaking en est la conséquence.
- **Cascade canonique** : `aria-labelledby` > `aria-label` du consommateur > prop `label` > dictionnaire > `fr`. `useAriaLabel` n'a pas bougé (son argument est déjà un getter) : `useAriaLabel(() => props.label ?? m.value.x.y)`. Les ~30 props texte sont CONSERVÉES et prioritaires — seul leur défaut littéral a quitté `withDefaults` pour un `computed`.
- **Résolution par sous-balise de langue** : `'fr-FR'`/`'fr-CA'` partagent leurs mots, ce qui les distingue vient d'`Intl`. Trois invariants : jamais de chaîne vide, jamais de clé technique affichée, jamais de silence en dev quand une langue manque.
- **Mots et formats se résolvent SÉPARÉMENT** : `setLocale('de-DE')` sans dictionnaire allemand donne déjà mois, 1er jour de semaine et cycle horaire allemands (tout vient d'`Intl`) avec des libellés français. État dégradé cohérent, pas un bug.
- **Frontière du dictionnaire** : y entre ce qui est un MOT ou une convention typographique de langue (l'espace insécable devant `%`, le `hh:mm` fait d'initiales) ; en restent dehors ce qu'`Intl` dérive de la balise, et ce qui n'est fait que de chiffres et de ponctuation universelle — `99+` (VBadge), `+N` (VAvatarGroup), le compteur `N/M`, le `:` de `TIME_SEPARATOR`, le repli `PLACEHOLDER_FALLBACK` de `date.ts`. Ces composants exposent un slot pour une reformulation.
- **VCalendar/VDatePicker/VTimePicker** gardent leur prop `locale`, PRIORITAIRE ; son défaut `'fr-FR'` est devenu `undefined` et retombe sur la locale globale (idiome `props.x ?? contexte` de `VAvatar.vue`) — `undefined` doit rester distinguable, même raison que `mode`/`showDial`. VDatePicker est la source UNIQUE : c'est `resolvedLocale` qui descend au VCalendar. `VDataTable` trie via `localeCompare(…, dsLocale.value, …)` et non `undefined`, dont la locale de runtime diffère entre Node et navigateur → ordre de lignes divergent, donc mismatch d'hydratation.
- **Tests** : tout en vitest/jsdom (aucun comportement navigateur en jeu). `i18n.test.ts` porte les tests CANONIQUES du mécanisme (réactivité post-montage, cascade prop/attribut, locale des pickers) — ne pas les dupliquer dans les 20 fichiers de composants. Les ~30 assertions FR préexistantes sont le FILET : la locale par défaut restant `fr`, elles doivent rester vertes sans être touchées ; une rougeur signale une chaîne mal recopiée, jamais un test à corriger. Piège de recopie : `VTimePicker` mélange apostrophe droite et typographique, et ses tests ciblent les deux.
- **Stories** : l'état module survit à la navigation Storybook → `beforeEach` avec teardown obligatoire (même règle que le `dismissToast()` des stories de VToast).

## Tests : répartition stricte

- **vitest + jsdom** (`*.test.ts`) : logique uniquement — emits, v-model, attributs ARIA, fallthrough. jsdom ne couvre pas VPopover/top-layer : la Popover API est stubbée globalement dans `vitest.setup.ts` (marqueur `data-popover-open` + display inline, car `:popover-open` n'est pas évaluable en jsdom et le style UA `[popover]{display:none}` cache le panneau aux requêtes par rôle ; `hidePopover` ferme aussi les descendants `[data-popover-open]` — cascade de pile nécessaire aux sous-menus). Ne pas tester le comportement navigateur en jsdom.
- **Play functions Storybook** (`storybook/test` : `expect`, `userEvent`, `within`, `waitFor`) : comportements navigateur réels (ouverture popover, Esc, `:user-invalid`…). Les mises à jour v-model étant asynchrones, toujours passer par `waitFor` après une interaction. Elles s'exécutent **localement dans Chromium** via `@storybook/addon-vitest` (`pnpm test:stories`) — plus besoin de brûler un build Chromatic pour les valider.
- `vitest.config.ts` déclare **deux projets** : `unit` (jsdom, `src/**/*.test.ts`) et `storybook` (browser mode Playwright, alimenté par `storybookTest({ configDir: '.storybook' })`). Deux pièges : un projet Vitest **n'hérite pas** des plugins de la racine — `vue()` doit être répété dans le projet `storybook`, sinon les `.vue` importés par les stories échouent en « invalid JS syntax » ; et depuis Storybook 10.3 le plugin applique **lui-même** les annotations de `preview.ts`, donc aucun fichier de setup à écrire (un `setProjectAnnotations` manuel serait signalé comme redondant).
- `globals: true` dans vitest.config.ts est **requis** pour le cleanup automatique de @testing-library/vue — ne pas le retirer (projet `unit`).
- L'`expect` de vitest n'a PAS les matchers jest-dom (`toBeVisible`, `toHaveFocus`…) : en jsdom, asserter sur les propriétés DOM (`el.hidden`, `document.activeElement`). Ces matchers n'existent que dans `storybook/test` (play functions).

## Support navigateur

Popover API, `<dialog>`, `<details name>`, `:user-invalid`, `color-mix()`, `:has()` : Baseline, utilisables sans fallback. **CSS Anchor Positioning : utilisé SANS fallback** — cible navigateurs modernes uniquement (Chrome/Edge 125+, Safari 26+ ; Firefox non supporté tant qu'anchor positioning n'y est pas stable). Ne pas ajouter de fallback JS sans demande explicite. `@starting-style`/`allow-discrete` : progressive enhancement uniquement, jamais requis.

**Patterns d'ancrage** (`src/styles/floating.css` : `.v-overlay` + `.v-floating` + `data-placement` → `position-area`/`position-try-fallbacks`) :

- Panneau invoqué par `popovertarget` (VMenu — sous-menus compris : l'item parent est l'invocateur du panneau imbriqué) : l'invocateur est l'**ancre implicite**, aucun `anchor-name` nécessaire.
- Panneau ouvert programmatiquement (VTooltip, et `VPopover` quand un `#trigger` lui est fourni) : `anchor-name` **statique partagé** sur le wrapper + `anchor-scope` (même nom) qui le confine au sous-arbre du wrapper + `position-anchor` sur le panneau. Le confinement est indispensable : un popover affiché passe en top layer et est considéré comme « après » tout le document pour la résolution d'ancre — sans `anchor-scope`, tous les panneaux se rattacheraient au dernier wrapper nommé de la page. Pas d'ID unique, pas de style inline. `anchor-scope` : Chrome/Edge 131+, Safari 26+ (léger relèvement du plancher Chrome 125 assumé). Range vertical par `writing-mode` (VSlider) : Chrome/Edge 129+, Safari 18.1+ (même logique de relèvement assumé).
- Placements alignés (`top-start`, `bottom-end`…) : la marge inline du côté aligné est annulée dans floating.css (`[data-placement$='-start']`/`[$='-end']`), sinon le `margin` d'écart décale le panneau du bord du trigger. Placements latéraux (sous-menus, `right-start`) : axe inversé, la marge inline est restaurée (l'écart est inline, l'alignement block).
- Panneau dont le consommateur possède déjà racine et contrôle (VCombobox, VDatePicker, VTimePicker, et VTooltip qui garde son wrapper pour y attacher pointer/focus) : il pose lui-même `anchor-scope`/`anchor-name` et transmet le seul nom à `VPopover` par la prop **`anchor`** (dashed-ident) → `position-anchor: var(--anchor-name)`. C'est la voie obligée dès que le contrôle est un `<input>` texte, sur lequel `popovertarget` est invalide.
- Les triggers sont fournis par slots scopés : `#trigger="{ triggerProps }"` + `v-bind="triggerProps"` (popovertarget, aria-*). VTooltip suit le même pattern (slot default scopé) : c'est le consommateur qui pose `aria-describedby`, jamais un pont JS automatique au mount.
- **`.v-overlay`** est le socle de tout popover du DS : `position: fixed; inset: auto` (neutralise les styles UA de `[popover]`) + le garde-fou `.v-overlay:not(:popover-open) { display: none }`. Un panneau qui pose son propre `display` (`.v-panel` en flex, la pile de toasts en colonne) écrase le `display: none` UA de `[popover]` (styles auteur > UA) et le panneau fermé resterait cliquable en `opacity: 0` par-dessus le contenu ; la spécificité (0,2,0) du garde-fou le met hors de portée d'un `display` de composant, quel que soit l'ordre du bundle. **La classe se pose sur les six panneaux ET sur les piles de toasts** (`.v-toast-stack`, qui redéclarait ce bloc mot pour mot mais ne peut pas porter `.v-floating` : coordonnées physiques, pas d'ancre, marge nulle). Les blocs de transition restent séparés (VToaster : opacité seule en `--vectis-duration-base` ; `.v-floating` : opacité + `transform` en `--vectis-duration-fast`). VDialog reste dehors : `<dialog>` n'est pas un popover, `:popover-open` ne s'y applique pas — d'où son `.v-dialog:not([open])` propre.

## Échelle de tailles (contrôles)

Échelle unifiée **xs/sm/md/lg/xl** (24/32/40/48/56px, tokens `--vectis-control-height-xs…xl`). Le mapping taille → hauteur/font/icône/opsz/gap vit en UNE incarnation CSS : `src/styles/control-size.css`, classe **`.v-control`** posée sur la racine porteuse de `data-size`/`data-compact`. Les blocs `[data-size]` ne définissent QUE des custom properties `--control-*` (héritées jusqu'aux enfants, ex. le field de VInput — aucun conflit de spécificité) + le contexte VIcon `--vectis-icon-size`/`--vectis-icon-opsz`.

- **Compact** = -4px de hauteur partout (`--control-height` dérivée de `--control-height-base`).
- Mappings (littéraux, contrat police maintenu — pas de nouveaux tokens) : icônes xs→16 / sm-md→20 / lg-xl→24 ; opsz xs-md→20, lg-xl→24 ; fonts xs→xs, sm-md→sm, lg-xl→md ; gap `--control-gap` xs→4px, sm-md→8px, lg-xl→12px ; paddings = `--vectis-space-*` directs.
- **L'échelle complète n'est pas exposée partout** : chaque composant restreint son union TS au sous-ensemble qui a du sens pour lui, `control-size.css` restant la table unique (ses blocs xs/xl servent toujours aux boutons). Il n'existe volontairement **aucun type `ControlSize` partagé** — les échelles diffèrent, un type unique serait faux.
- Adoptants et sous-ensembles : VButton/VIconButton/VPagination/VTabs/VToggle (**xs–xl**) ; VSideNavigation (sm/md, défaut md — `v-control` sur le `<nav>`, toutes les sous-listes héritent) ; **tout composant à champ de saisie → sm/md/lg** (32/40/48px, défaut md) : VInput, VTextarea, VInputOTP (typo majorée d'un à deux crans), VDatePicker, VTimePicker, VCombobox (qui propage sa taille telle quelle à son panneau) — `xs` (24px) est trop bas pour du texte saisissable et `xl` (56px) hors gabarit formulaire : ne pas les exposer ; VChip (xs/sm, défaut xs) ; VMenu (sm/md/lg, défaut sm — `v-control` sur le panneau, cf. puce suivante) ; VAvatarGroup.
- **Les panneaux portent `v-control` sur le PANNEAU, leurs rangées consomment** : le panneau, qui porte déjà `data-size`/`data-compact`, porte `v-control` ; `.v-menu-item`/`.v-combobox-option`/`.v-combobox-state` lisent les `--control-*` hérités (hauteur, `--control-padding-inline`, gap, font-size) et les icônes suivent sans une ligne de CSS. **Invariant** : un sous-panneau de VMenu ne prend PAS la classe (`:class="{ 'v-control': !submenu }"`) — `.v-control` repose `--control-height` depuis `--control-height-base` **sans** la condition `[data-compact]`, qu'un sous-panneau ne porte pas : il perdrait le compact hérité. Même raison pour laquelle `panel.css` ne pose plus le contexte VIcon. Seule exception à la table : la typo des rangées est composite (taille de l'échelle, leading `body-md` unitless, poids regular) — la recette `control` vaut medium/leading 1, or une rangée peut passer à la ligne et porter un sous-libellé. **Les LIBELLÉS DE GROUPE consomment eux aussi `--control-height`** (`.v-menu-group-label`, `.v-combobox-group-label`, `.v-side-nav-group-label` — les trois seuls du DS) : `display: flex` + `align-items: center` + `min-height`, même recette que les rangées, pour que l'en-tête de section ne casse pas le rythme vertical de la liste (compact compris, `--control-height` en dérive déjà). Leur typo reste hors échelle (rôle `overline`), d'où le centrage vertical. Règle non factorisée dans `panel.css` : elle y serait à spécificité égale de celle des panneaux, et VSideNavigation ne partage de toute façon pas le padding (indenté par niveau).

### Caractéristiques par composant

- **VIcon** : **le DS ne requiert AUCUNE police d'icônes.** Résolution, dans cet ordre : prop `render` (rendu explicite) → prop `src` → `name` (résolveur consommateur → **registre intégré** → ligature) → slot SVG. L'ordre EST le contrat : le résolveur passe avant le registre (sinon les icônes du DS resteraient en Material chez qui a branché sa propre bibliothèque), et un résolveur rendant `undefined` laisse la main au registre — ce qui rend les mappings PARTIELS utilisables. `data-icon="<name>"` est posé quelle que soit la source : accroche des tests, point d'extension CSS. Pilotage contextuel `--vectis-icon-size`/`--vectis-icon-opsz` ; la prop `size` explicite prime — **`--vectis-icon-opsz` ne joue QUE sur la ligature** (axe de police ; le registre est dessiné à opsz 24), la taille vaut pour toutes les sources. VIcon a perdu sa propriété « zéro import / zéro JS » : le `computed` de résolution n'est pas du comportement (ni événement, ni cycle de vie, ni DOM), mais cette propriété était un corollaire de « la police fait tout ».
  - **Registre intégré** — `VIcon/icons.ts`, GÉNÉRÉ par `pnpm icons` : les 20 icônes que la librairie rend par défaut, en paths Material Symbols Rounded (wght 400 · GRAD 0 · opsz 24, Apache-2.0 © Google), sous la forme `[contour, plein?]` — le second path n'est émis que si l'axe FILL change réellement la géométrie (7 sur 20 ; le script fait la comparaison, jamais la main). ~2 Ko gzip **non tree-shakables** (recherche par chaîne au runtime) : prix assumé de l'autonomie. Ajouter un nom au tableau du script quand un composant se met à rendre une nouvelle icône par défaut. Rendu en `<svg><path>` et non en `mask-image` : un fond masqué disparaît en forced-colors Windows, là où `fill: currentcolor` survit.
  - **`setIconResolver`** (`VIcon/resolver.ts`) — branchement d'une bibliothèque tierce, **2e état global module-level du repo** après `VToast/state.ts` (le 3e est `i18n/state.ts`). À poser au niveau module (plugin Nuxt, `main.ts`), jamais dans un `setup()`, jamais client-only (mismatch d'hydratation). Trois fabriques génériques, une par famille de source, sans aucune connaissance d'une lib tierce : `ligatureIconResolver` (Material, IcoMoon — **et la façon de retrouver l'axe opsz 20/24 sur les 20 icônes du DS**), `classIconResolver` (Font Awesome, Phosphor, Bootstrap — rend un `<span class="v-icon-glyph">` du DS, pas un `<i>` : le DS possède l'élément donc le normalise d'une règle ; `strict` par défaut, un nom du registre non aliasé retombe sur le SVG intégré plutôt que de produire un carré vide), `componentIconResolver` (Lucide, Untitled UI — contrat : racine `<svg>` unique, le dimensionnement passe par `.v-icon > svg`).   - **`IconSource = string | IconRender`** (`VIcon/types.ts`) — type de TOUTES les props d'icône du DS. **AUCUNE heuristique** : une chaîne est toujours un NOM, une image/un composant se déclare en objet (`{ src }`, `{ component }`, `{ path }`, `{ text }`, `{ class }`). `VIcon/iconProps.ts` devinait par regex `[./:]` qu'une chaîne contenant `.`, `/` ou `:` était une URL — ce qui interdisait `mdi:close` ou `fa6-solid:xmark` (ils partaient en `<img>` sans jamais atteindre le résolveur). **Le typecheck ne rattrape PAS cette migration** (une URL reste une chaîne valide) : ce sont les tests qui la couvrent. `iconName(source)` en est le pendant — nom lisible pour un libellé de repli, `undefined` sur un objet (VInput/VTextarea, sinon `[object Object]` dans l'arbre d'accessibilité).

Label au centre par slot scopé (`font-size` proportionnel au diamètre, plancher au token xs) — pas de `contrast-color()` : il est dans le trou du donut, sur le fond de page. Indéterminé = `v-spin` sur le `<svg>` (keyframe partagée, `styles/utilities.css`) **+** `v-progress-circular-dash` sur l'arc, périodes décalées (×4 / ×5). `rotate: -90deg` en propriété individuelle pour se **composer** avec l'animation de `transform`. RTL : `scale: 1 -1` (progression anti-horaire).
- **VSlider** : deux `<input type="range">` superposés en mode range (`pointer-events` sur les thumbs uniquement, anti-croisement JS). Track 6px via tokens `--vectis-control-size-slider-*`. Custom properties inline en **fractions unitless** `--start-fraction`/`--end-fraction` (fill/ticks/labels/tooltips centrés sur le thumb réel). `orientation="vertical"` (`writing-mode` + `direction: rtl` sur `.v-slider-control`). `inputs` (compose `<VInput type="number">`, commit au `change` avec clamp/snap), `ticks`, `labels: SliderLabel[]` (pose `aria-valuetext`), `tooltip` (`:has(:active/:focus-visible)` — pas d'anchor positioning, le thumb natif n'est pas ancrable). Layout racine en grid à zones piloté par `:has()`.
- **VCalendar** : grille inline `role="grid"` (inspiration Material). Toute la logique de dates vit dans `utils/date.ts` (helpers PURS partagés avec VDatePicker, chaînes ISO `YYYY-MM-DD` en **heure locale** — jamais `new Date('YYYY-MM-DD')`/`toISOString()` ; noms via `Intl` sur dates de référence UTC, SSR-safe). `focusedISO` = **source de vérité unique** du mois affiché (les computed `viewYear`/`viewMonth0` en dérivent). Trois vues (`data-view` days/months/years, mois/années en `v-if`). Types de sélection (prop **`selection`**, type `CalendarSelection` — `mode` est réservé à l'affichage du champ chez VDatePicker/VTimePicker, d'où ce nom ici) : `single` (`string|null`) / `range` (`DateRange {start,end}`, prévisualisation au survol) / `multiple` (`string[]`) — le type du v-model suit `selection`. `min`/`max` (nav + sélection bornées), `disabledDates` (tableau **ou** prédicat → barrées, focusables non sélectionnables), `showAdjacentDays`/`selectAdjacentDays` (jours adjacents = spans statiques, ou boutons `data-outside` si sélectionnables), `events: CalendarEvent[]` (≤3 pastilles, couleur inline `--calendar-dot-color`), slots `#day` (contenu custom, ex. prix) et `#footer` (presets/actions). Roving tabindex + clavier flèches/Home/End/PageUp-Down(+Shift an)/Entrée. Tokens dédiés `--vectis-control-size-calendar-cell`/`-dot`. `today` posé en `onMounted` (pas de mismatch d'hydratation). Expose `focus()`.
- **VDatePicker** : champ `VInput` + `VCalendar` dans un `VPopover` en `mode="manual"` sans surface (PAS de VMenu ni de `#trigger` : `popovertarget` invalide sur `<input>` texte). Ancrage pur CSS `anchor-scope` (racine) / `anchor-name` (contrôle), le nom `--datepicker-anchor` transmis par prop `anchor` (précédent VTooltip/VCombobox), ouverture programmatique → **focus déplacé dans la grille** ; fermeture par `@focusout` racine + `Échap` (refocus champ) + sélection en mode simple. La coquille champ+panneau est partagée avec le VTimePicker (`composables/useFieldPanel`) — c'est elle qui porte la garde `defaultPrevented` sur ArrowDown/Entrée, sans laquelle l'Entrée de sélection du VCalendar remonte à la racine et rouvre le panneau qu'elle vient de fermer (couvert par un test). Passe-plat des props VCalendar + champ (`size`/`compact`/`clearable`…) ; texte du champ formaté via `Intl` (plage via `formatRange`). Icône de fin `calendar_today` (surchargeable par **`calendarIcon`**, absente sans panneau) et **croix d'effacement à sa GAUCHE** — pas une bascule : la croix passe par le `clearable` de VInput, donc l'ordre, les classes et le comportement sont ceux de VInput/VTextarea/VCombobox. C'est `clear-visible` (et non le défaut « champ non-vide ») qui la fait survivre au `readonly` du champ, et `clearValue()` doit garder son verrou `refocusing` : il focalise l'input PENDANT l'`emit('clear')`, ce qui rend inopérant le `focus()` que VInput exécute ensuite (déjà focalisé = aucun événement) et empêche la réouverture du panneau. Slot `#footer` reçoit `close`.
  **Deux modes de champ, prop `mode`** (le passe-plat de sélection du VCalendar s'appelle donc `selection` ici aussi ; `DatePickerMode`, ex-`DatePickerEntry`) : **`input` par DÉFAUT** et `readonly`. La saisie est **réservée à la sélection `single`** — une plage ou une liste retombe d'office en readonly, SANS avertir tant que `mode` n'a pas été fourni explicitement. Le défaut de la prop est d'ailleurs `undefined` et non `'input'` (résolu par `props.mode ?? 'input'`), pour la même raison que `showDial` : distinguer « non fournie » d'un choix explicite est ce qui permet de n'avertir que le consommateur qui a demandé quelque chose d'inopérant. En saisie, le champ est masqué : l'utilisateur ne tape que des chiffres, les séparateurs sont posés dès que le champ précédent est plein. Ordre des champs, séparateur et gabarit du placeholder sont **dérivés de la locale** par les helpers purs de `utils/date.ts` (`dateMaskFor`/`formatDateMask`/`isoToMask`/`parseDateMask`/`caretAfterDigits`/`maskPlaceholder`) — `formatToParts` y force `calendar: 'gregory'` + `numberingSystem: 'latn'` (sinon fa-IR renvoie une année persane, ar-EG des chiffres arabes-indiens) et le séparateur est pris **entre deux champs** puis nettoyé de ses marques bidi (hu-HU formate « 2021. 11. 22. »). `displayFormat` n'a pas cours en saisie (warn dev — donc il ne concerne plus que `mode="readonly"` et les sélections range/multiple) ; commit dès que la date est complète ET acceptable (bornes + `disabledDates`), **revert silencieux** au `change`/`blur` sinon ; année à 2 chiffres étendue au blur seulement (pivot FIXE 2000 — un pivot glissant rendrait les helpers impurs). Trois pièges, chacun verrouillé par un test qui rougit sans son correctif : (1) **`v-model` et non `:model-value` sur le VInput** — sans écouteur `onUpdate:modelValue`, `useModel` recopie en interne le texte BRUT tapé et le réécrit au patch suivant, effaçant le masque dès qu'il ne change pas lui-même (9e chiffre, caractère refusé) ; (2) **verrou de refocus** — le `focus()` rendu au champ par `closePanel(true)` rouvrirait le panneau, qui s'ouvre AU FOCUS : toute fermeture avec refocus passe par `closeAndFocus()` ; (3) **`endIconLabel` toujours défini** même sans icône rendue — `useIconClickHandlers` avertit AU SETUP dès qu'un `@click:icon-end` est attaché sans libellé, sans savoir si une icône existe. `useFieldPanel` gagne pour l'occasion `focusOnOpen` (ouvrir sans happer le curseur).
  **`showCalendar`** (booléen, défaut **false**) : en saisie le calendrier est **opt-in** — sans lui, ni icône, ni panneau monté, ni raccourci d'ouverture (un popover à chaque focus est du bruit dans un formulaire dense) ; la croix de `clearable` reste, elle. Sans effet en lecture seule, où le calendrier est le seul chemin. Point de coupure **unique** : `disabled: () => props.disabled || !hasPanel.value` passé à `useFieldPanel`, dont `disabled()` garde à la fois `openPanel` et `onControlClick` — donc clic, focus, ArrowDown, Entrée et icône deviennent inertes d'une ligne, sans garde répétée dans chaque handler. `aria-haspopup`/`-expanded`/`-controls` disparaissent avec le panneau (un `aria-controls` orphelin sinon).
- **VTimePicker** : même coquille que le VDatePicker, partagée via `composables/useFieldPanel` (champ `VInput` + `VPopover` en `mode="manual"` ancré `--timepicker-anchor`, focusout + Échap ; brouillon et live region par les crochets `onOpen`/`onClose`) ; v-model `'HH:mm' | null` **24 h canonique** quel que soit l'affichage. **Trois modes de CHAMP, prop `mode`** (BREAKING : `TimePickerMode` valait `'dial' | 'input'`, d'où le repli runtime sur le défaut + warn citant l'ancienne API) : **`input` par DÉFAUT** (champ masqué, cadran optionnel), `readonly` (le cadran est le seul chemin, `showDial` y est **forcé**) et `list`. Défaut de la prop à `undefined`, résolu par `props.mode ?? 'input'` **avant** la validation — sinon une prop absente tomberait dans la branche « valeur inconnue » et avertirait sur un `<VTimePicker />` nu. **`showDial`** (défaut `undefined`, PAS `false` : c'est ce qui distingue « non fournie » d'un `false` explicite et évite d'avertir la configuration par défaut) suit `showCalendar` du VDatePicker — ignoré en `list` + warn. Même point de coupure unique : `disabled: () => props.disabled || !hasPanel.value`.
  **Cadran** (brouillon commité par OK seulement ; Annuler/Échap/focusout abandonnent) : **`role="slider"` unique** (flèches ±1 h / ±`minuteStep` min, PageUp/Down ±5, Entrée arrête l'étape heure → minutes → commit), chiffres `aria-hidden` positionnés par **`sin()`/`cos()` CSS** sur fraction de tour inline `--dial-turn` (idiome `--fill-fraction` VSlider), aiguille en `rotate` **sans transition** (le wrap 55→0 min interpolerait par le grand tour) dont la pastille de pointe (`::before`) fait la taille d'une cellule de chiffre sur un repère — elle le recouvre — mais tombe à `--vectis-control-size-timepicker-hand-minor` sur une minute hors repère 5 min (`[data-minor]`), où elle ne recouvre rien et déborderait sur les deux voisins : à cette taille elle est à elle seule le repère précis, sans le point clair central de M3. Cette bascule de taille est le SEUL élément animé de l'aiguille (transition `--vectis-duration-fast` sur `inline-size`/`block-size`, annulée en `prefers-reduced-motion`) : elle interpole entre deux valeurs bornées, là où le `rotate` reste sans transition. Ne jamais obtenir cette réduction en redéfinissant `--vectis-control-size-timepicker-number` sur l'aiguille (il alimente `--dial-radius`, donc la longueur de l'aiguille et le rayon des anneaux). `left`/`top` **physiques délibérés** (une horloge ne se miroite jamais en RTL ; le groupe HH:MM force `direction: ltr`), 24 h = double anneau extérieur 12,1–11 / intérieur 00,13–23, géométrie pointeur **pure dans `utils/time.ts`** (`angleToIndex`/`DIAL_INNER_THRESHOLD` couplé aux tokens du cadran, testable — jsdom ne mesure rien ; ne toucher ni au seuil ni aux tokens sans l'autre), `setPointerCapture` sous try/catch, `touch-action: none`. Les deux grosses cellules HH/MM sont des **`VButton` `size="lg"` `variant="tonal"`** dont le `tone` passe neutral → accent selon l'étape : `--tone-bg-soft`/`--tone-text-tinted` reproduisent EXACTEMENT l'ancien couple surface-muted/text ↔ accent-surface/accent-text, la surcharge locale se limitant au gabarit « grand chiffre » (`[data-size]`, modèle VIconButton/VTabs). Le focus du panneau vise le slider par **requête DOM** (`VTimePickerDial` n'a aucun `defineExpose` et n'a pas à en gagner un). Pas de caption, pas de bascule de mode dans le pied.
  **Saisie** : décalque du VDatePicker `mode="input"` (masque, caret, revert silencieux, verrou `refocusing`, `v-model` obligatoire sur le VInput, `endIconLabel` toujours défini) — mais le séparateur `:` est **universel**, d'où une forme CLOSE (`timeCaret`) au lieu du `caretAfterDigits` balayant de `date.ts`.
  **Liste** : `VPopover` en `surface` + `.v-timepicker-list v-control` + `role="listbox"`, rangées `<button role="option" tabindex="-1">` locales (surtout pas `VComboboxOption`, interne à VCombobox), **focus DOM dans le panneau** (modèle VMenu/VCalendar, pas `aria-activedescendant`) → `utils/arrowNav` adoptable, avec liste PROPRE et non `navigableItems` (qui appelle `getComputedStyle` par élément — inacceptable sur des dizaines de rangées). Défilement à l'ouverture par `scrollIntoView?.({block:'center'})` + `focus({preventScroll:true})`. **Commit direct + fermeture** (ni brouillon ni pied) ; piège : l'Entrée doit faire `preventDefault` ET commiter explicitement, sinon le clic natif du `<button>` ferme puis la racine rouvre (la garde `defaultPrevented` de `useFieldPanel` ne jouerait pas) — couvert par un test qui rougit sans lui.
  Format 12 h/24 h dérivé de la locale (`resolvedOptions().hourCycle`), surchargeable par `format` ; **AM/PM = `VToggle mandatory` posé À CÔTÉ DU CHAMP** (hors du popover, donc utile aux trois modes) qui écrit le v-model — et non plus le brouillon ; sans valeur le choix est mémorisé dans `pendingMeridiem` ('AM' en dur : déterministe donc SSR-safe), et cadran ouvert le brouillon est resynchronisé sinon OK réécrirait l'ancien méridien. Son alignement sur le CHAMP (et non sur le bloc VInput, qui empile label/champ/hint) passe par une compensation en marges dérivées des tokens de typo sous `:has(.v-input-label)` / `:has(.v-input-hint)`. Étape annoncée par live region polie. Icône fin `expand_more` (liste, convention VCombobox) ↔ `schedule` (surchargeable par **`clockIcon`**, qui ne couvre QUE le cadran) ↔ **`undefined`** (saisie sans cadran), avec la **croix d'effacement à sa gauche** — même câblage que le VDatePicker (`clearable`/`clear-visible` de VInput, verrou `refocusing` dans `clearValue()`), donc en `mode="list"` le couple croix + chevron du VCombobox. Tokens `--vectis-control-size-timepicker-*` (le `-cell-h` est mort : la hauteur vient de `--control-height`) ; `VTimePickerDial.vue` interne non exporté.
