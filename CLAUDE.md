# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## The project

**Vectis UI** (`@vectis/ui`): a Vue 3 + TypeScript design system shipped as an npm library, Nuxt 3 (SSR) compatible. pnpm monorepo — `packages/ui` holds the library, `apps/docs` the documentation site (a Nuxt 3 app, statically generated, published to GitHub Pages — see its own section below). A live-theming app manipulating the token source programmatically is still to come. Project language: **English** (code, comments, docs). Storybook stories are **bilingual FR/EN** (see Storybook below).

## Commands

Everything runs from the root (pnpm enabled through corepack):

```bash
pnpm lint              # eslint (root flat config)
pnpm format            # prettier --check   (format:fix to fix)
pnpm typecheck         # vue-tsc -r
pnpm test              # vitest run -r  → `unit` project (jsdom) only
pnpm test:stories      # play functions + axe in Chromium (Vitest browser mode), light theme
VECTIS_THEME=dark pnpm test:stories   # the same suite in the dark theme
pnpm test:coverage     # BOTH projects in one run, merged v8 report → packages/ui/coverage/
pnpm build             # lib build (tokens in prebuild, CSS split check in postbuild)
pnpm tokens            # regenerates tokens.css + tokens.json from the TS source
pnpm icons             # regenerates the SVG icon registry (network; on demand, NOT in prebuild)
pnpm storybook         # dev server, port 6006
pnpm build-storybook

pnpm --filter @vectis/ui run tokens:check    # generated artefacts vs the TS source, without writing
pnpm --filter @vectis/ui run check:package   # publint + attw, AFTER a build (see below)

pnpm --filter @vectis/docs dev               # documentation site, port 3000 (builds the lib first)
pnpm --filter @vectis/docs build             # nuxt generate → .output/public, + check-prerender
pnpm --filter @vectis/docs preview           # serves the ARTEFACT, the only way to exercise the base URL
pnpm --filter @vectis/docs icons             # regenerates the docs icon registry (network; on demand)
```

**`check:package` must never move into `postbuild`**: `attw --pack` shells out to `npm pack`, which fires `prepack` → `build` → `postbuild` → `attw`, unbounded. CI calls it as its own step. It is also what guards the `.d.ts` extension rewrite (`dtsExtensions` in `vite.config.ts`) — without which a consumer on `node16`/`nodenext` resolution gets NO types at all, silently.

**CI** (`.github/workflows/ci.yml`) runs the whole checkpoint on push and PR, plus `tokens:check`, `check:package`, and `test:stories` in a two-value matrix (light and dark) — the dark axe pass has no other scheduled runner.

A single test: `pnpm --filter @vectis/ui exec vitest run --project unit src/components/VButton/VButton.test.ts` (or `-t 'test name'`).

**Never prefix a shell command with `cd` or `Set-Location`** — the working directory is already the repo root. Use paths relative to it (`pnpm --filter @vectis/ui exec …`, `packages/ui/src/…`). A leading `cd` turns the call into a compound command, and the permission allowlist arbitrates each segment separately: the prefix alone is what makes an otherwise-allowed `pnpm lint` prompt.

Checkpoint before wrapping up a step: `pnpm lint && pnpm typecheck && pnpm test && pnpm build && pnpm build-storybook` must all pass. `pnpm test:stories` is **outside the checkpoint** (it needs the Playwright binaries, ~115 MB, via `pnpm --filter @vectis/ui exec playwright install chromium`): run it as soon as you touch a play function, browser behaviour, **a colour token or any markup carrying a role** — it also runs axe, and **in BOTH themes** (see Accessibility below).

## Philosophy (non-negotiable — from the project brief)

1. **HTML/CSS first, JS as a last resort.** Native primitives: `<dialog>`+`showModal()`, Popover API, CSS Anchor Positioning, `<details>`, `:user-invalid`, `:has()`, `color-mix()`, `@starting-style`… Any behavioural JS must be **justified by a comment** in the component (see VMenuPanel.vue: the JS is limited to keyboard roving focus and the v-model ↔ imperative popover API bridge; and VHotkeys.vue, which holds the DS's ONLY `navigator` read and its ONLY document-level listener — the latter opt-in through `listen`).
2. **Zero runtime dependency besides Vue** (`peerDependencies: { vue }` only). No floating-ui: for floating elements, CSS anchor positioning under `@supports` + a small in-house JS fallback (~30 lines) if needed.
3. **No raw values in component CSS** (colour, radius, spacing, type, shadow, duration): semantic `var(--vectis-*)` tokens only. A duration names the step it wants (`var(--vectis-duration-1000)`), never a multiplier on another one. Tolerated: `1px` borders, opacities.
4. **SSR-safe (Nuxt 3)**: no `window`/`document`/browser-API access outside `onMounted`/`watch`/handlers. Support detection (`CSS.supports`) client-side only. IDs through Vue's `useId()`.

## Comments

Every comment is written in **English, as complete sentences** rather than telegraphic shorthand. **Length is not a defect**: a comment that takes four lines to be genuinely clear is better than a one-liner only its author can decode. What is still a defect is a comment that says nothing (a banner, a restatement of the identifier on the next line) or that is out of date. Two audiences, so two registers:

- **The module's introduction block is written for anyone** — an integrator, a designer, someone who is not an expert front-end developer. It is the raw material of the documentation, so it says what the thing is and what it is for in plain prose, spelling out the concepts instead of assuming them.
- **Every other comment is written for a front-end developer.** It may be as long as it needs to be, but it can freely name the platform and the framework (the cascade, the top layer, `flush: 'post'`, hydration) without explaining them from first principles.

**Keep:**

- **One header block per module**, at the very top of `<script setup>` **before the imports**. It introduces the component in plain prose — what it is for the user, how it is built, and **why any behavioural JS exists** (philosophy rule 1 makes that justification mandatory, not optional).
- **JSDoc on props, slots, emits and exported functions.** It is the only source of the description column in Storybook's `<Controls>` table (there are no `argTypes.description` anywhere in the repo), and it drives IDE hovers — so it is read by integrators, not just by us: write a full sentence, say what the option does and what its default behaviour is.
- **Trap comments**: wherever deleting a line would let someone silently break the code — a cascade-order dependency, a CSS cycle, a `flush: 'post'`, a guard whose absence produces no error — spell out the mechanism AND the symptom, so the reader can recognize the bug if it ever comes back.

**Delete:** section banners, anything that merely restates the next line without adding meaning, and any comment recording a past state (what a thing used to be called, which bug it fixed, which component did it first). Docs and comments describe the code as it is now.

## JS by intention

Philosophy rule 1 requires every behavioural JS block to be justified. That justification used to exist only as prose — unreadable in bulk, uncountable, unverifiable. Each block now also carries a **one-line tag** stating WHY it exists, from a **closed vocabulary of six**:

```
@core      behaviour the component cannot exist without
@a11y      ARIA state, focus management, accessible name, live region
@keyboard  key handling, roving focus
@ssr       hydration determinism, no DOM at setup
@fallback  API absent from the environment, progressive enhancement
@devwarn   integrator-facing warning (isDev)
```

Cumulative, **least specific last** — `@keyboard @a11y`, `@ssr @core`. The tag goes on its **own `//` line ABOVE** the block's existing comment (which is never rewritten), and **NEVER inside a JSDoc body**: prop/slot/emit JSDoc is the sole source of Storybook's `<Controls>` description column, where an unknown tag would be absorbed by the docgen. A trivial one-liner takes no tag — "a comment that restates the code is noise" still wins. The three big pure-domain modules (`utils/date`, `utils/time`, `utils/file`) carry ONE module-wide tag instead of fifty identical per-function ones.

Current state — **188 tag lines over 76 files**:

|             | lines | of which pure |
| ----------- | ----: | ------------: |
| `@a11y`     |    93 |            45 |
| `@core`     |    74 |            38 |
| `@keyboard` |    41 |             6 |
| `@ssr`      |    26 |            10 |
| `@fallback` |    17 |            13 |
| `@devwarn`  |    13 |             9 |

**One line of behavioural JS in two carries `@a11y`**, against 38 lines of pure `@core`. That is the number to keep an eye on: the JS in this DS exists first to make the components accessible, not to make them work. A new component whose script is mostly `@core` is a component that has probably been written twice.

Checks: `git grep -hoE '// @[a-z0-9]+' -- packages/ui/src | sort -u` must return exactly the six; and no tag may appear inside a `/** */` body.

## Token architecture (the core of the project)

Chain: `src/tokens/*.ts` (typed source of truth, DTCG format `{ $value, $type, $description? }`) → `scripts/build-tokens.ts` (via `pnpm tokens`, run automatically in `prebuild`/`prestorybook`) → `src/styles/tokens.css` + `src/tokens/tokens.json`. An inline Vite plugin (`vite.config.ts`) also emits `dist/tokens.json`.

- **Two namespaces, never to be mixed.** `--vectis-*` = the **public tokens**, generated from the TS source, documented, overridable at runtime by the consumer. Everything else is **private and non-contractual**: a component's local variables, which are **qualified** — either by their component (`--skeleton-w`, `--side-nav-level`, `--dial-radius`, `--calendar-cell`), or by the cross-cutting contract they embody (`--tone-bg-solid` & co for tones, `--control-*` for the size scale, `--fill-fraction` shared by both Progress components and VSlider). **Qualification is not cosmetic**: these variables INHERIT (`.v-control` sets them, every descendant reads them), so a generic name like `--size`, `--radius` or `--gap` would be captured by any host app that defined it on an ancestor — and nothing here would see it, since jsdom does not evaluate styles. Every new local variable therefore takes a qualified name.
- **The `--<component>-anchor` idents are NOT tokens**: `--popover-anchor`, `--combobox-anchor`, `--datepicker-anchor`, `--timepicker-anchor`, `--tooltip-anchor` are `anchor-name` dashed-idents, absent from `tokens.css` and not overridable. Naming them `--vectis-*` would invite the opposite belief. Each has exactly 3 sites (an `anchor-name`, an `anchor-scope`, at least one consumer) and **one of them is a TypeScript prop value**, therefore invisible to any CSS tool: making them diverge by one character paints the panel at the viewport origin, with no console error.
- **Two levels**: primitives (`primitives.ts` — OKLCH palettes, scales) and semantics (`semantic.ts` — the only ones components consume). DTCG aliases `{color.gray.500}` are resolved to `var(--vectis-color-gray-500)` at build time (`css.ts`, also exported through `@vectis/ui/tokens` for the future theming app). Aliasing works **primitive → primitive** too, and one token relies on it: `font.family.display` points at `font.family.sans`, which is what makes a heading typeface a single override rather than a duplicated font stack.
- **The palette is Tailwind CSS 4's, all 26 families × 11 steps**, transcribed from its published `theme.css` (never from memory — the repo's rule on standard data). Only five are wired to a role: `gray` (surfaces, text, borders), `indigo` (accent), `red`/`green`/`amber` (danger/success/warning); the other twenty-one ship unused so an application can point a role at one without a release. **TRAP — `neutral` means three unrelated things**: the Tailwind palette of that name (pure grey, which NO role consumes), the greys the DS actually paints with (`gray`, faintly blue), and `tone="neutral"`, a component role. `git grep neutral` hits all three; check which one you are in before substituting anything.
- **Shadow is `xs/sm/md/lg/xl`** and **radius carries a `none`** (`0px`, unit-bearing: it is subtracted in `calc()` to derive a nested corner, and `calc(0 - 1px)` is invalid).
- **Motion is two layers, unlike the rest**. Primitives: a scale named after its own milliseconds — `--vectis-duration-0/50/100/150/200/300/400/500/700/1000/1500/2000/3000/5000`. Semantics: the three roles a `transition` asks for, `fast` (150) / `base` (200) / `slow` (300). A **long looping animation names the primitive directly** (VSpinner, VProgressCircular, VProgressLinear, VSkeletonLoader, and their `prefers-reduced-motion` counterparts) — the one sanctioned reach into a primitive outside the `--vectis-font-*` list, because a 1s loop is a duration and not a role. That is what replaced eleven `calc(var(--vectis-duration-slow) * N)` sites whose multipliers made the real periods (1050 ms, 1200 ms…) unreadable and unrelated. Motion never varies by theme, so `dark.ts` holds nothing of it.
- **Themes**: `themes/dark.ts` may override ONLY existing semantic keys (the build checks this and fails otherwise). The generated CSS sets `:root` (everything) + `[data-theme='light']` and `[data-theme='dark']` (semantics only) → theming per DOM subtree, runtime override without a rebuild.
- **`src/styles/tokens.css` and `src/tokens/tokens.json` are GENERATED**: never edit them by hand (they are in .prettierignore; every change goes through the TS source + `pnpm tokens`). **The repo's second generated artefact is `src/components/VIcon/icons.ts`** (`pnpm icons`) — same discipline, different trigger: it is NOT wired into `prebuild` (its script downloads from `google/material-design-icons` at a pinned revision, and the build must not depend on the network).
- **Dedicated dimension tokens**: never `--vectis-space-*` for a component dimension (track, thumb, pill height…) — create a dedicated semantic token. Real spacing (gutter, offset, compact delta, padding) stays legitimately `--vectis-space-*`.
- **Semantic typography**: the `text` group in `semantic.ts` — one role = one complete recipe `--vectis-text-<role>-size/weight/leading[/tracking]` (display, heading-1…4, subtitle, body-lg/md/sm, label, caption, overline, code) + the three families `--vectis-text-family`/`-family-heading`/`-family-code` + the technical `control` role (weight/leading of control labels; the size comes from `--control-font-size`). Component CSS consumes these recipes, never the `--vectis-font-*` primitives — deliberate, commented exceptions: state emphasis in `--vectis-font-weight-semibold` (VDataTable th, VToast title, VAvatar initials, VCalendar selection/today), VInputOTP's contextual scale, VIcon's font contract.

## CSS cascade

`src/styles/index.css` declares the order: `@layer vectis.reset, vectis.tokens, vectis.components, vectis.utilities;`. Any non-layered consumer style wins — that is the intended override mechanism.

**The layers carry the LONG name where the classes carry `v-`**, and that is not an inconsistency: a layer name is **global and not namespaced**. A consumer writing `@layer v { … }` would see their block absorbed into the DS's and arbitrated by the order declared here — a silent cascade bug, invisible in dev. The shorthand is justified for a class (it is written in the HTML, read in devtools, typed hundreds of times); not for an identifier typed 56 times inside `<style>` blocks and never by a user. **An SFC keeping an undeclared layer would be ordered AFTER every declared layer, and would therefore win over everything** — and since the split it ships in an isolated file, with no neighbours to make it obvious. The `git grep -E "@layer\s+(?!vectis)"` still applies to the source; on the artefact the guard is now mechanical (`scripts/check-css-split.ts`, run at `postbuild`).

- Every SFC has one **non-scoped** `<style>` whose entire content is wrapped in `@layer vectis.components { … }`. The local-variable tables (tones + `[data-custom]`, sizes `data-size`/`data-compact`) live there too, right before the rules that consume them — **one `<style>` per SFC, never a neighbouring CSS file** — no `X.tokens.css` alongside. Internal order stays meaningful: `[data-custom]` after the tones, same specificity, last one wins.
- **NOTHING may depend on the order of two component sheets** — each ships in its own file and the consumer's bundler decides where they land. The export order in `src/index.ts` is editorial (dependency → dependent, for reading). A declaration that would collide with another component's **at equal specificity** is therefore qualified — `[data-size]` (`.v-tab`, `.v-toggle-item`, `.v-icon-button`, `.v-pagination-page`), a compound class (`.v-button-group.v-pagination-items`, `.v-popover-panel.v-tooltip-panel`), a descendant (`.v-table-toolbar .v-input`) — or routed through the custom property the target already reads (`.v-table-title` sets `--typography-color`, which `.v-typography` consumes, instead of a colliding `color`). This is the ONE rule the split turned from convention into correctness: it used to be papered over by the bundle order.
- **Shared stylesheets** (`src/styles/`, imported by `index.css` in this order: reset, tokens, tones, floating, panel, control-size, utilities): `tones.css` (`.v-tone` — the tone table, see below), `floating.css` (`.v-overlay` — the foundation of EVERY popover; `.v-floating` — anchoring and placements), `panel.css` (`.v-panel` — the common chrome of panels listing rows: VMenu, VCombobox; set by VPopover's `surface` prop), `control-size.css` (`.v-control`), `utilities.css` (`.v-visually-hidden` + the global `v-spin` keyframe, shared by VSpinner and VProgressCircular: `@keyframes` are not arbitrated like declarations, so they sit outside any layer and are declared once). Rule for `.v-panel`: put ONLY declarations there that no panel redeclares — `.v-panel` and `.v-menu`/`.v-combobox-panel` have equal specificity (0,1,0), and the shared sheets now arrive in a file of their own, so a shared declaration would be arbitrated by an order nobody controls. Dimensions (`min/max-inline-size`, `max-block-size`, `overflow`) therefore stay with each panel — `position-anchor` comes from `VPopover`, which also sets `.v-panel` through its `surface` prop. When a panel genuinely MUST redeclare (VDatePicker cancels the padding, VTimePicker's dial changes `gap`/`padding`), the sanctioned form is the compound selector **`.v-popover-panel.v-x-panel`**: `VPopover` puts `.v-popover-panel` on that same element unconditionally, where `.v-panel` follows the `surface` prop — so the compound is available even to VTooltip, which passes `surface: false`. **Corollary — VDatePicker and VTimePicker render their VPopover as a `surface`**: the former because VCalendar carries no background or radius of its own; the latter for BOTH of its panels (a single `VPopover` serves the dial and the list), the dial panel keeping only its column layout and padding.
- Build: **one sheet per component**, `dist/<path>/VX.css`, imported by its own `dist/<path>/VX.js` — a consumer downloads the CSS of what they import (a lone VButton: 4.6 kB gzip against the 18.0 kB of the former bundle). `dist/styles.css` keeps its name and its export but carries the CORE alone (reset + tokens + floating + panel + control-size + utilities, 3.8 kB gzip), and stays an explicit consumer import: a `<link>`-able artefact is what Nuxt's `css: []` and critical-CSS extraction need. Mechanism in `vite.config.ts`: `cssCodeSplit: true`, an `assetFileNames` function that names each sheet after its SFC, and the `shipComponentCss` plugin, which puts back the import Vite strips (an app injects its `<link>` from the HTML; a library has no HTML) and stamps the layer-order statement on every sheet — a `@layer vectis.components{}` block parsed before that statement would pin the layer FIRST, under the reset, irreversibly. **`sideEffects: ["**/*.css"]` is load-bearing**: it is what stops the consumer's bundler from pruning `import './VX.css'`.

## Component conventions

- **Naming, three tiers.** `V` + PascalCase for **components** (`VButton`, `VComboboxOption`, `VTimePickerDial`): the prefix removes the ambiguity of a tag in a template (`<VButton>` vs the native `<button>` vs another library's `Button`). `Vectis` + PascalCase for **cross-cutting** public types, which carry the brand (`VectisMessages`, `VectisMessagesInput`, `VectisIconName`). **No prefix** for types **owned by a component** (`ButtonTone`, `TabsVariant`, `ComboboxOption`, `DataTableColumn`, `CalendarSelection`…): a type inside an `import type {}` has none of a tag's ambiguity, and above all this is what keeps `VComboboxOption.vue` and the `ComboboxOption` type in two distinct namespaces. Prefixing them would collide the component and its type on the same identifier.
- One folder per component: `src/components/VX/VX.vue` + `VX.stories.ts` + `VX.test.ts` + **`VX.mdx`** (Storybook doc — mandatory, written with every new component). Named export added to `src/index.ts`. **Ancillary** files keep their role name, unprefixed: `context.ts`, `state.ts`, `resolver.ts`, `types.ts`, `iconProps.ts`, `icons.ts`, `keyboard.ts` — the `V` marks a tag, and a TS module has none.
- `.v-<name>` classes; **variants through `data-variant` / `data-tone` / `data-size`** (no class proliferation). Tones define local variables `--tone-bg-solid`, `--tone-text-tinted`… that the variants consume (see VButton.vue, the reference model). The table itself lives ONCE in `src/styles/tones.css`, on the class **`.v-tone`** set on the element carrying `data-tone` — the `.v-control` model. Adopters: VButton, VChip, VToast. **`neutral` solid is a full text/surface INVERSION**, and that value is canonical, not a component's taste: `surface-muted` would make `--tone-bg-solid` equal to `--tone-bg-soft` (a solid neutral indistinguishable from a soft one), and `surface-inverse` equals `surface-muted` in dark, where a selected neutral control would then vanish. Its hover/active consequently mix towards `surface`, the opposite direction from the chromatic tones. **It is declared in `vectis.tokens`, one layer BELOW the components**, and that is the whole point: a component overriding a tone (VToast's `neutral`, VChip's `[data-custom]`) sits at EQUAL specificity with it — `.v-toast[data-tone='neutral']` and `.v-tone[data-tone='neutral']` are both (0,2,0) — so in the same layer the winner would depend on the sheet order the consumer's bundler decides. One layer down, every component rule wins by construction. Deliberately NOT adopters: VBadge, VTypography, VProgressLinear and VProgressCircular map a tone to a SINGLE local variable (`--badge-bg`, `--typography-color`) and never consume the `--tone-*` contract — routing them through it would add coupling without removing any duplication.
- API: typed `defineProps` + `withDefaults`, typed `defineSlots`, `defineModel` for v-model, typed `defineEmits` only when there are non-native events. Native attributes go through fallthrough (never redeclared).
- **Wrapper-root pattern** — a component whose root is a wrapper (hidden controls VCheckbox/VRadio/VSwitch inside an enclosing `<label>`; VInput/VTextarea fields; VChip): `defineOptions({ inheritAttrs: false })` + `v-bind="$attrs"` on the functional element (native control / action), keeping `class`/`style` on the root. Otherwise `name`/`required`/`aria-*` land on the wrapper and break forms and accessibility. A hidden input is hidden with `opacity: 0` (stays focusable and submitted), never `display: none`.
- Manipulating a DOM property with no HTML attribute (e.g. `indeterminate`): `watchEffect(..., { flush: 'post' })` — in `pre` flush the template ref is not set yet on the first pass.
- Visible focus: `outline: var(--vectis-focus-ring-width) solid var(--vectis-focus-ring-color)` + offset token. `@media (prefers-reduced-motion: reduce)` for every transition/animation.
- **`src/composables/` and `src/utils/`** — see "Shared code" below. A helper whose natural OWNER is one component stays in its folder even when imported elsewhere: `VIcon/iconProps.ts` produces `VIcon` props, so VIcon sets the contract (same for `VIcon/types.ts` and `VIcon/resolver.ts`).

## Shared code (`src/composables/`, `src/utils/`)

Two folders, one sharp boundary: **`composables/`** = Vue behaviour (`ref`/`computed`/`watch`/lifecycle); **`utils/`** = helpers with no Vue state (pure computation and imperative DOM). Nothing is publicly exported — `index.ts` is untouched, these are internal modules. Admission rule: **≥2 consumers AND a genuinely common body**.

**`utils/`** — `date.ts` and `time.ts` (date and time logic: ISO `YYYY-MM-DD` and 24 h `HH:mm` strings, all in local time, `Intl` on UTC reference instants → SSR-safe; consumed by VCalendar/VDatePicker and VTimePicker/VTimePickerDial); `number.clamp(n, min, max)` (on an empty interval `min` wins: `max` may be derived from an empty list); `css.px(v)` (number or numeric string → `12px`, otherwise `undefined` rather than an invalid custom property); `text.normalizeText(s)` (NFD, accent-insensitive filtering — VCombobox, VDataTable), `text.pad2(n)` and `text.digitsOf(s)` (purely lexical helper: the input masks of VDatePicker and VTimePicker only ever know the digit run, never the separators, which they place themselves — hence its home here rather than in `date.ts`); `array.toggleValue(list, v)` (never mutates in place: the new reference is what wakes consumer v-models — VToggle, VCombobox, VCalendar, VDataTable); `matcher.resolveMatcher(array | predicate)` (the `disabledDates`/`disabledPages` convention, resolved ONCE in a `computed`, array → `Set`); `env.isDev` (dev guards, optional access to `import.meta.env` so it stays inert in a non-Vite consumer); `file.ts` (the FILE domain, grouped by subject like `text.ts`: `matchesAccept` — the `accept` rule in JS, because the ATTRIBUTE has no say over a drop; `formatBytes` — SI base 1000, the base `Intl`'s sanctioned unit names actually mean; `screenFiles(incoming, current, limits)` — the screening of a batch, which RETURNS its refusals instead of emitting them, so the order `type → size → count → total-size` (a contract both `.mdx` state) is testable without a mount. Consumed by VFilePicker and VFileUpload); `vnode.flattenSlot(nodes)` (a slot's VNodes reduced to the elements actually rendered: Fragments from a `v-for` unwrapped, a false `v-if`'s Comment and whitespace Text dropped. It is what lets a component know how many children it was given WITHOUT a registry the children feed at mount — a registry renders 0 on the server and N on the client, the same hydration argument as VTabs' `hasPanels`. Consumed by VAvatarGroup and VCarousel); `chip.chipScaleFor(size, compact)` (the scale of a VChip rendered INSIDE a text field — VCombobox's values, VFilePicker's files: one step below the field, the catch-up going through `compact`. It also returns the **`height`**, set inline as `--chip-height`: the field has to force its `<input>` to the chips' height or it grows on focus, and that height used to be restated as a four-rule CSS table in EACH consumer with a comment asking that the two be kept in step by hand — deriving it from the same pair makes them incapable of drifting); `arrowNav` (below).

**Memoized `Intl` formatters.** `file.ts`, `date.ts` and `time.ts` each keep a module-level `Map` of formatters keyed by `(locale, …)`. Construction costs one to two orders of magnitude more than use, and these functions are called ONE VALUE AT A TIME — `timeList(1, …)` formats 1440 entries, measured at ~82 ms against ~2 ms memoized. Any new per-call `Intl` helper takes the same treatment; the ones that already format a whole list (`weekdayNames`, `monthNames`) just hoist their formatter out of the loop.

**`utils/arrowNav.ts`** — `navigableItems(container, selector)` + `arrowNavigate(event, container, items, { vertical })`, the SINGLE incarnation of arrow-key navigation: DOM discovery (no registry), `display !== 'none'` filter (an item hidden by a container query or by the consumer does not take focus), modulo wrap, RTL inversion on the inline axis only, `preventDefault` applied only when the key is handled. Contract: **move focus, never activate** — activation on focus (VTabs `activation: 'automatic'`) is set by the component, in its own `@focus`. Adopters: VPagination, VTabs, VToggle, and VMenuPanel which passes its OWN list (it also excludes `aria-disabled` items and confines roving to the current panel). Deliberately outside: VCalendar, VCombobox, VInputOTP, VTimePickerDial — they navigate a space of **values**, not a DOM list, and their list edge is a domain clamp.

**`composables/`**

- **`usePopover(el)`** → `{ shown, syncShown, show, hide }`, the state plumbing of a `[popover]` (the JS counterpart of `floating.css`). Two invariants: `shown` is fed **by the DOM** — wire `syncShown` to the panel's `@beforetoggle` AND `@toggle` (the first is synchronous and catches light dismiss, the second is the only one the jsdom stub emits; ToggleEvents do not bubble, so always on the popover element itself) — and **never set by hand**; the idempotence guards avoid `hidePopover()`'s `InvalidStateError` on an already-closed popover. **Every popover in the DS goes through it**: VMenuPanel and VToaster directly, all the others through the `VPopover` component (VCombobox, VTooltip, VDatePicker, VTimePicker). Idiom: **one instance per popover** when a component drives several (VToaster: one per placement, indexed in a `Map`, each carrying its own element ref).
- **`useFieldPanel({ rootEl, panelRef, fieldEl, disabled, focusInPanel, onOpen?, onClose? })`** → `{ open, openPanel, closePanel, onControlClick, onFocusout, onKeydown, onPanelMousedown }`. The "field + `VPopover` in `mode="manual"`" shell of VDatePicker and VTimePicker (their field is read-only only in some modes). The panel is **written imperatively** (`panelRef.show()/hide()`) and **read by model** (`open`, to be bound as `v-model:open` on the VPopover, which feeds it from the DOM): the write must stay synchronous, since the `rAF` that moves focus assumes the panel is already open when it is armed. A `manual` popover does nothing on its own: no light dismiss, no focus move, no focus return to the field. `onOpen`/`onClose` carry what is specific to each component (VTimePicker's draft and step, clearing its live region). `onKeydown` guards `!event.defaultPrevented` on ArrowDown/Enter: **an Enter consumed inside the panel has just closed it and would reopen it as the event bubbles to the root** (covered by a unit test). **`onPanelMousedown` (to be bound as `@mousedown` on the VPopover)** cancels mousedown on the panel's NON-interactive areas: clicking a non-focusable pixel (padding, the gutter between cells) hands focus back to `<body>`, the root's `focusout` fires with a null `relatedTarget` and closes a panel that was just clicked — in VTimePicker that discarded the pending draft. The filter (`closest('button, a, input, select, textarea, [tabindex]')`) is essential: VCombobox's unconditional `preventDefault`, whose focus never leaves the field, would here rob the days and navigation arrows of focus and desynchronize VCalendar's roving. **Invisible in jsdom** (no focus on click) → the `ClicDansLeVide` play functions of both components, verified red without the handler.
- **`useFocusoutDismiss(root, close)`** → the root's `@focusout` handler. A popover stays a DOM descendant even when painted in the top layer, so `contains` is enough; a null `relatedTarget` counts as leaving too. Adopters: VCombobox, and VDatePicker/VTimePicker through `useFieldPanel`.
- **`useRootAttrs()`** → `{ attrs, rootClass, rootStyle, forwardedAttrs }`, the plumbing of the **wrapper-root pattern** (7 adopters: VInput, VTextarea, VTabs, VCombobox, VDataTable, VDatePicker, VTimePicker). `defineOptions({ inheritAttrs: false })` stays in the SFC (it is a compilation option). `rootClass` is typed `ClassBinding` (redeclared locally: `@vue/runtime-dom` exports `ClassValue`, the `vue` package does not re-export it, and `unknown` is rejected by the template).
- **`useAriaLabel(() => props.label)`** → precedence `aria-labelledby` > `aria-label` > `label` prop. Required as soon as a component with `inheritAttrs: false` renders both `v-bind="forwardedAttrs"` and `:aria-label` (VTabs, VToggle) — without arbitration both apply. Elsewhere (VPagination, VBreadcrumb, VToaster, VInputOTP) Vue's fallthrough already makes the consumer's attribute win: there the composable only removes a now-redundant default. Do NOT apply it to VIcon/VIconButton, where `label` is the accessible name of an icon-only control.
- **`useTimer()`** → `{ start(fn, delay), cancel() }`, a re-armable `setTimeout` cancelled on unmount; `delay ≤ 0` runs **synchronously** (DS convention: 0 disarms the deferral; `setTimeout(…, 0)` would not be synchronous). Adopters: VTooltip (open delay), VMenuItem (hover intent delay — ONE instance, since opening and closing are mutually exclusive), VCombobox and VDataTable (their debounces, each keeping its own semantics: dedupe by term on one side, commit to a `ref` on the other). VToaster stays out: its `Map<id, timeout>` is a different structure.
- **`useFieldIds(attrs, hasHint)`**, **`useIconClickHandlers({ name, iconStartLabel, iconEndLabel })`**, **`useTextLimit({ el, text, maxlength, softLimit })`** — shared by VInput and VTextarea. Respectively: ids and `aria-describedby` aggregation (a consumer `id` WINS over the internal `useId()`); detection of `@click:icon-*` listeners in `vnode.props` (declared emits are removed from `$attrs`) with the a11y guard; counter, overflow and soft limit through `setCustomValidity`.
- **`useFileDrop(enabled, onFiles)`** → `{ dragging, onDragEnter, onDragOver, onDragLeave, onDrop }`, the drop-target plumbing of VFilePicker and VFileUpload. It carries ONCE the two traps that are the module's real asset: `dragover` MUST `preventDefault`, or the browser refuses the drop and then NAVIGATES to the file, replacing the page; and the state is a depth COUNTER, never a boolean — `dragleave` fires every time the pointer crosses into a child, so a boolean would flicker off under the cursor, while `drop` forces the depth back to 0 (a drag leaving the window never sends the matching `dragleave`, and `currentTarget.contains(relatedTarget)`, the other classic fix, is useless there since `relatedTarget` is null in exactly that case). `enabled` is a getter, read at event time, so a component disabled mid-drag stops accepting with nothing re-bound.
- **`useProgressValue(value, max)`** → `{ clamped, fraction }` (VProgressLinear, VProgressCircular).
- **`useFileField({ model, forwardedAttrs, enabled, multiple, limits, onReject, onChange, excludeFromControl? })`** → `{ fileEl, nativeAttrs, controlAttrs, acceptFiles, onNativeChange, openPicker, resetNative }`. The hidden `<input type="file">` gate of VFilePicker and VFileUpload: the THREE-bucket attribute split (`NATIVE_ONLY = name/required/form/capture` on the input, the rest on whatever the user focuses), the single entry into the model on top of `utils/file.screenFiles`, `.click()`-not-`showPicker()`, and `resetNative()` on every path. `excludeFromControl` is VFilePicker's `aria-describedby`, which it re-aggregates itself.
- **`useMaskedField({ fieldEl, typing, displayText, readValue, writeValue, maxDigits, format, caret, parse, toMask, acceptable? })`** → `{ draft, fieldModel, writeField, commitLive, commitOrRevert, onFieldInput }`. The FIELD half of VDatePicker and VTimePicker, `useFieldPanel` being the panel half. It carries the traps: `fieldModel` must be bound with **`v-model`** and never `:model-value`; the anti-loop guard on the sync; the caret invariant (the number of digits to the LEFT is preserved, and the caret crosses the separator only on INSERTION). `parse`'s `final` flag exists for VDatePicker alone — the 2-digit year expands on the leave commit only.

**Merges not to attempt** (analysed, no genuinely common body): a shared IntersectionObserver for VTabs/VCombobox; merging `utils/date.ts` and `utils/time.ts`; a shared interface for `defineExpose({ …, el })`; `onClear()` of VInput/VTextarea.

## Internationalization (`src/i18n/`)

**No user-facing text literal in an SFC**: everything goes through the dictionary. DEVELOPER messages (`[Component] …`) stay hardcoded — they address the integrator, not the user.

Chain: `i18n/types.ts` (the `VectisMessages` contract) → `en.ts` (the base, always bundled) + `fr.ts` (opt-in) → `state.ts` (registry + public `setLocale`/`registerMessages`, internal `useMessages`/`useLocale`). A top-level folder, on a par with `tokens/`: neither `utils/` (the current dictionary is reactive state) nor `composables/` (this is configuration, not behaviour).

- **Module-level state** in a `shallowRef` (as in `VIcon/resolver.ts` and `VToast/state.ts`), not provide/inject nor a Vue plugin: it is configuration, settable from any `.ts`. The `shallowRef` is what makes ALREADY-MOUNTED components re-render when `setLocale` is called later. **Trap**: reading `useMessages().value.x` in a `setup()` body FREEZES the value — always inside a `computed` or the template.
- **ACCEPTED LIMIT: one locale per process.** Multi-locale SSR PER REQUEST is not covered (a single Node process serving /fr and /en must pass the text props explicitly); a client-only `setLocale` makes server and client diverge → hydration mismatch. The planned way out: `useMessages` has the shape of a composable, so only its BODY would become `inject(messagesKey, null) ?? currentMessages`, without touching the ~20 consumer SFCs (that would then need a `getCurrentInstance()` guard, the function staying callable outside a component).
- **Depth EXACTLY 2** (`namespace.key` → leaf). This is not decorative: it is what makes merging partial overrides NON-RECURSIVE, hence structurally incapable of descending into a function value (a recursive `DeepPartial<T>` would turn `(n: number) => string` into `{}`).
- **Parameterized messages are typed TS functions**, with no plural engine and no ICU: the English plural is a ternary inside the function. `en` and `fr` are ANNOTATED `: VectisMessages` → key and signature parity is guaranteed at COMPILE time; the parity test covers only the rest (arity, an `as` slipped in later).
- **`en` bundled, `fr` opt-in by import.** The argument is not weight (~0.8 kB gzip) but the uniqueness of the mechanism: enabling the shipped French and adding a language the DS does not ship are the SAME gesture (`registerMessages`), instead of two categories of dictionary. Tree-shaking follows from that.
- **Canonical cascade**: `aria-labelledby` > consumer `aria-label` > `label` prop > dictionary > `en`. `useAriaLabel` takes a getter, so it composes directly: `useAriaLabel(() => props.label ?? m.value.x.y)`. The ~30 text props are KEPT and take precedence — only their literal default lives in a `computed` rather than `withDefaults`.
- **Resolution by language subtag**: `'en-GB'`/`'en-US'` share their words; what distinguishes them comes from `Intl`. Three invariants: never an empty string, never a technical key displayed, never silence in dev when a language is missing.
- **Words and formats resolve SEPARATELY**: `setLocale('de-DE')` with no German dictionary already gives German months, first day of week and hour cycle (all from `Intl`) with English labels. A coherent degraded state, not a bug.
- **Dictionary boundary**: in goes anything that is a WORD or a language's typographic convention (the non-breaking space before `%` in French, the `hh:mm` made of initials); out stays whatever `Intl` derives from the tag, and whatever is made only of digits and universal punctuation — `99+` (VBadge), `+N` (VAvatarGroup), the `N/M` counter, `TIME_SEPARATOR`'s `:`, `date.ts`'s `PLACEHOLDER_FALLBACK`. Those components expose a slot for rephrasing. **The sharpest case is VHotkeys**: its GLYPHS (`⌘ ⌃ ⌥ ⇧ ↵ ⌫ ⌦ ⇥ ↑ ↓ ← →`) stay in `VHotkeys/platform.ts` — engraved on the hardware, identical in every language — while its WORDS (Ctrl, Shift → Maj, Enter → Entrée) are the `hotkeys.*` namespace. Same key, two forms: the glyph wins on screen, the word wins in the accessible name.
- **VCalendar/VDatePicker/VTimePicker** keep their `locale` prop, which takes PRECEDENCE; its default is `undefined` and falls back to the global locale (the `props.x ?? context` idiom of `VAvatar.vue`) — `undefined` must stay distinguishable, same reason as `mode`/`showDial`. VDatePicker is the SINGLE source: `resolvedLocale` is what flows down to VCalendar. `VDataTable` sorts through `localeCompare(…, vectisLocale.value, …)` and not `undefined`, whose runtime locale differs between Node and browser → divergent row order, hence a hydration mismatch.
- **Tests**: all in vitest/jsdom (no browser behaviour involved). `i18n.test.ts` carries the CANONICAL tests of the mechanism (post-mount reactivity, prop/attribute cascade, picker locale) — do not duplicate them across the 20 component files. The English assertions elsewhere are the SAFETY NET: since the default locale is `en`, they must stay green untouched; a red one signals a mis-copied string, never a test to fix.
- **Stories**: the locale itself is driven by story-level `globals` (`globals: { locale: 'fr-FR' }`), which the `preview.ts` decorator turns into a `setLocale`. Do NOT set it in a `beforeEach`: the decorator body runs afterwards and would win. A `beforeEach` with teardown remains mandatory for a `registerMessages` override, whose registry survives Storybook navigation (same rule as `dismissToast()` in the VToast stories).

## Tests: strict split

- **vitest + jsdom** (`*.test.ts`): logic only — emits, v-model, ARIA attributes, fallthrough. jsdom does not cover VPopover/top-layer: the Popover API is stubbed globally in `vitest.setup.ts` (a `data-popover-open` marker + inline display, because `:popover-open` is not evaluable in jsdom and the UA style `[popover]{display:none}` hides the panel from role queries; `hidePopover` also closes `[data-popover-open]` descendants — the stack cascade submenus need). Do not test browser behaviour in jsdom.
- **Storybook play functions** (`storybook/test`: `expect`, `userEvent`, `within`, `waitFor`): real browser behaviour (popover opening, Esc, `:user-invalid`…). Since v-model updates are asynchronous, always go through `waitFor` after an interaction. They run **locally in Chromium** through `@storybook/addon-vitest` (`pnpm test:stories`). They run with the default globals, so the locale is deterministically `en-US`: **play functions assert the English strings**.
- `vitest.config.ts` declares **two projects**: `unit` (jsdom, `src/**/*.test.ts`) and `storybook` (Playwright browser mode, fed by `storybookTest({ configDir: '.storybook' })`). Two traps: a Vitest project **does not inherit** the root's plugins — `vue()` must be repeated in the `storybook` project, otherwise the `.vue` files imported by the stories fail with "invalid JS syntax"; and the plugin applies the `preview.ts` annotations **itself**, so there is no setup file to write (a manual `setProjectAnnotations` would be flagged as redundant).
- `globals: true` in vitest.config.ts is **required** for @testing-library/vue's automatic cleanup — do not remove it (`unit` project).
- vitest's `expect` does NOT have the jest-dom matchers (`toBeVisible`, `toHaveFocus`…): in jsdom, assert on DOM properties (`el.hidden`, `document.activeElement`). Those matchers exist only in `storybook/test` (play functions).
- **Coverage** (`@vitest/coverage-v8`, `pnpm test:coverage`): the ONLY command that filters no `--project`, so the two layers merge into one figure — it therefore needs the Playwright binaries and stays **outside the checkpoint**, like `test:stories`. `coverage` is a ROOT option of `vitest.config.ts`, never a project one. `coverage.include` is what makes a file no test ever imports show up at 0% (without it only the loaded modules count, and the figure flatters); `exclude` carries the two GENERATED artefacts and the `src/index.ts` barrel. Two things to read with care: **a coverage run is also a full test run**, axe included, so it fails on an a11y regression (light theme only — the theme is `VECTIS_THEME`'s); and **v8 instruments the COMPILED SFC** and maps back through the source map, so template branches can read as uncovered while being exercised — the `<script setup>` figure is the reliable one. The `unit` project carries a `testTimeout` above the default for this run alone: alongside Chromium, the jsdom workers no longer compile a file within 5 s.

## Accessibility (axe, in the `storybook` project)

`addon-a11y` runs axe **after every play function**, and `preview.ts` sets `a11y.test = 'error'`: a violation fails `pnpm test:stories`. Left at the addon's default (`'todo'`) every violation would be a silent warning. The suite is green at **0 violations in both themes** — keep it there.

- **One run covers ONE theme.** axe reads computed colours, so contrast has to be checked twice: `pnpm test:stories` (light) and `VECTIS_THEME=dark pnpm test:stories`. The lever is Playwright's emulated colour scheme in `vitest.config.ts`, which works because `initialGlobals.theme` is `system` and the decorator resolves it through `prefers-color-scheme` — no story, no decorator is involved.
- **axe only sees what the play function leaves on screen.** A closed popover, a view behind a `v-if` are never audited. That is why `VMenu/SubmenusOnHover` deliberately ends with a submenu OPEN — the only place a nested panel is ever checked.
- **What axe canNOT judge**: it derives a background from the boxes that CONTAIN an element's rect, so text painted over a SIBLING it only partly covers is measured against whatever is underneath. The two cases in the DS (VProgressLinear's clipped copy, the dial's selected numeral) are listed in `preview.ts`'s `a11y.context.exclude`, with the reasoning. Do not add to that list without the same demonstration: an exclusion is for a tool limitation, never for a real violation.
- **Rules that are NOT running**, so do not expect them: the addon calls axe with `include: document.body`, and axe only enables its page-level rules when the include is `document.documentElement` — `page-has-heading-one`, `landmark-one-main` and `html-has-lang` are therefore inapplicable, and `region` is disabled by the addon itself.
- **Traps found the hard way**: `aria-expanded` is not allowed on `textbox` (hence `role="combobox"` on the VDatePicker/VTimePicker fields as soon as a panel exists); a `role="listbox"` owns nothing but `option`/`group`, but an EMPTY one is merely reviewed (hence the `aria-hidden` states of VCombobox, plus a live region outside the panel); `scrollable-region-focusable` demands a TABBABLE descendant (`tabindex="-1"` does not count) but exempts any listbox a `[role=combobox]` points at; `menu` **does** own `menu` in axe-core 4.12, so VMenu's nested panels are fine.

## Storybook

Storybook 10, `@storybook/vue3-vite` framework. Imports: types from `@storybook/vue3-vite`, test utilities from `storybook/test`, MDX blocks from `@storybook/addon-docs/blocks`. Addons: `addon-docs`, `addon-a11y` (blocking, see Accessibility) and `addon-vitest` (play function execution, see Tests). Chromatic stays CLI-driven (`pnpm chromatic`) — no addon in the UI. The project token is read from **`CHROMATIC_PROJECT_TOKEN`**, never from `chromatic.config.json`: that file is committed, so a token written there is in the git history for good.

- `.storybook/preview.ts`: global decorator for theme (System/Light/Dark toolbar — System follows `prefers-color-scheme` and listens for OS changes), direction (LTR/RTL) and **locale (English/Français)**. **vue3 trap**: theme, direction and locale are applied as side effects — `<html data-theme>`, `<html dir>`, `setLocale()` — and NOT through the state of a templated wrapper: the vue3 renderer does not re-mount the tree when a toolbar global changes (only args are reactive), so state captured in `setup()` stays frozen. The decorator BODY, however, does re-run on every change.
- **Bilingual stories.** Story-authored text goes through **`storyText({ en, fr })`** (`src/stories/storyText.ts`), which returns a `computed` on the DS's reactive locale. `setup` must return **the ref, never `.value`** — that is exactly what sidesteps the frozen-`setup()` trap, since the template unwraps the computed and the render effect tracks the locale. Demo _data_ (person names, `Alpha`/`Bravo`, ISO dates) stays as-is; only prose goes in the dictionary. `src/stories/**` is in `tsconfig.build.json`'s `exclude` so it never reaches `dist`. **A story meta NEVER pins `locale`** — the pickers then follow the global locale, so the toolbar drives their mask, months and hour cycle along with the words; the dedicated `Localization` stories are the ones that pass an explicit tag. Two consequences on the play functions: they read the `en-US` formats, and a row whose label comes from `Intl` is queried by `data-value` rather than by its accessible name (Node's and the browser's ICU builds do not pad the same way).
- **Accented demo data is deliberate where a test depends on it**: `Réunion` (VCombobox) and `Éclair` (VDataTable) are what the accent-insensitive filtering is asserted against, in both directions. Each carries a comment saying so — do not "translate" them away.
- The Material Symbols font is loaded by Storybook through `.storybook/preview-head.html` (never bundled in the lib) — it only serves the icon names used by the STORIES (`favorite`, `edit`…): the DS's own icons come from the built-in registry. Do not remove it, it is what keeps the ligature fallback alive; the `VIcon/WithoutFont` story neutralizes it locally to prove the autonomy.
- Every story covers: default, variants, states (disabled/loading/error), edge cases (long text). The sidebar has two top-level groups: `Components/…` and `Foundations/…` (`src/tokens/Tokens.mdx`, `src/i18n/I18n.stories.ts`). Tokens.mdx renders the TS source — never duplicate hardcoded values there.
- **NAMING EXEMPTION — Storybook is written WITHOUT the `V`.** `title: 'Components/Button'` and the `# Button` heading at the top of the `.mdx` keep the bare name: the sidebar is a table of contents, and a `V` repeated on every entry adds noise without removing any ambiguity (there is no native `<button>` in a navigation menu). By contrast **all the prose and all the code in the docs is written `VButton`** — the reader must always see the name they will type. This is the only exception to the prefix in the whole repo; the check is inverted, it is the PRESENCE of a `V` that is the bug: `git grep "title: 'Components/V"` and `git grep -E "^# V[A-Z]" -- "*.mdx"` must both return 0.

Prose only (the rendering comes from the stories) — no hardcoded token values.

## Packaging

Vite lib mode, **ESM only**, `preserveModules` (one module per source file → per-component tree-shaking) and `cssCodeSplit` (one sheet per component, shipped with its module — see "CSS cascade" for the mechanism and the invariant it imposes). Exports map: `.`, `./styles.css`, `./tokens` (typed module), `./tokens.json` — **unchanged by the split**: a relative import INSIDE the package is resolved on the filesystem, not through the exports map, so `./VX.css` needs no subpath and no `./*` wildcard (which would be new public API for nothing). `sideEffects: ["**/*.css"]` — hygiene before the split, load-bearing after it. The d.ts files come out of vite-plugin-dts on `tsconfig.build.json` (which excludes stories, tests and `src/stories/`). `postbuild` runs `scripts/check-css-split.ts`, the repo's only check on the ARTEFACT rather than the source.

## Known traps

- **TypeScript pinned to ^5.9** (root and packages/ui): do not let pnpm resolve TS 7 (the native compiler), vue-tsc/vite-plugin-dts do not support it.
- A new dependency with a postinstall: pnpm 11 blocks it → add it under `allowBuilds:` in `pnpm-workspace.yaml` (esbuild is already there).
- Prettier is separate from ESLint: `pnpm lint` does not check formatting, run `pnpm format` too.
- ESLint: `no-undef` is disabled for `.ts`/`.vue` (false positives on DOM globals, TS covers it); `vue/multi-word-component-names` and `vue/no-reserved-component-names` are disabled (simple names are intended: VButton, VInput, VMenu…).
- `corepack enable pnpm` if `pnpm` is not found in a fresh shell.
- **Some component names are also VALUES, not identifiers.** `'Tab'` is a keyboard key (`VCombobox.vue`, `VMenuPanel.vue`); `'Pagination'`, `'Tabs'`, `'Breadcrumb'` are i18n dictionary `aria-label`s; `'Menu'` is the visible text of a demo trigger; "Popover API" is the W3C spec. Never mass-substitute a component name without checking each site.

## Browser support

Popover API, `<dialog>`, `<details name>`, `:user-invalid`, `color-mix()`, `:has()`: Baseline, usable without a fallback. **CSS Anchor Positioning: used WITHOUT a fallback** — modern browsers only (Chrome/Edge 125+, Safari 26+; Firefox unsupported until anchor positioning is stable there). Do not add a JS fallback without an explicit request. `@starting-style`/`allow-discrete`: progressive enhancement only, never required.

**Anchoring patterns** (`src/styles/floating.css`: `.v-overlay` + `.v-floating` + `data-placement` → `position-area`/`position-try-fallbacks`):

- Panel invoked by `popovertarget` (VMenu — submenus included: the parent item is the invoker of the nested panel): the invoker is the **implicit anchor**, no `anchor-name` needed.
- Panel opened programmatically (VTooltip, and `VPopover` when given a `#trigger`): a **shared static `anchor-name`** on the wrapper + `anchor-scope` (same name) confining it to the wrapper's subtree + `position-anchor` on the panel. The confinement is indispensable: a shown popover moves to the top layer and is considered "after" the whole document for anchor resolution — without `anchor-scope`, every panel would attach to the last named wrapper on the page. No unique ID, no inline style. `anchor-scope`: Chrome/Edge 131+, Safari 26+. Vertical range through `writing-mode` (VSlider): Chrome/Edge 129+, Safari 18.1+.
- Aligned placements (`top-start`, `bottom-end`…): the inline margin on the aligned side is cancelled in floating.css (`[data-placement$='-start']`/`[$='-end']`), otherwise the gap `margin` offsets the panel from the trigger's edge. Side placements (submenus, `right-start`): the axis is swapped, so the inline margin is restored (the gap is inline, the alignment block).
- Panel whose consumer already owns the root and the control (VCombobox, VDatePicker, VTimePicker, and VTooltip which keeps its wrapper to attach pointer/focus to it): it sets `anchor-scope`/`anchor-name` itself and passes the name alone to `VPopover` through the **`anchor`** prop (a dashed-ident) → `position-anchor: var(--anchor-name)`. This is the required route as soon as the control is a text `<input>`, on which `popovertarget` is invalid.
- Triggers are provided by scoped slots: `#trigger="{ triggerProps }"` + `v-bind="triggerProps"` (popovertarget, aria-*). VTooltip follows the same pattern (scoped default slot): the consumer is the one setting `aria-describedby`, never an automatic JS bridge at mount.
- **`.v-overlay`** is the foundation of every popover in the DS: `position: fixed; inset: auto` (neutralizes the UA styles of `[popover]`) + the guard `.v-overlay:not(:popover-open) { display: none }`. A panel setting its own `display` (`.v-panel` as flex, the toast stack as a column) overrides the UA `display: none` of `[popover]` (author styles > UA) and a closed panel would stay clickable at `opacity: 0` on top of the content; the guard's specificity (0,2,0) puts it out of reach of a component `display`, whatever the bundle order. **The class goes on the six panels AND on the toast stacks** (`.v-toast-stack`, which cannot carry `.v-floating`: physical coordinates, no anchor, zero margin). The transition blocks stay separate (VToaster: opacity alone at `--vectis-duration-base`; `.v-floating`: opacity + `transform` at `--vectis-duration-fast`). VDialog stays out: a `<dialog>` is not a popover, `:popover-open` does not apply to it — hence its own `.v-dialog:not([open])`.

## Size scale (controls)

Unified **xs/sm/md/lg/xl** scale (24/32/40/48/56px, tokens `--vectis-control-height-xs…xl`). The size → height/font/icon/opsz/gap mapping lives in ONE CSS incarnation: `src/styles/control-size.css`, class **`.v-control`** set on the root carrying `data-size`/`data-compact`. The `[data-size]` blocks define ONLY `--control-*` custom properties (inherited down to the children, e.g. VInput's field — no specificity conflict) + the VIcon context `--vectis-icon-size`/`--vectis-icon-opsz`.

- **Compact** = -4px of height everywhere (`--control-height` derived from `--control-height-base`).
- Mappings (literal, font contract preserved — no new tokens): icons xs→16 / sm-md→20 / lg-xl→24; opsz xs-md→20, lg-xl→24; fonts xs→xs, sm-md→sm, lg-xl→md; gap `--control-gap` xs→4px, sm-md→8px, lg-xl→12px; paddings = `--vectis-space-*` directly.
- **The full scale is not exposed everywhere**: each component restricts its TS union to the subset that makes sense for it, `control-size.css` remaining the single table (its xs/xl blocks still serve the buttons). There is deliberately **no shared `ControlSize` type** — the scales differ, a single type would be wrong.
- Adopters and subsets: VButton/VIconButton/VPagination/VTabs/VToggle (**xs–xl**); VSideNavigation (sm/md, default md — `v-control` on the `<nav>`, every sublist inherits); **every component with a text input → sm/md/lg** (32/40/48px, default md): VInput, VTextarea, VInputOTP (type bumped one or two notches), VDatePicker, VTimePicker, VFilePicker, VCombobox (which propagates its size unchanged to its panel) — `xs` (24px) is too short for editable text and `xl` (56px) is outside the form template: do not expose them; **VFileUpload is deliberately OUTSIDE the scale** (a surface, the VAccordion case: no `size` prop, no `.v-control`, dimensions through dedicated tokens) — do not add one; VChip and VHotkeys (xs/sm, default xs — VHotkeys carries `v-control` on its root, its `<kbd>` caps consume `--control-height`); VMenu (sm/md/lg, default sm — `v-control` on the panel, see next bullet); VAvatarGroup.
- **Panels carry `v-control` on the PANEL, their rows consume it**: the panel, which already carries `data-size`/`data-compact`, carries `v-control`; `.v-menu-item`/`.v-combobox-option`/`.v-combobox-state` read the inherited `--control-*` (height, `--control-padding-inline`, gap, font-size) and the icons follow without a line of CSS. **Invariant**: a VMenu subpanel does NOT take the class (`:class="{ 'v-control': !submenu }"`) — `.v-control` re-sets `--control-height` from `--control-height-base` **without** the `[data-compact]` condition, which a subpanel does not carry: it would lose the inherited compact. Same reason why `panel.css` does not set the VIcon context. The only exception to the table: row typography is composite (size from the scale, unitless `body-md` leading, regular weight) — the `control` recipe means medium/leading 1, but a row may wrap and carry a sublabel. **GROUP LABELS consume `--control-height` too** (`.v-menu-group-label`, `.v-combobox-group-label`, `.v-side-nav-group-label` — the only three in the DS): `display: flex` + `align-items: center` + `min-height`, the same recipe as the rows, so a section header does not break the list's vertical rhythm (compact included, `--control-height` already derives from it). Their typography stays outside the scale (`overline` role), hence the vertical centring. This rule is not factored into `panel.css`: it would be at equal specificity with the panels' own rules, and VSideNavigation does not share the padding anyway (indented per level).

## Components

Inventory (exported from `src/index.ts` — that order is editorial, see "CSS cascade"): **VIcon, VTypography, VPopover, VSeparator, VButton, VIconButton, VButtonGroup, VPagination, VTabs** (+ VTab/VTabPanel)**, VToggle** (+ VToggleItem)**, VInput, VTextarea, VCheckbox, VRadio, VSwitch, VTooltip, VMenu** (+ VMenuItem/VMenuGroup/VMenuSeparator)**, VAccordion** (+ VAccordionItem)**, VToaster** (+ `toast()`/`dismissToast`)**, VBadge, VAvatar, VSpinner, VSkeletonLoader, VCombobox, VBreadcrumb, VSideNavigation** (+ VSideNavigationItem/VSideNavigationGroup/VSideNavigationSeparator)**, VChip, VHotkeys, VDataTable, VInputOTP, VProgressLinear, VProgressCircular, VSlider, VDialog** (+ VDialogAlert)**, VCalendar, VDatePicker, VTimePicker, VFilePicker, VFileUpload, VCarousel** (+ VCarouselItem)**. VTypography, VPopover and VSeparator come first because they are rendered INSIDE other components (VTypography by VInput, VTextarea, VDialog, VAccordion, VDataTable; VPopover by VTooltip, VCombobox, VDatePicker, VTimePicker, whose panel class lands on the SAME element; VSeparator by VMenuSeparator and VComboboxSeparator, whose class lands on the same element too) — that is a reading order, not a cascade one: the consumers of those elements qualify their own rules, so nothing breaks if the list is reordered.

The native Popover API is used by VPopover (hence VCombobox/VTooltip/VDatePicker/VTimePicker), VMenu and VToast.

**Internal, non-exported components** (no story and no `.mdx` — their doc lives with their consumer): `VMenu/VMenuPanel.vue`, `VCombobox/VComboboxOption.vue`, `VCombobox/VComboboxGroup.vue`, `VCombobox/VComboboxSeparator.vue`, `VToast/VToast.vue`, `VTimePicker/VTimePickerDial.vue`.

**VMenu and the VCombobox list are two distinct things**: **VMenu** is a public component carrying the whole ARIA menu pattern (roving focus, submenus, popover stack); the VCombobox list is a `role="listbox"` panel with **no autonomy at all**, rendered by VCombobox itself and driven from the field. Do not refactor them into a single panel parameterized by a `role` prop: they share only the chrome (`.v-panel`) and the plumbing (`VPopover`), which is already factored out.

**`VPopover` is the shared brick for panel PLUMBING** (the `[popover]` element and its mode, the DOM ↔ `v-model:open` state bridge, anchoring, placement, optional surface) — never the ARIA role, the keyboard, the focus or the dismissal policy, which stay with each component. Adopters: VCombobox, VTooltip, VDatePicker, VTimePicker. **VMenu and VToaster stay out, deliberately**: VMenu is the only `popover="auto"` (native light dismiss, implicit anchor through `popovertarget`, submenus opened with `showPopover({ source })` forming a native stack) — moving it in would impose a 3rd anchoring strategy and a 2nd mode for no gain; VToaster has no anchor at all (physical coordinates, six permanent stacks) and already does not carry `.v-floating`.

Cross-cutting rules covered above: tone/variant (VButton = the reference), wrapper-root pattern, size scale, disabled **greyed through tokens** (never `opacity` — except `loading`, which keeps `opacity: 0.5`).

### Per-component characteristics

- **VIcon**: **the DS requires NO icon font.** Resolution, in this order: `render` prop (explicit rendering) → `src` prop → `name` (consumer resolver → **built-in registry** → ligature) → SVG slot. The order IS the contract: the resolver comes before the registry (otherwise the DS's icons would stay Material for anyone who wired their own library), and a resolver returning `undefined` hands over to the registry — which is what makes PARTIAL mappings usable. `data-icon="<name>"` is set whatever the source: a test hook and a CSS extension point. Contextual control through `--vectis-icon-size`/`--vectis-icon-opsz`; an explicit `size` prop wins — **`--vectis-icon-opsz` only affects the ligature** (a font axis; the registry is drawn at opsz 24), while the size applies to every source.
  - **Built-in registry** — `VIcon/icons.ts`, GENERATED by `pnpm icons`: the 34 icons the library renders by default, as Material Symbols Rounded paths (wght 400 · GRAD 0 · opsz 24, Apache-2.0 © Google), in the form `[outline, filled?]` — the second path is emitted only when the FILL axis really changes the geometry (15 of 34; the script does the comparison, never a human). ~3.8 kB gzip, **not tree-shakable** (string lookup at runtime): the accepted price of autonomy. Add a name to the script's array when a component starts rendering a new icon by default. Rendered as `<svg><path>` and not `mask-image`: a masked background disappears under Windows forced-colors, where `fill: currentcolor` survives.
  - **`setIconResolver`** (`VIcon/resolver.ts`) — hook for a third-party library, module-level global state. To be set at module level (Nuxt plugin, `main.ts`), never inside a `setup()`, never client-only (hydration mismatch). Three generic factories, one per source family, with no knowledge of any third-party lib: `ligatureIconResolver` (Material, IcoMoon — **and the way to find the opsz 20/24 axis on the DS's 34 icons**), `classIconResolver` (Font Awesome, Phosphor, Bootstrap — renders a DS `<span class="v-icon-glyph">`, not an `<i>`: the DS owns the element, so it normalizes it in one rule; `strict` by default, a registry name with no alias falls back to the built-in SVG rather than producing an empty square), `componentIconResolver` (Lucide, Untitled UI — contract: a single `<svg>` root, sizing goes through `.v-icon > svg`). No per-library preset: the alias tables live in the docs, where they can be fixed without a release.
  - **`IconSource = string | IconRender`** (`VIcon/types.ts`) — the type of EVERY icon prop in the DS. **NO heuristic**: a string is always a NAME, an image or a component is declared as an object (`{ src }`, `{ component }`, `{ path }`, `{ text }`, `{ class }`). That is what makes `mdi:close` or `fa6-solid:xmark` valid names rather than URLs. `iconName(source)` is its counterpart — a readable name for a fallback label, `undefined` on an object (VInput/VTextarea, otherwise `[object Object]` in the accessibility tree).
- **VTypography**: a text element — `variant` (13 roles, see the semantic type tokens) + `tone` (default = inherit, muted/subtle/accent/danger/success/warning/on-inverse) + `as` (free tag; defaults h1…h4/p/span/code per variant) + `truncate`. No margins (spacing belongs to the parent layout), no JS beyond deriving the tag; single root → native fallthrough (`as="label"` + `for` = a real field label). The base block re-sets `--typography-family`/`--typography-tracking` on every instance (cutting inheritance from an ancestor VTypography's `--*`). Rendered internally by VDialog (title/subtitle), VInput/VTextarea (label/hint), VAccordionItem (subtitle), VDataTable (title) — their own classes (`.v-dialog-title`…) stay in place as hooks. The VInput/VTextarea counters stay local (tabular-nums + data-over ≠ a type role). The "all variants" story uses `as="p"` (the docs page owns the heading hierarchy).
- **VPopover**: a generic floating panel and a plumbing brick (see above). Two mutually exclusive anchoring modes: the **`#trigger`** slot (standalone) → a `.v-popover` wrapper in `inline-block` carrying `anchor-name`/`anchor-scope: --popover-anchor` (a shared static name, confined per instance) + `triggerProps` (`popovertarget`/`aria-expanded`/`aria-controls`, the **disclosure** pattern: neither a role nor `aria-haspopup` is imposed); the **`anchor`** prop (internal brick) → no layout wrapper, `display: contents` — an empty `inline-block` would create a line box, hence height, for every consumer. A single declaration covers both: `position-anchor: var(--anchor-name, --popover-anchor)`. `mode` auto (default, native light dismiss) / manual. `surface` (default true) sets `.v-panel`. `v-model:open` is **bidirectional** (fed by the DOM through `usePopover`) AND `defineExpose({ show, hide, el })`: the expose is what VTooltip and `useFieldPanel` use, since their opening must be **synchronous** (the model would insert a tick, and both `useTimer`'s 0 delay and the focus `rAF` would lose their meaning). `inheritAttrs: false` + `v-bind="$attrs"` on the **panel**, class/style included — a deliberate variant of the wrapper-root pattern (the visual subject is the panel, not the anchoring wrapper), hence no `useRootAttrs`. **The CSS carries NO dimension**: `min/max-inline-size`, `max-block-size` and `overflow` vary from one consumer to the next and would be arbitrated by bundle order at equal specificity.
- **VSeparator**: a 1px rule, an `<hr>` (implicit `separator` role, never focusable, outside every roving focus) in `--vectis-color-border` — the DS's single colour for a rule, `1px` being a tolerated raw value. `orientation` horizontal (default) / vertical, always mirrored in `data-orientation` (one block per branch, the VButtonGroup model), while **`aria-orientation` is emitted for `vertical` alone**: a `separator` is implicitly horizontal, so setting it on one would restate the role (the VTabs `tablist` convention). **No content slot** (a labelled divider is a heading with a rule: VFileUpload's "or" keeps its local `::before`/`::after`, which carry the dropzone's own colour and font-size) and **no spacing prop** — it ships `margin: 0`, the gap belongs to the parent layout, the VTypography rule. **Painted with a BORDER, not a background**, and that is the whole reason `VSideNavigationSeparator` was converted with it: Windows forced-colors forces a background to `Canvas`, where the rule VANISHES, and a border colour to `CanvasText`, where it survives — the VIcon registry argument; under `box-sizing: border-box` the two paints are pixel-identical everywhere else, so the box needs no `block-size`/`inline-size` of its own. **Vertical carries a contract**: an `<hr>` has no intrinsic block size, so `align-self: stretch` is what gives it its flex/grid line's cross size whatever the container's `align-items` — and in normal flow it collapses to zero **silently**, where the consumer sets a `block-size` (covered by the `Vertical` play function, red without the declaration). **Its `margin: 0` is overridden from two OTHER sheets** (VMenuSeparator and VComboboxSeparator, which bleed the rule out to the panel edges): both are written as the compound `.v-separator.v-menu-separator` / `.v-separator.v-combobox-separator` — the `.v-popover-panel.v-tooltip-panel` model — since at equal specificity the winner would be whichever sheet the consumer's bundler puts last. Every declaration added to `.v-separator` falls under that rule; one added to an ORIENTATION branch would need `.v-separator[data-orientation='horizontal'].v-x-separator`, the branches being (0,2,0) like the compound. **Deliberately NOT an adopter: VSideNavigationSeparator**, a decorative `<li>` imposed by the `<ul>`/`list` ARIA semantics — hence no `as` prop here. The border-based rules (VAccordionItem, the VCalendar footer, VDataTable's th/td, the VTabs track, VButtonGroup's seam, VDialog's sticky edges) are borders on existing layout elements, not separators.
- **VButton**: the reference tone/variant model. **Three tones only, `accent`/`neutral`/`danger`**: on a button `tone` is an action INTENTION, where `success`/`warning` are STATES — so those two live on the components that report one (VChip, VToast, VBadge, VTypography, the Progress pair) and `tones.css` keeps its blocks for them. The rule propagates to every component that forwards a tone INTO a VButton: `TabsTone`, `ToggleTone` and VPagination's inline union carry the same three. Four variants `solid`/`outline`/`ghost`/`soft` — `soft` is named after `--tone-bg-soft`, the token it paints, which also removes the one-character ambiguity with the `tone` prop. **`elevated` is a BOOLEAN, orthogonal to the variant** (`data-elevated`), never a variant value: it applies the shadow scale (shadow-sm / -md on hover / -sm on active) to all four, and adds `surface-raised` to `ghost` and `outline` alone — in dark, `surface-raised` (gray-900) sits a step above `surface` (gray-950), and without it the shadow has nothing casting it, so `ghost` + `elevated` is what reproduces the old `elevated` variant. Two mechanics not to simplify: the raised background is scoped by `:is([data-variant='ghost'], [data-variant='outline'])` because that `:is()` carries the (0,3,0) beating the ghost/outline base with no order dependency; and the ghost/outline hover/active carry `:not([data-elevated])` to be DISJOINT from the elevation rules rather than merely less specific. The disabled `box-shadow: none` needs **its own rule** — no variant declares a shadow, so the per-variant disabled rules cancel nothing, and a disabled raised ghost would go on casting one. `iconStart`/`iconEnd` (fallback slots #start/#end). Rendered as `<a>` through `href` (an inert link when disabled/loading: href removed + aria-disabled + click handlers filtered — the only JS, `inheritAttrs: false`). `compact` = -4px.
- **VIconButton**: square, width = `var(--control-height)` as set by VButton. **`shape` square (default) / circular** lives HERE and deliberately not on VButton: a full radius only says something on a box that is already square, and a `shape` upstream would open a table to maintain across everything that renders a VButton (VButtonGroup, VPagination, VTabs, VToggle). The value names the SILHOUETTE and not the radius — `--vectis-radius-interactive` is a consumer-overridable token, so a `rounded` would lie the day it is set to `0px`, where "square" only becomes truer. `data-shape` is the one attribute VIconButton passes DOWN THROUGH `$attrs` (VButton knows nothing of it) and the rule is qualified `.v-icon-button[data-shape='circular']` (0,2,0) so it beats VButton's own `border-radius` whatever order the two sheets land in — the neighbouring `[data-size]` argument. Only the non-default value writes CSS. Inside a VButtonGroup the group's corner rules (0,4,0) still win, so a circular segment keeps square seams: intended, and documented in the `.mdx`. **VCarousel's previous/next pair is the reason it exists** and passes `shape="circular"` in hard — a rounded rectangle laid over arbitrary media competes with it; `--carousel-outset` is unaffected, that trap is about `size`.
- **VButtonGroup**: a `role="group"` wrapper that joins VButton/VIconButton into a segmented control (merged borders `margin: -1px`, rounded corners only at the ends through logical `border-*-*-radius` properties, a `--vectis-color-border` seam between solid segments, `z-index` on hover/focus/active). CSS-only (no provide/inject): each button keeps its props; set the same variant/tone/size on the children for consistency. `orientation` horizontal (default) / vertical. Exported after VIconButton (overrides `.v-button-group > .v-button`).
- **VPagination**: **composed** — every pill is a `VButton` (the active page is always `solid` + `aria-current="page"`; inactive ones `ghost`/`outline` in `tone="neutral"`), the controls are a `VButton`/`VIconButton` (`controlsDisplay` icon/text/both, `prevIcon`/`nextIcon` through `iconProps`), and `attached` joins everything in a **VButtonGroup**. **No `<ul>`/`<li>`**: VButtonGroup only styles its direct children — which is also why the ellipsis is a disabled `VIconButton` `more_horiz` (still a `.v-button`, so the seam stays continuous) rather than a `<span>`. No state rule is redefined (everything comes from VButton); `size`/`compact` are propagated to every child; `.v-pagination-page[data-size]` overrides `min-inline-size: var(--control-height)` (the VIconButton model) **and cancels VButton's colour transition** → **export after VButtonGroup in `index.ts`**. That `transition: none` is not a taste decision and must not be "restored for consistency": the truncation window SHIFTS, so from one page to the next the highlight keeps its slot but changes ELEMENT, and VButton's 120 ms `background-color` fade then runs on the outgoing and the incoming pill at once — two half-tinted pills for a few frames, read as a flicker. No duration fixes it (symmetric = overlap, asymmetric = a gap or a trailing highlight), and CSS cannot keep the fade for hover alone: a transition is resolved from the state being ENTERED, and "no longer current" is the same state as "no longer hovered". Guarded by the `Default` play function (`getComputedStyle(…).transitionProperty`), the padding override's own model — mind that VButton also zeroes it under `prefers-reduced-motion`, so verify that assertion red. **Double truncation**: (1) logical — `length` (default 1) sets the page count, all rendered by default; `totalVisible` is the total number of **slots** rendered, ellipses included (clamped to a minimum of 5), first/last always kept, the window centred on the current page **shifting** at the ends instead of shrinking (constant bar width), pure derivation; (2) responsive — **100% CSS**, the nav is its own query container (`container-type: inline-size` + `container-name`), 3 `@container` steps (36/31/25rem) hide neighbours with `display: none` by decreasing `data-distance` (capped at 3), the edges (`data-edge`) and the current page carrying none and so never hidden; the middle step also folds a `both` control down to icon-only (it costs ~4× a pill). Each threshold is the width **needed to display** the level, not what is left after hiding — otherwise the row overflows for the whole interval. The containment is **reserved for responsive mode** (`.v-pagination[data-responsive]`): every `@container` depends on it, and outside responsive mode (the default) the nav regains an intrinsic width — so no `flex: 1` is needed from the parent (see the VDataTable footer). Accepted consequence when it applies: the nav is **block-level** (an `inline-flex` would collapse to zero), hence the `align` prop. Thresholds as rem literals (no `var()` in `@container`), calibrated on `md`; escape hatches `totalVisible` / `responsive: false`. No ellipsis is added to compensate for a hidden neighbour (same width as a pill, zero gain). `disabledPages`: a list **or** a predicate (the `disabledDates` convention); the controls **step over** disabled pages and disable themselves when none is left (covering the ends without a separate test). The only behavioural JS: arrow/Home/End keys on the nav, delegated to `utils/arrowNav` — whose `display` filter excludes the pills hidden by the container queries.
- **VTabs** (+ **VTab**, **VTabPanel**): **composed** — every tab is a `ghost` `VButton` (raised through `elevated` when active in the `inset` variant; the context `tone` when active, `neutral` when inactive), the scroll controls are `VIconButton`s. No state rule is redefined. **Composed** API with two slots: `#default` (the `VTab`s, inside the `role="tablist"`) and `#panels` (the `VTabPanel`s) — a single slot could not split them across two DOM containers; `#panels` absent = a plain bar / segmented control. A `VTabs/context.ts` context (getters, the VAccordion model) carries `value`/`select`/`tabId`/`panelId`/`hasPanels`/`variant`/`tone`/`size`/`compact`/`activation` — `size`/`compact` travel through it (and not through CSS inheritance: each VButton sets its own `v-control[data-size]`). Ids derive from a single `useId()` and are **sanitized** (`aria-controls` is a space-separated IDREF list); `hasPanels` is a getter on `slots.panels !== undefined`, **deterministic SSR/client** so there is no reactive registry and no hydration mismatch (the trade-off: `#panels` must be statically present or absent). The root uses the **wrapper-root pattern** (`inheritAttrs: false`, class/style on the root, everything else on the tablist). Variants pack **two decisions into one `data-variant`** — the track (`flat` / `inset`) and the frame (`outlined` = `flat` + a frame). `flat` (default; track `border-block-end` carried by `.v-tabs-bar` — not by the scroller, otherwise it would stop before the scroll buttons and the indicator could not cover it — plus `margin-block-end: -1px` on the list, the VButtonGroup idiom; `::after` indicator in `currentColor`, which follows both the tone AND the disabled grey, dedicated token `--vectis-control-size-tab-indicator`). On a track (`flat` as well as `outlined`) the tabs are **contiguous square-cornered segments** — `gap: 0` on the list, `border-radius: 0` on the tab: it is the indicator and the track that carve the bar, not the buttons' silhouette (the BAR's `gap` stays, it separates the scroll buttons); `outlined` alone takes `--vectis-radius-interactive` back at the **ends** of the row, on the side the track does not occupy (the VButtonGroup idiom, square internal seams; `:first-of-type`/`:last-of-type` — the edge sentinels are the list's real first and last children). `outlined`: `flat` line for line **plus** the frame from the **decoration scale shared with VAccordion and VDataTable** (`surface-raised` + a 1px border + `--vectis-radius-surface`) set on the ROOT, so around the bar AND the panels — the track becomes the separator between the two, inside the frame. Gutter `--tabs-frame-pad` (the `--table-frame-pad` idiom: `0px` when flat — a strict no-op — `--vectis-space-3` when framed), consumed by the bar (`padding-inline` + `padding-block-start`; **never the edge the track occupies**, or it would stop separating) and by `.v-tabs-panels` (full padding); **fixed, not indexed on `data-size`/`compact`** — it is a card measurement, and the `--control-*` variables live on the descendant VButtons, out of the root's reach. **No `overflow: clip`** unlike VDataTable, whose table is edge-to-edge by construction: here the gutter always leaves a band ≥ the inner radius (no box reaches a corner, so no nested `calc()` radius is needed), the list already crops its own overflow, and clipping would crop the `VTabPanel`'s **outer** focus ring, the only one leaving the component. Track and indicator are written for BOTH values with `:is([data-variant='flat'], [data-variant='outlined'])` — explicit rather than `:not([data-variant='inset'])`: a 4th frame will have to opt in by hand instead of inheriting silently, and both literals stay greppable; specificity is unchanged, `:is()` taking that of its arguments. `inset`: a hollow `surface-sunken` track on the scroller itself, so that its padding protects the shadow of the `elevated` tab; nested radius through `calc()`; never framed (it is already its own surface). `orientation` vertical: the root becomes a `row` (panels alongside), the indicator sits at the start edge in both frames — but the track **migrates** from `border-inline-start` (flat: it delimits the tab column) to `border-inline-end` (framed: that edge is already held by the frame's border; what is missing is the bar/panels boundary), and the `margin-inline-start: -1px` overlap trick is then **neutralized** — there is nothing left to overlap, and it would slide the list under the border. These overrides are at EQUAL specificity with the `:is()` rules: order decides. Without a `#panels` slot, `outlined` removes the track (it would double the frame's border, flush against it) and closes the gutter on that edge — guard `:not(:has(> .v-tabs-panels))`. None of these rules is observable in jsdom (styles not injected, no layout): the unit tests only lock `data-variant` and the mapping to the VButton's `data-elevated`, the rest is covered by the `Variants` and `Vertical` stories (Chromatic). `align` is set on the **bar** and not on the list (a `justify-content` on an overflowing container would make the part past the start edge unreachable) — so it is a no-op in vertical without a height. `grow` = `flex: 1 1 0` on the tabs (the label wrapped in `.v-tab-label`, since `text-overflow` does not apply to the anonymous text of a flex item); incompatible by construction with scrolling. Scrolling: list `overflow: auto` + `scrollbar-width: none` + `scroll-behavior: smooth` (so `scrollBy` **without** `behavior`, which would not respect reduced-motion). `scrollButtons` is opt-in; **the ends are measured by two `IntersectionObserver` sentinels** (a single observer for scroll + resize + tab additions, where a ResizeObserver would be a second mechanism and the repo's first; defaults `true` = buttons disabled in SSR/jsdom; `::scroll-button()` is a future target, below the Safari floor). Every VButton override is qualified **`.v-tab[data-size]`** (the VIconButton model) → the order in `index.ts` is not constraining. **Inner** focus ring (negative `outline-offset`): the scroller would crop a positive one. Panels: native `hidden` (content state preserved; fields still submitted) + a `lazy` prop; guard `.v-tabs-panel[hidden] { display: none }` **without `!important`** (the UA style is overridden by any author `display` declaration). Behavioural JS: roving tabindex + arrows/Home/End through `utils/arrowNav`, which **moves focus without activating** (`activation: 'manual'` by default; `'automatic'` = select on focus, set in `VTab.@focus` so the value does not travel through the DOM); the active tab is scrolled back into view with `scrollBy` **bounded to the list** (`scrollIntoView` would walk up every scrollable ancestor). A `disabled` tab is a `<button disabled>` (skipped by the arrows, like VPagination's pages). Contract: the `v-model` must reference an existing, activatable tab, otherwise no tab has `tabindex="0"`.

Two consequences that are not cosmetic: a `<button>` admits only phrasing content, so title and subtitle are `VTypography as="span"` in **both** modes (one CSS table, one shape); and the preview list is rendered OUTSIDE the zone in every mode, `bottom` included, or its remove buttons would be buttons inside a button (axe `nested-interactive`, blocking). `preview` is a single three-state prop `false | 'bottom' | 'end'`; `end` folds back under the zone through a **container query**, where the root is the container and `.v-file-upload-body` is what flips — an element cannot query ITSELF, so deleting that wrapper makes the query silently inert, and the containment is reserved for `end` (elsewhere the root would lose its intrinsic width). **Thumbnails** are a `reactive(Map<File, string>)` of object URLs keyed BY FILE IDENTITY — safe because `reactive()` converts only Object/Array/Map/Set, so a `File` traverses the model unproxied, the exact opposite of VCombobox's option cache; a name key would collide across folders. `syncThumbnails()` reconciles map and model in one pass and is called ONLY from `onMounted`, a `watch` and handlers (rule 4): the server renders the type icon, and so does the first client render, so there is no hydration mismatch. Four exits, one per way of losing a reference: removal and wholesale replacement (the watch), a decoding failure (`@error` on the `<img>`), unmount (`onBeforeUnmount`). The kind → icon table lives in the SFC (prop `typeIcons`); the classification is pure in `VFileUpload/fileKind.ts`, MIME first then extension, `dot > 0` because `.gitignore` has no extension. **Trap**: the map is named `thumbUrls` and NOT `thumbnails` — a top-level `<script setup>` binding SHADOWS the prop of the same name in the template (the VHotkeys `listening` precedent; ESLint's `vue/no-dupe-keys` caught it). A consumer `aria-label` is inert on the `<div>` zone AND reported by axe as `aria-prohibited-attr` → dev warn, name the zone through `title`.
- **VCarousel** (+ VCarouselItem): scrolls through content — images or text. **ONE mechanism, a native `scroll-snap` scroller**: touch, trackpad, scrollbar, keyboard and snapping all come from the browser, so there is no `transform` track, no cloned slide and — deliberately — **a keyboard handler on the VIEWPORT, and only there** (which carries `tabindex="0"`, needed anyway for axe's `scrollable-region-focusable`). A focused scroll container does move on the arrows by itself — but Chromium scrolls a fixed pixel step that mandatory snapping immediately undoes, so the net movement is zero and the handler moves the MODEL instead, keeping one write path. `arrowNav` is the wrong tool here: there is no roving focus and slides are not controls. Responsiveness is **100% CSS with no breakpoint, no `@container` and no observer**: `itemsPerView` is a MAXIMUM, `itemMinSize` a floor, and `max()` inside the slide's `flex-basis` IS the container query — `flex-basis` and not `inline-size` because it is the one dimension resolving on the flex MAIN axis, hence on the scroll axis, in both orientations and both directions. `peek` (the strip left for the next slide) **includes its leading gap**, which is what keeps the formula branch-free: `peek: 0` collapses it exactly to `(100% - (N-1)·gap) / N`. `min-inline-size: 0` on the slide is load-bearing — the `auto` content floor can push a flex item past its basis and desynchronize the whole snap grid.
  **The slide count comes from the slot's VNODES** (`utils/vnode.flattenSlot`, shared with VAvatarGroup) and never from a registry the items feed at mount, which would render 0 slides on the server and N on the client; `cloneVNode` then carries each slide its `index`, since `setup()` order is deterministic on the first render but not on a later insertion. `VCarouselItem` renders **two boxes and no `<style>`**: `.v-carousel-slide` is the snap area and the view-timeline subject, `.v-carousel-effect` the animated inner box. That split is correctness, not tidiness — a scroll-snap area is the element's **TRANSFORMED** border box, so animating the slide would make its snap position depend on the scroll position, and the symptom is jitter with no error anywhere. Its rules live in VCarousel's sheet (all qualified by the root's `data-orientation`/`data-effect`): split across two sheets they would be arbitrated by the consumer's bundler.
  **Effects (`slide`/`fade`/`scale`/`cover`) are CSS SCROLL-DRIVEN animations** (`view-timeline` named on the slide, resolved by tree walk so each inner finds its own; `animation-range: cover`), progressive enhancement behind `@supports (view-timeline-name: --v) and (animation-range: cover)` — without it nothing is declared and the carousel is a plain `slide` (Firefox lands there, the anchor-positioning precedent). Three traps: **longhands, never the `animation` shorthand** (`animation-timeline` and `animation-duration` are reset-only sub-properties, so a shorthand written after would silently restore `auto`/`0s` and every effect would vanish); `animation-duration: auto` is the whole timeline, a duration in seconds would be read as a PROPORTION of it; and `linear` is load-bearing, the default `ease` re-maps the progress and `fade`'s counter-translate would no longer cancel the scroll travel. `cover` is the only usable range — `contain` has length `|V - S|`, hence exactly ZERO at one item per view. **`fade` counter-translates ±100% of the slide's own size** to dissolve in place, which is only exact when a slide equals the viewport: past one item per view, or with a `peek`, every slide would pile onto the same spot, so it **downgrades to `slide`** (a computed, plus a dev warn) rather than degrade. Keyframes are written on a vector (`--carousel-axis-x/y`) and a sign (`--carousel-dir`, flipped by `[dir='rtl']` for `horizontal` only), never duplicated per orientation and per direction — `calc(0 * -100%)` is a valid zero. `v-carousel-cover` uses `transform` and not the individual properties because `perspective()` must sit in the function list: a `perspective` PROPERTY on the viewport would be inert, an `overflow: auto` box being forced to `transform-style: flat`. `translateZ`/depth stay deliberately physical (the VTimePickerDial precedent).
  **PAGES, NOT SLIDES.** `v-model` is a slide index, but `scroll-snap-align: start` makes a position past the end of the track UNREACHABLE — the scroller clamps short of it — so 6 slides three at a time offer **4** leading positions, not 6. `pageCount` drives the indicator list and every clamp (`goTo`, `End`, `atEnd`); one dot per SLIDE would hand out dots that scroll nowhere and let the model hold a value the DOM can never satisfy (the bug that shipped in the first cut, together with the tie-break below). It is **measured** off the scroller by `measure()`, which reads RECTS and the scroller's own sizes only: `starts = floor((scrollable + SLACK) / step)` start-aligned positions, **plus the END of the track** when `residual = scrollable - starts·step` exceeds `SLACK` (2px — `scrollWidth`/`clientWidth` are integers where the flex layout is fractional, so the same slack that saves an exactly reachable last position stops a sub-pixel leftover minting a phantom one). `step` is the delta between the first two slides, hence physical: RTL and vertical free. **The end page is the other half of the fix and it has a CSS half**: `.v-carousel-slide:last-child { scroll-snap-align: end }`, without which a `peek` leaves the scroller resting a strip short of the end and the last slide is NEVER fully revealed (the reported bug). That rule is a no-op when a slide is exactly the port's size (both offsets are the same number) and inert when a slide is larger (an oversized snap area makes every covering position valid); it is insurance rather than the mechanism, Chromium clamping an out-of-range snap position into the range on its own — the JS is what actually offers the page. **Page index == slide index**, in every branch: `pages - 1 = ceil(scrollable / step)` is exactly the first fully visible slide at the end of the track, which is why nothing downstream translates. The prop-derived `count - itemsPerView + 1` survives as the **SSR/jsdom fallback**, and it is now exact for a peek TOO (the strip costs a start position and the end of the track gives it back); only an ACTIVE `itemMinSize` makes it over-count until the first measurement. Being a pure function of the props is what keeps the dot list identical on both sides of hydration. Indicator labels stay slide-based (`1 of 6` … `4 of 6`): the control parks that slide at the start edge — or leads with it, at the end of the track — so the name agrees with the slide's own and with the live region; a page ordinal would announce three different totals in one widget.
  **TRAP — `1` must stay in the observer's `threshold`.** An IntersectionObserver is not a ResizeObserver: it queues an entry only when a threshold bucket is crossed, never because the root resized. **Nothing READS a ratio any more** — the reading is positional (below) — but the buckets still decide WHEN the callback runs, and what makes ONE observer cover the resize here is that `pageCount` changes exactly when the number of FULLY visible slides changes, which crosses the 1.0 bucket, which re-triggers the measurement. Drop the 1 (it serves neither `atStart`/`atEnd` nor any reading) and the page count freezes silently. Second premise: a slide's box never exceeds the port on the cross axis, so the area ratio equals the scroll-axis ratio and a slide becoming fully visible really does cross 1.0. Covered by the `ResponsivePages` play function, which is what settled the question empirically; no ResizeObserver is needed.
  **JS budget, in full**: `scrollToIndex` (v-model → DOM, deltas from the RECTS so LTR/RTL/vertical fall out with no direction test, `scrollBy?.()` optional-called for jsdom, `behavior` omitted so `scroll-behavior` — hence reduced-motion — governs); **ONE IntersectionObserver**, which TRIGGERS both the page measurement and the current-index read-back, plus a second call from `scrollend`; and autoplay through `useTimer`. VTabs' two edge sentinels are unnecessary here (we know our slides), and `atStart`/`atEnd` are **pure derivations** (`model <= 0`, `model >= pageCount - 1`) — safe only because `pageCount` never over-counts, which is the whole reason the measured form is mandatory; what the ratio-based ends used to insure against is autoplay-shaped (a false `atEnd` re-arms the timer on every bounce, forever), and the `Pages` play function is its regression test. **The read-back is POSITIONAL, and going back to an `intersectionRatio` would bring back the bug it fixes**: the page is `round(offset / step)` — `offset` being `|first slide's start - the port's start|`, a rect delta like `step`, hence unsigned where `scrollLeft` is negative in RTL — special-cased to the last page when `offset` is within `SLACK` of `scrollable`, since the end of the track is the one position that is not a multiple of `step`. A ratio has to be DELIVERED to be read, and an observer delivers on a threshold crossing alone: with a `peek` the outgoing slide keeps the strip's worth of slack and stays fully visible for the WHOLE of a backward scroll, destination included, so every mid-flight reading named the page being LEFT while the incoming slide, parked at 0.997 by a fractional layout, crossed nothing on arrival. `scrollend` then wrote that stale reading to the model and `readBack` suppressed the correcting scroll: **the dot stuck one page ahead of the content, for good** (reported; the jsdom regression test fails with `expected 4 to be 3`). Hence `onScrollEnd` measures before lowering the guard — it is the CALL that removes the race, NOT its position: the sync watcher is a `pre` one, both writes land in the same flush and it runs once on the final values. The reading is `clamp`ed to `pageCount - 1` (not to the locally computed count, which does not cap at `count`): a slide larger than the port mints a page no slide carries, and `scrollToIndex` would then do nothing while `settling` never came back down. `settling` guards the write loop and is a **ref, not a `let`**: lowering it must be able to re-run the sync, since `scrollend` and the observer callback race and a smooth scroll the user interrupts is the losing order. **The two directions must never CHAIN**, hence the `readBack` flag raised around the read-back's own model write and read by `watch(model)`: a drag writes the model on every frame, and each of those writes came back as a programmatic `scrollBy` **fighting the finger** — the scroller jumped to the slide just named, the release snapped it again, and one gesture played two animations (reported on touch, where a gesture ends between two snap positions far more often than a wheel does). `scrollToIndex`'s "already there" test does not cover it: it holds at rest, and mid-gesture the delta is real. The flag is lowered in a `nextTick` and NOT inside `watch(model)` — a controlled v-model that refuses the value fires no watcher, and the flag would swallow the consumer's next change.
  **Autoplay** (no loop: it stops on the last PAGE) gathers every reason to stop in ONE `rotating` computed so a single `watch` — `immediate`, or the first delay would only ever be armed by a later change — re-arms the timer. `autoplay > 0` is a GUARD, not a default: `useTimer` runs a delay ≤ 0 SYNCHRONOUSLY and a synchronous callback bumping the model would recurse until the stack blows — and it is ALSO the consumer's stop control, the prop being reactive, so binding it to `0` cancels the timer on the spot. It carries the **DS's second `window` preference read** (`matchMedia`, after VHotkeys' `navigator`), and that is not redundant with the CSS media query: a media query stops a transition, never a TIMER, and WCAG 2.2.2 is about the content moving at all. **No pause button is rendered** (removed on request, along with the `play_arrow`/`pause` registry icons and the `carousel.play`/`.pause` dictionary keys it was the only consumer of): hover, keyboard focus and reduced-motion remain, so a TOUCH user has no way to stop the rotation — the `.mdx` states the binding to add and the five-second exemption it relies on. Do not re-add the button without asking; do not silently drop the warning either.
  **A11y**: root `role="region"` + translated `aria-roledescription` (dictionary text — an untranslated `aria-roledescription` is the one a11y string that stays English with no visible symptom) + `useAriaLabel`; slides `role="group"` + `aria-roledescription` + "N of M"; the viewport is a NAMED `role="group"` because a focusable box carrying an `aria-label` without a role is axe's `aria-prohibited-attr` (the VFileUpload trap). Every story passes a DISTINCT `label`: a region is a landmark and `landmark-unique` is one of the best-practice rules the addon does run. The live region is a dedicated `role="status"`, **not** an `aria-live` on the viewport (which fires on DOM mutation, and the slides never mutate), and it is **emptied while rotating** (APG). The `inside` indicator bar has **NO surface of its own** — a pill behind the dots covers a slice of the slide permanently, which is a lot of media to spend on a few 8px marks. The legibility lives in the DOTS: a `text-on-accent` fill (white in BOTH themes — their backdrop is arbitrary media, not the page, so they are deliberately theme-independent) plus a 1px `box-shadow` ring in `surface-inverse` (dark in both themes), the classic pair that reads on light and dark media alike, drawn as a shadow so it costs no layout. Translucency is safe THERE and was not on the bar: a dot holds no text, so `color-contrast` never runs on it — the rule that made the bar opaque was about text drawn over the bar, and there is none; what the ring answers is WCAG 1.4.11, on any backdrop rather than on a judged one. `controls`/`indicators` are the three-state `false | 'inside' | 'outside'` prop of VFileUpload's `preview`.
  **LAYOUT — the stage/root split is the whole placement contract.** `.v-carousel-stage` holds the viewport, the controls and the autoplay control and NOTHING else; the indicator bar is a SIBLING, a direct child of the root. That is not tidiness: the controls are positioned against the stage, so putting the bar inside it would add its height to the box they are centred on and drop an `inside` pair visibly below the middle of the slides (the bug that shipped). Both placements are `position: absolute` against the stage — `inside` insets by `--vectis-space-2`, `outside` by `calc(-1 * var(--carousel-outset))`, i.e. into padding the ROOT reserved, so the component's footprint never changes and the slides narrow instead (the `flex-basis` is a percentage of the viewport, so it follows with no branch and no second measurement). The root is a flex `column` when horizontal and a **`row` when vertical**, which is what puts an `outside` bar below in one case and at the inline end in the other with no dedicated rule; in vertical the stage needs **`flex-grow: 1`** (and `flex-grow`, never `flex: 1`, whose `0` basis collapses it against the existing `min-*-size: 0`) or the inline axis becomes the main axis and the stage shrink-wraps its widest slide. Not in horizontal, where growing into a consumer-set height would re-centre the controls on empty space. **INVARIANT — `--carousel-outset` is applied on the SCROLL axis and always SYMMETRICALLY**: that is what lets every `inside` inset be written against the stage's edges with no compensation (an absolute box resolves against the PADDING box, the edges those insets pin to are on the cross axis, and the axis they centre on stays symmetric). One-sided, it decentres the `inside` bar silently. The outset is `calc(var(--vectis-control-height-md) + var(--vectis-space-2))` — a **coupling to the size VIconButton renders at**, since the two controls pass no `size`; and it is gated by `:has(> .v-carousel-stage > .v-carousel-controls)` so a consumer `#controls` does not inherit two buttons' worth of dead padding. RTL is free for the LAYOUT — logical properties, symmetric negative insets, and `space-between` putting `previous` at the inline start — but **not for the glyphs**: an arrow points at a physical direction, so `[dir='rtl'] … .v-carousel-control .v-icon { scale: -1 1 }`, horizontal only, word for word the VTabs and VPagination rule — what the three share is the RULE, not the glyph. **The default icons are `arrow_left_alt`/`arrow_right_alt` (horizontal) and `arrow_upward_alt`/`arrow_downward_alt` (vertical), where VTabs and VPagination keep chevrons**, and the divergence is deliberate: those two put their control in a dense bar, this pair is a round button laid over arbitrary media, where a hairline chevron dissolves at the centre of the disc and a shaft fills it. The `Rtl` play function is the DS's only mechanical guard on that rule, which the other two carry untested.
  **`controlsVisibility`** (`'always' | 'hover'`, default `'always'`) is a MODE union and not a boolean — the `controlsDisplay` shape of VPagination — because the trigger is hover OR keyboard focus OR unconditional on a coarse pointer, which `onHover` would misname; mirrored unconditionally as `data-controls-visibility` (the DS rule: unions always, booleans only when true). It hides with **`opacity` alone**, never `display`/`visibility`, which would drop the buttons from the tab order and the a11y tree — the hidden-input rule. Behind **`@media (hover: hover)`** (never `any-hover`, true as soon as any hovering pointer is attached) so touch keeps them permanent. axe short-circuits `color-contrast` to a pass at an opacity of exactly `0` but JUDGES anything in between, hence the hard rule that the hover story's play function must end REVEALED. `userEvent.hover()` cannot drive that test — it dispatches synthetic pointer events where `:hover` comes from the browser's real input pipeline — so it is asserted through the focus branch.
  **KEYBOARD focus, both here and for the autoplay pause — `:has(:focus-visible)` on the root, never `:focus-within`, and `matches(':focus-visible')` on the focusin target, never a bare flag.** A pointer click LEAVES the focus on the control it hit, so reading any focus pinned the reveal up and the rotation paused until the user clicked somewhere outside the carousel entirely, long after the pointer had left — reported as a bug, and the shape of it is worth remembering: `focusin` tells you focus arrived, never how. The JS wraps the call in a `try` returning `true`, since jsdom's selector engine may not know the pseudo-class and pausing is the conservative answer; the two jsdom tests stub `matches` on both sides rather than trusting it, because what they lock is that the component ASKS and branches, not what jsdom answers. The browser side asserts the reveal RELEASES on blur (`userEvent.click` cannot be trusted for the pointer branch: Chromium's focus-visible heuristic follows real input modality, not synthetic events).

## The documentation site (`apps/docs`)

A **Nuxt 3** application, `nuxt generate`d to static files and published to GitHub Pages at `/vectis-ui/` by the `pages` job in `ci.yml`. It is the library's end-to-end SSR test: a component reaching for `window` outside a handler fails the prerender rather than the visitor. **One-time repository setting: Pages → Source → GitHub Actions.**

- **Storybook is NOT published.** It is an internal tool — run locally, exercised by CI (`build-storybook`, `test:stories`) and reviewed through Chromatic — and it is deliberately kept off the public site. The docs site therefore links to it nowhere, and `nuxt.config.ts` needs no prerender `ignore` for it. Do not add a Storybook link to a doc page: the crawler would follow it, get a 404 and fail the whole `generate`.

- **It is a CONSUMER, and every deviation goes through the sanctioned override path.** Nothing in it touches `packages/ui`. Its layout, its accent (violet, repointed from the palette) and its two webfonts are all UNLAYERED rules — the mechanism the Theming page documents, practised rather than described. `assets/css/docs-layout.css` holds only what a media query owns; a state (`:hover`, `:focus-visible`) lives in the component's own `<style scoped>`.
- **The library ships NO webfont.** `--vectis-font-family-display` resolves to the platform stack. 'Josefin Sans' and 'Geist' are the SITE's brand layer (`assets/css/fonts.css`), which is why the Font family page documents the family tokens and how this site wires them, and never claims the library ships a typeface.
- **`content/nav.ts` is the single source** for the rail, the search index and `nitro.prerender.routes` — the three cannot drift, and `scripts/check-prerender.ts` (`postbuild`) fails the build if a slug in it produced no HTML. 41 component families, 6 written + 35 stubs, plus 6 introduction and 2 utility pages.
- **Icons**: the built-in registry is 34 icons, and the site's chrome needs five it has no reason to ship (`content_copy`, `open_in_new`, `menu`, `light_mode`, `dark_mode`). `scripts/build-icons.ts` generates `icons/icons.ts` from the SAME pinned revision as the library's twin (on demand, never in a build hook), and `plugins/vectis.ts` installs it through `setIconResolver` **at module level in a UNIVERSAL plugin** — returning `undefined` for every other name, which is what hands them back to the registry. Client-only would be a hydration mismatch on every icon; with no resolver at all, an unknown name renders as its own NAME in text.
- **Three traps recovered from the deleted VitePress site, all in `nuxt.config.ts`**: `vite.ssr.noExternal: ['@vectis/ui']` (each component module carries `import './VX.css'`, which Node cannot resolve externalised); `vite.resolve.dedupe: ['vue']` (two Vue copies break `provide`/`inject` across the library boundary, silently); and the pre-paint inline script setting `data-theme`, since `tokens.css` carries NO `prefers-color-scheme` query — "follow the system" is the application's job. A fourth is new: **`imports.transform.exclude` must cover `packages/ui/dist`**, or Nuxt's auto-import injects `import { h } from 'vue'` on top of the bundle's own minified `var h` (a pnpm workspace link has no `node_modules` in its path, so the default exclusion misses it).
- **`features.inlineStyles: false`** — Nuxt inlines critical CSS per page by default, which for 52 prerendered pages means re-sending the same ~50 kB with each and caching none of it.
- **Theme and locale settle AFTER hydration** (`plugins/*.client.ts`, on `app:mounted`): the artefact is one HTML for everybody, so the server cannot know the scheme and the library accepts one locale per process. The cost is one frame of a light-mode icon, the VHotkeys platform precedent.
- **Every destination is a real `<a href>`** inside a `<NuxtLink custom>` — the anchor for middle-click and crawlers, `navigate` for the client-side transition. The slot types `href` as `string | null`, hence the `?? undefined` on each library `href` prop.
- **`BASE_URL` is written once**, at the top of `nuxt.config.ts`. Asset URLs are relative so Vite rewrites them; the two places that need it absolute (the favicon, the `/docs` → `/docs/installation` redirect, whose `<meta http-equiv>` nitro writes VERBATIM) compose it from that constant.
