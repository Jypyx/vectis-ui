# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## The project

**Vectis UI** (`@vectis/ui`): a Vue 3 + TypeScript design system shipped as an npm library, Nuxt 3 (SSR) compatible. pnpm monorepo — `packages/ui` holds everything; `apps/` is reserved for a future live-theming app that will manipulate the token source programmatically and import `@vectis/ui` as `workspace:*`. Project language: **English** (code, comments, docs). Storybook stories are **bilingual FR/EN** (see Storybook below).

## Commands

Everything runs from the root (pnpm enabled through corepack):

```bash
pnpm lint              # eslint (root flat config)
pnpm format            # prettier --check   (format:fix to fix)
pnpm typecheck         # vue-tsc -r
pnpm test              # vitest run -r  → `unit` project (jsdom) only
pnpm test:stories      # play functions in Chromium (Vitest browser mode)
pnpm build             # lib build (regenerates the tokens in prebuild)
pnpm tokens            # regenerates tokens.css + tokens.json from the TS source
pnpm icons             # regenerates the SVG icon registry (network; on demand, NOT in prebuild)
pnpm storybook         # dev server, port 6006
pnpm build-storybook
```

A single test: `pnpm --filter @vectis/ui exec vitest run --project unit src/components/VButton/VButton.test.ts` (or `-t 'test name'`).

**Never prefix a shell command with `cd` or `Set-Location`** — the working directory is already the repo root. Use paths relative to it (`pnpm --filter @vectis/ui exec …`, `packages/ui/src/…`). A leading `cd` turns the call into a compound command, and the permission allowlist arbitrates each segment separately: the prefix alone is what makes an otherwise-allowed `pnpm lint` prompt.

Checkpoint before wrapping up a step: `pnpm lint && pnpm typecheck && pnpm test && pnpm build && pnpm build-storybook` must all pass. `pnpm test:stories` is **outside the checkpoint** (it needs the Playwright binaries, ~115 MB, via `pnpm --filter @vectis/ui exec playwright install chromium`): run it as soon as you touch a play function or browser behaviour.

## Philosophy (non-negotiable — from the project brief)

1. **HTML/CSS first, JS as a last resort.** Native primitives: `<dialog>`+`showModal()`, Popover API, CSS Anchor Positioning, `<details>`, `:user-invalid`, `:has()`, `color-mix()`, `@starting-style`… Any behavioural JS must be **justified by a comment** in the component (see VMenuPanel.vue: the JS is limited to keyboard roving focus and the v-model ↔ imperative popover API bridge).
2. **Zero runtime dependency besides Vue** (`peerDependencies: { vue }` only). No floating-ui: for floating elements, CSS anchor positioning under `@supports` + a small in-house JS fallback (~30 lines) if needed.
3. **No raw values in component CSS** (colour, radius, spacing, type, shadow, duration): semantic `var(--vectis-*)` tokens only. Derived durations go through `calc()` on a token. Tolerated: `1px` borders, opacities.
4. **SSR-safe (Nuxt 3)**: no `window`/`document`/browser-API access outside `onMounted`/`watch`/handlers. Support detection (`CSS.supports`) client-side only. IDs through Vue's `useId()`.

## Comments

The bar is high on purpose: a comment that restates the code is noise, and noise is what makes the load-bearing comments invisible.

**Keep:**

- **One header block per module**, at the very top of `<script setup>` **before the imports**. States what the component is and **why any behavioural JS exists** — philosophy rule 1 makes that justification mandatory, not optional.
- **JSDoc on props, slots, emits and exported functions.** It is the only source of the description column in Storybook's `<Controls>` table (there are no `argTypes.description` anywhere in the repo), and it drives IDE hovers.
- **Trap comments**: a comment earns its place when deleting it would let someone silently break the code — a cascade-order dependency, a CSS cycle, a `flush: 'post'`, a guard whose absence produces no error.

**Delete:** section banners, anything restating the next line, and any comment recording a past state (what a thing used to be called, which bug it fixed, which component did it first). Docs and comments describe the code as it is now.

## Token architecture (the core of the project)

Chain: `src/tokens/*.ts` (typed source of truth, DTCG format `{ $value, $type, $description? }`) → `scripts/build-tokens.ts` (via `pnpm tokens`, run automatically in `prebuild`/`prestorybook`) → `src/styles/tokens.css` + `src/tokens/tokens.json`. An inline Vite plugin (`vite.config.ts`) also emits `dist/tokens.json`.

- **Two namespaces, never to be mixed.** `--vectis-*` = the **public tokens**, generated from the TS source, documented, overridable at runtime by the consumer. Everything else is **private and non-contractual**: a component's local variables, which are **qualified** — either by their component (`--skeleton-w`, `--side-nav-level`, `--dial-radius`, `--calendar-cell`), or by the cross-cutting contract they embody (`--tone-bg-solid` & co for tones, `--control-*` for the size scale, `--fill-fraction` shared by both Progress components and VSlider). **Qualification is not cosmetic**: these variables INHERIT (`.v-control` sets them, every descendant reads them), so a generic name like `--size`, `--radius` or `--gap` would be captured by any host app that defined it on an ancestor — and nothing here would see it, since jsdom does not evaluate styles. Every new local variable therefore takes a qualified name.
- **The `--<component>-anchor` idents are NOT tokens**: `--popover-anchor`, `--combobox-anchor`, `--datepicker-anchor`, `--timepicker-anchor`, `--tooltip-anchor` are `anchor-name` dashed-idents, absent from `tokens.css` and not overridable. Naming them `--vectis-*` would invite the opposite belief. Each has exactly 3 sites (an `anchor-name`, an `anchor-scope`, at least one consumer) and **one of them is a TypeScript prop value**, therefore invisible to any CSS tool: making them diverge by one character paints the panel at the viewport origin, with no console error.
- **Two levels**: primitives (`primitives.ts` — OKLCH palettes, scales) and semantics (`semantic.ts` — the only ones components consume). DTCG aliases `{color.neutral.500}` are resolved to `var(--vectis-color-neutral-500)` at build time (`css.ts`, also exported through `@vectis/ui/tokens` for the future theming app).
- **Themes**: `themes/dark.ts` may override ONLY existing semantic keys (the build checks this and fails otherwise). The generated CSS sets `:root` (everything) + `[data-theme='light']` and `[data-theme='dark']` (semantics only) → theming per DOM subtree, runtime override without a rebuild.
- **`src/styles/tokens.css` and `src/tokens/tokens.json` are GENERATED**: never edit them by hand (they are in .prettierignore; every change goes through the TS source + `pnpm tokens`). **The repo's second generated artefact is `src/components/VIcon/icons.ts`** (`pnpm icons`) — same discipline, different trigger: it is NOT wired into `prebuild` (its script downloads from `google/material-design-icons` at a pinned revision, and the build must not depend on the network).
- **Dedicated dimension tokens**: never `--vectis-space-*` for a component dimension (track, thumb, pill height…) — create a dedicated semantic token. Real spacing (gutter, offset, compact delta, padding) stays legitimately `--vectis-space-*`.
- **Semantic typography**: the `text` group in `semantic.ts` — one role = one complete recipe `--vectis-text-<role>-size/weight/leading[/tracking]` (display, heading-1…4, subtitle, body-lg/md/sm, label, caption, overline, code) + `--vectis-text-family`/`-family-code` + the technical `control` role (weight/leading of control labels; the size comes from `--control-font-size`). Component CSS consumes these recipes, never the `--vectis-font-*` primitives — deliberate, commented exceptions: state emphasis in `--vectis-font-weight-semibold` (VDataTable th, VToast title, VAvatar initials, VCalendar selection/today), VInputOTP's contextual scale, VIcon's font contract.

## CSS cascade

`src/styles/index.css` declares the order: `@layer vectis.reset, vectis.tokens, vectis.components, vectis.utilities;`. Any non-layered consumer style wins — that is the intended override mechanism.

**The layers carry the LONG name where the classes carry `v-`**, and that is not an inconsistency: a layer name is **global and not namespaced**. A consumer writing `@layer v { … }` would see their block absorbed into the DS's and arbitrated by the order declared here — a silent cascade bug, invisible in dev. The shorthand is justified for a class (it is written in the HTML, read in devtools, typed hundreds of times); not for an identifier typed 56 times inside `<style>` blocks and never by a user. **An SFC keeping an undeclared layer would be ordered AFTER every declared layer, and would therefore win over everything**: the guard is `git grep -E "@layer\s+(?!vectis)"`.

- Every SFC has one **non-scoped** `<style>` whose entire content is wrapped in `@layer vectis.components { … }`. The local-variable tables (tones + `[data-custom]`, sizes `data-size`/`data-compact`) live there too, right before the rules that consume them — **one `<style>` per SFC, never a neighbouring CSS file** — no `X.tokens.css` alongside. Internal order stays meaningful: `[data-custom]` after the tones, same specificity, last one wins.
- **The export order in `src/index.ts` fixes the bundled CSS order**: at equal specificity, the last one wins. Current constraints: VIconButton after VButton (overrides padding/width), VSlider after VInput (overrides the width of the `.v-slider-field` number inputs), VToaster after VButton (the close cross is a recoloured VIconButton).
- **Shared stylesheets** (`src/styles/`, imported by `index.css` in this order: reset, tokens, floating, panel, control-size, utilities): `floating.css` (`.v-overlay` — the foundation of EVERY popover; `.v-floating` — anchoring and placements), `panel.css` (`.v-panel` — the common chrome of panels listing rows: VMenu, VCombobox; set by VPopover's `surface` prop), `control-size.css` (`.v-control`), `utilities.css` (`.v-visually-hidden` + the global `v-spin` keyframe, shared by VSpinner and VProgressCircular: `@keyframes` are not arbitrated like declarations, so they sit outside any layer and are declared once). Rule for `.v-panel`: put ONLY declarations there that no panel redeclares — `.v-panel` and `.v-menu`/`.v-combobox-panel` have equal specificity (0,1,0), so any shared declaration would be arbitrated by bundle order. Dimensions (`min/max-inline-size`, `max-block-size`, `overflow`) therefore stay with each panel — `position-anchor` comes from `VPopover`, which also sets `.v-panel` through its `surface` prop. **Corollary — VDatePicker and VTimePicker render their VPopover as a `surface`**: the former because VCalendar carries no background or radius of its own; the latter for BOTH of its panels (a single `VPopover` serves the dial and the list), the dial panel keeping only its column layout and padding.
- Build: a single `dist/styles.css` (reset + tokens + components), never CSS imported by the emitted JS.

## Component conventions

- **Naming, three tiers.** `V` + PascalCase for **components** (`VButton`, `VComboboxOption`, `VTimePickerDial`): the prefix removes the ambiguity of a tag in a template (`<VButton>` vs the native `<button>` vs another library's `Button`). `Vectis` + PascalCase for **cross-cutting** public types, which carry the brand (`VectisMessages`, `VectisMessagesInput`, `VectisIconName`). **No prefix** for types **owned by a component** (`ButtonTone`, `TabsVariant`, `ComboboxOption`, `DataTableColumn`, `CalendarSelection`…): a type inside an `import type {}` has none of a tag's ambiguity, and above all this is what keeps `VComboboxOption.vue` and the `ComboboxOption` type in two distinct namespaces. Prefixing them would collide the component and its type on the same identifier.
- One folder per component: `src/components/VX/VX.vue` + `VX.stories.ts` + `VX.test.ts` + **`VX.mdx`** (Storybook doc — mandatory, written with every new component). Named export added to `src/index.ts`. **Ancillary** files keep their role name, unprefixed: `context.ts`, `state.ts`, `resolver.ts`, `types.ts`, `iconProps.ts`, `icons.ts` — the `V` marks a tag, and a TS module has none.
- `.v-<name>` classes; **variants through `data-variant` / `data-tone` / `data-size`** (no class proliferation). Tones define local variables `--tone-bg-solid`, `--tone-text-tinted`… that the variants consume (see VButton.vue, the reference model).
- API: typed `defineProps` + `withDefaults`, typed `defineSlots`, `defineModel` for v-model, typed `defineEmits` only when there are non-native events. Native attributes go through fallthrough (never redeclared).
- **Wrapper-root pattern** — a component whose root is a wrapper (hidden controls VCheckbox/VRadio/VSwitch inside an enclosing `<label>`; VInput/VTextarea fields; VChip): `defineOptions({ inheritAttrs: false })` + `v-bind="$attrs"` on the functional element (native control / action), keeping `class`/`style` on the root. Otherwise `name`/`required`/`aria-*` land on the wrapper and break forms and accessibility. A hidden input is hidden with `opacity: 0` (stays focusable and submitted), never `display: none`.
- Manipulating a DOM property with no HTML attribute (e.g. `indeterminate`): `watchEffect(..., { flush: 'post' })` — in `pre` flush the template ref is not set yet on the first pass.
- Visible focus: `outline: var(--vectis-focus-ring-width) solid var(--vectis-focus-ring-color)` + offset token. `@media (prefers-reduced-motion: reduce)` for every transition/animation.
- **`src/composables/` and `src/utils/`** — see "Shared code" below. A helper whose natural OWNER is one component stays in its folder even when imported elsewhere: `VIcon/iconProps.ts` produces `VIcon` props, so VIcon sets the contract (same for `VIcon/types.ts` and `VIcon/resolver.ts`).

## Shared code (`src/composables/`, `src/utils/`)

Two folders, one sharp boundary: **`composables/`** = Vue behaviour (`ref`/`computed`/`watch`/lifecycle); **`utils/`** = helpers with no Vue state (pure computation and imperative DOM). Nothing is publicly exported — `index.ts` is untouched, these are internal modules. Admission rule: **≥2 consumers AND a genuinely common body**.

**`utils/`** — `date.ts` and `time.ts` (date and time logic: ISO `YYYY-MM-DD` and 24 h `HH:mm` strings, all in local time, `Intl` on UTC reference instants → SSR-safe; consumed by VCalendar/VDatePicker and VTimePicker/VTimePickerDial); `number.clamp(n, min, max)` (on an empty interval `min` wins: `max` may be derived from an empty list); `css.px(v)` (number or numeric string → `12px`, otherwise `undefined` rather than an invalid custom property); `text.normalizeText(s)` (NFD, accent-insensitive filtering — VCombobox, VDataTable), `text.pad2(n)` and `text.digitsOf(s)` (purely lexical helper: the input masks of VDatePicker and VTimePicker only ever know the digit run, never the separators, which they place themselves — hence its home here rather than in `date.ts`); `array.toggleValue(list, v)` (never mutates in place: the new reference is what wakes consumer v-models — VToggle, VCombobox, VCalendar, VDataTable); `matcher.resolveMatcher(array | predicate)` (the `disabledDates`/`disabledPages` convention, resolved ONCE in a `computed`, array → `Set`); `env.isDev` (dev guards, optional access to `import.meta.env` so it stays inert in a non-Vite consumer); `arrowNav` (below).

**`utils/arrowNav.ts`** — `navigableItems(container, selector)` + `arrowNavigate(event, container, items, { vertical })`, the SINGLE incarnation of arrow-key navigation: DOM discovery (no registry), `display !== 'none'` filter (an item hidden by a container query or by the consumer does not take focus), modulo wrap, RTL inversion on the inline axis only, `preventDefault` applied only when the key is handled. Contract: **move focus, never activate** — activation on focus (VTabs `activation: 'automatic'`) is set by the component, in its own `@focus`. Adopters: VPagination, VTabs, VToggle, and VMenuPanel which passes its OWN list (it also excludes `aria-disabled` items and confines roving to the current panel). Deliberately outside: VCalendar, VCombobox, VInputOTP, VTimePickerDial — they navigate a space of **values**, not a DOM list, and their list edge is a domain clamp.

**`composables/`**

- **`usePopover(el)`** → `{ shown, syncShown, show, hide }`, the state plumbing of a `[popover]` (the JS counterpart of `floating.css`). Two invariants: `shown` is fed **by the DOM** — wire `syncShown` to the panel's `@beforetoggle` AND `@toggle` (the first is synchronous and catches light dismiss, the second is the only one the jsdom stub emits; ToggleEvents do not bubble, so always on the popover element itself) — and **never set by hand**; the idempotence guards avoid `hidePopover()`'s `InvalidStateError` on an already-closed popover. **Every popover in the DS goes through it**: VMenuPanel and VToaster directly, all the others through the `VPopover` component (VCombobox, VTooltip, VDatePicker, VTimePicker). Idiom: **one instance per popover** when a component drives several (VToaster: one per placement, indexed in a `Map`, each carrying its own element ref).
- **`useFieldPanel({ rootEl, panelRef, fieldEl, disabled, focusInPanel, onOpen?, onClose? })`** → `{ open, openPanel, closePanel, onControlClick, onFocusout, onKeydown, onPanelMousedown }`. The "field + `VPopover` in `mode="manual"`" shell of VDatePicker and VTimePicker (their field is read-only only in some modes). The panel is **written imperatively** (`panelRef.show()/hide()`) and **read by model** (`open`, to be bound as `v-model:open` on the VPopover, which feeds it from the DOM): the write must stay synchronous, since the `rAF` that moves focus assumes the panel is already open when it is armed. A `manual` popover does nothing on its own: no light dismiss, no focus move, no focus return to the field. `onOpen`/`onClose` carry what is specific to each component (VTimePicker's draft and step, clearing its live region). `onKeydown` guards `!event.defaultPrevented` on ArrowDown/Enter: **an Enter consumed inside the panel has just closed it and would reopen it as the event bubbles to the root** (covered by a unit test). **`onPanelMousedown` (to be bound as `@mousedown` on the VPopover)** cancels mousedown on the panel's NON-interactive areas: clicking a non-focusable pixel (padding, the gutter between cells) hands focus back to `<body>`, the root's `focusout` fires with a null `relatedTarget` and closes a panel that was just clicked — in VTimePicker that discarded the pending draft. The filter (`closest('button, a, input, select, textarea, [tabindex]')`) is essential: VCombobox's unconditional `preventDefault`, whose focus never leaves the field, would here rob the days and navigation arrows of focus and desynchronize VCalendar's roving. **Invisible in jsdom** (no focus on click) → the `ClicDansLeVide` play functions of both components, verified red without the handler.
- **`useFocusoutDismiss(root, close)`** → the root's `@focusout` handler. A popover stays a DOM descendant even when painted in the top layer, so `contains` is enough; a null `relatedTarget` counts as leaving too. Adopters: VCombobox, and VDatePicker/VTimePicker through `useFieldPanel`.
- **`useRootAttrs()`** → `{ attrs, rootClass, rootStyle, forwardedAttrs }`, the plumbing of the **wrapper-root pattern** (7 adopters: VInput, VTextarea, VTabs, VCombobox, VDataTable, VDatePicker, VTimePicker). `defineOptions({ inheritAttrs: false })` stays in the SFC (it is a compilation option). `rootClass` is typed `ClassBinding` (redeclared locally: `@vue/runtime-dom` exports `ClassValue`, the `vue` package does not re-export it, and `unknown` is rejected by the template).
- **`useAriaLabel(() => props.label)`** → precedence `aria-labelledby` > `aria-label` > `label` prop. Required as soon as a component with `inheritAttrs: false` renders both `v-bind="forwardedAttrs"` and `:aria-label` (VTabs, VToggle) — without arbitration both apply. Elsewhere (VPagination, VBreadcrumb, VToaster, VInputOTP) Vue's fallthrough already makes the consumer's attribute win: there the composable only removes a now-redundant default. Do NOT apply it to VIcon/VIconButton, where `label` is the accessible name of an icon-only control.
- **`useTimer()`** → `{ start(fn, delay), cancel() }`, a re-armable `setTimeout` cancelled on unmount; `delay ≤ 0` runs **synchronously** (DS convention: 0 disarms the deferral; `setTimeout(…, 0)` would not be synchronous). Adopters: VTooltip (open delay), VMenuItem (hover intent delay — ONE instance, since opening and closing are mutually exclusive), VCombobox and VDataTable (their debounces, each keeping its own semantics: dedupe by term on one side, commit to a `ref` on the other). VToaster stays out: its `Map<id, timeout>` is a different structure.
- **`useFieldIds(attrs, hasHint)`**, **`useIconClickHandlers({ name, iconStartLabel, iconEndLabel })`**, **`useTextLimit({ el, text, maxlength, softLimit })`** — shared by VInput and VTextarea. Respectively: ids and `aria-describedby` aggregation (a consumer `id` WINS over the internal `useId()`); detection of `@click:icon-*` listeners in `vnode.props` (declared emits are removed from `$attrs`) with the a11y guard; counter, overflow and soft limit through `setCustomValidity`.
- **`useProgressValue(value, max)`** → `{ clamped, fraction }` (VProgressLinear, VProgressCircular).

**Merges not to attempt** (analysed, no genuinely common body): a shared IntersectionObserver for VTabs/VCombobox; merging `utils/date.ts` and `utils/time.ts`; a shared interface for `defineExpose({ …, el })`; `onClear()` of VInput/VTextarea.

## Internationalization (`src/i18n/`)

**No user-facing text literal in an SFC**: everything goes through the dictionary. DEVELOPER messages (`[Component] …`) stay hardcoded — they address the integrator, not the user.

Chain: `i18n/types.ts` (the `VectisMessages` contract) → `en.ts` (the base, always bundled) + `fr.ts` (opt-in) → `state.ts` (registry + public `setLocale`/`registerMessages`, internal `useMessages`/`useLocale`). A top-level folder, on a par with `tokens/`: neither `utils/` (the current dictionary is reactive state) nor `composables/` (this is configuration, not behaviour).

- **Module-level state** in a `shallowRef` (as in `VIcon/resolver.ts` and `VToast/state.ts`), not provide/inject nor a Vue plugin: it is configuration, settable from any `.ts`. The `shallowRef` is what makes ALREADY-MOUNTED components re-render when `setLocale` is called later. **Trap**: reading `useMessages().value.x` in a `setup()` body FREEZES the value — always inside a `computed` or the template.
- **ACCEPTED LIMIT: one locale per process.** Multi-locale SSR PER REQUEST is not covered (a single Node process serving /fr and /en must pass the text props explicitly); a client-only `setLocale` makes server and client diverge → hydration mismatch. The planned way out: `useMessages` has the shape of a composable, so only its BODY would become `inject(messagesKey, null) ?? currentMessages`, without touching the ~20 consumer SFCs (that would then need a `getCurrentInstance()` guard, the function staying callable outside a component).
- **Depth EXACTLY 2** (`namespace.key` → leaf). This is not decorative: it is what makes merging partial overrides NON-RECURSIVE, hence structurally incapable of descending into a function value (a recursive `DeepPartial<T>` would turn `(n: number) => string` into `{}`).
- **Parameterized messages are typed TS functions**, with no plural engine and no ICU: the English plural is a ternary inside the function. `en` and `fr` are ANNOTATED `: VectisMessages` → key and signature parity is guaranteed at COMPILE time; the parity test covers only the rest (arity, an `as` slipped in later).
- **`en` bundled, `fr` opt-in by import.** The argument is not weight (~0.8 kB gzip) but the uniqueness of the mechanism: enabling the shipped French and adding a language the DS does not ship are the SAME gesture (`registerMessages`), instead of two categories of dictionary. Tree-shaking follows from that.
- **Canonical cascade**: `aria-labelledby` > consumer `aria-label` > `label` prop > dictionary > `en`. `useAriaLabel` takes a getter, so it composes directly: `useAriaLabel(() => props.label ?? m.value.x.y)`. The ~30 text props are KEPT and take precedence — only their literal default lives in a `computed` rather than `withDefaults`.
- **Resolution by language subtag**: `'en-GB'`/`'en-US'` share their words; what distinguishes them comes from `Intl`. Three invariants: never an empty string, never a technical key displayed, never silence in dev when a language is missing.
- **Words and formats resolve SEPARATELY**: `setLocale('de-DE')` with no German dictionary already gives German months, first day of week and hour cycle (all from `Intl`) with English labels. A coherent degraded state, not a bug.
- **Dictionary boundary**: in goes anything that is a WORD or a language's typographic convention (the non-breaking space before `%` in French, the `hh:mm` made of initials); out stays whatever `Intl` derives from the tag, and whatever is made only of digits and universal punctuation — `99+` (VBadge), `+N` (VAvatarGroup), the `N/M` counter, `TIME_SEPARATOR`'s `:`, `date.ts`'s `PLACEHOLDER_FALLBACK`. Those components expose a slot for rephrasing.
- **VCalendar/VDatePicker/VTimePicker** keep their `locale` prop, which takes PRECEDENCE; its default is `undefined` and falls back to the global locale (the `props.x ?? context` idiom of `VAvatar.vue`) — `undefined` must stay distinguishable, same reason as `mode`/`showDial`. VDatePicker is the SINGLE source: `resolvedLocale` is what flows down to VCalendar. `VDataTable` sorts through `localeCompare(…, vectisLocale.value, …)` and not `undefined`, whose runtime locale differs between Node and browser → divergent row order, hence a hydration mismatch.
- **Tests**: all in vitest/jsdom (no browser behaviour involved). `i18n.test.ts` carries the CANONICAL tests of the mechanism (post-mount reactivity, prop/attribute cascade, picker locale) — do not duplicate them across the 20 component files. The English assertions elsewhere are the SAFETY NET: since the default locale is `en`, they must stay green untouched; a red one signals a mis-copied string, never a test to fix.
- **Stories**: the locale itself is driven by story-level `globals` (`globals: { locale: 'fr-FR' }`), which the `preview.ts` decorator turns into a `setLocale`. Do NOT set it in a `beforeEach`: the decorator body runs afterwards and would win. A `beforeEach` with teardown remains mandatory for a `registerMessages` override, whose registry survives Storybook navigation (same rule as `dismissToast()` in the VToast stories).

## Tests: strict split

- **vitest + jsdom** (`*.test.ts`): logic only — emits, v-model, ARIA attributes, fallthrough. jsdom does not cover VPopover/top-layer: the Popover API is stubbed globally in `vitest.setup.ts` (a `data-popover-open` marker + inline display, because `:popover-open` is not evaluable in jsdom and the UA style `[popover]{display:none}` hides the panel from role queries; `hidePopover` also closes `[data-popover-open]` descendants — the stack cascade submenus need). Do not test browser behaviour in jsdom.
- **Storybook play functions** (`storybook/test`: `expect`, `userEvent`, `within`, `waitFor`): real browser behaviour (popover opening, Esc, `:user-invalid`…). Since v-model updates are asynchronous, always go through `waitFor` after an interaction. They run **locally in Chromium** through `@storybook/addon-vitest` (`pnpm test:stories`). They run with the default globals, so the locale is deterministically `en-US`: **play functions assert the English strings**.
- `vitest.config.ts` declares **two projects**: `unit` (jsdom, `src/**/*.test.ts`) and `storybook` (Playwright browser mode, fed by `storybookTest({ configDir: '.storybook' })`). Two traps: a Vitest project **does not inherit** the root's plugins — `vue()` must be repeated in the `storybook` project, otherwise the `.vue` files imported by the stories fail with "invalid JS syntax"; and the plugin applies the `preview.ts` annotations **itself**, so there is no setup file to write (a manual `setProjectAnnotations` would be flagged as redundant).
- `globals: true` in vitest.config.ts is **required** for @testing-library/vue's automatic cleanup — do not remove it (`unit` project).
- vitest's `expect` does NOT have the jest-dom matchers (`toBeVisible`, `toHaveFocus`…): in jsdom, assert on DOM properties (`el.hidden`, `document.activeElement`). Those matchers exist only in `storybook/test` (play functions).

## Storybook

Storybook 10, `@storybook/vue3-vite` framework. Imports: types from `@storybook/vue3-vite`, test utilities from `storybook/test`, MDX blocks from `@storybook/addon-docs/blocks`. - Every story covers: default, variants, states (disabled/loading/error), edge cases (long text). `src/tokens/Tokens.mdx` is generated from the TS source — never duplicate hardcoded values there.
- **NAMING EXEMPTION — Storybook is written WITHOUT the `V`.** `title: 'Components/Button'` and the `# Button` heading at the top of the `.mdx` keep the bare name: the sidebar is a table of contents, and a `V` repeated on every entry adds noise without removing any ambiguity (there is no native `<button>` in a navigation menu). By contrast **all the prose and all the code in the docs is written `VButton`** — the reader must always see the name they will type. This is the only exception to the prefix in the whole repo; the check is inverted, it is the PRESENCE of a `V` that is the bug: `git grep "title: 'Components/V"` and `git grep -E "^# V[A-Z]" -- "*.mdx"` must both return 0.

Prose only (the rendering comes from the stories) — no hardcoded token values.

## Browser support

Popover API, `<dialog>`, `<details name>`, `:user-invalid`, `color-mix()`, `:has()`: Baseline, usable without a fallback. **CSS Anchor Positioning: used WITHOUT a fallback** — modern browsers only (Chrome/Edge 125+, Safari 26+; Firefox unsupported until anchor positioning is stable there). Do not add a JS fallback without an explicit request. `@starting-style`/`allow-discrete`: progressive enhancement only, never required.

**Anchoring patterns** (`src/styles/floating.css`: `.v-overlay` + `.v-floating` + `data-placement` → `position-area`/`position-try-fallbacks`):

- Panel invoked by `popovertarget` (VMenu — submenus included: the parent item is the invoker of the nested panel): the invoker is the **implicit anchor**, no `anchor-name` needed.
- Panel opened programmatically (VTooltip, and `VPopover` when given a `#trigger`): a **shared static `anchor-name`** on the wrapper + `anchor-scope` (same name) confining it to the wrapper's subtree + `position-anchor` on the panel. The confinement is indispensable: a shown popover moves to the top layer and is considered "after" the whole document for anchor resolution — without `anchor-scope`, every panel would attach to the last named wrapper on the page. No unique ID, no inline style. `anchor-scope`: Chrome/Edge 131+, Safari 26+. Vertical range through `writing-mode` (VSlider): Chrome/Edge 129+, Safari 18.1+.
- Aligned placements (`top-start`, `bottom-end`…): the inline margin on the aligned side is cancelled in floating.css (`[data-placement$='-start']`/`[$='-end']`), otherwise the gap `margin` offsets the panel from the trigger's edge. Side placements (submenus, `right-start`): the axis is swapped, so the inline margin is restored (the gap is inline, the alignment block).
- Panel whose consumer already owns the root and the control (VCombobox, VDatePicker, VTimePicker, and VTooltip which keeps its wrapper to attach pointer/focus to it): it sets `anchor-scope`/`anchor-name` itself and passes the name alone to `VPopover` through the **`anchor`** prop (a dashed-ident) → `position-anchor: var(--anchor-name)`. This is the required route as soon as the control is a text `<input>`, on which `popovertarget` is invalid.
- Triggers are provided by scoped slots: `#trigger="{ triggerProps }"` + `v-bind="triggerProps"` (popovertarget, aria-*). VTooltip follows the same pattern (scoped default slot): the consumer is the one setting `aria-describedby`, never an automatic JS bridge at mount.
- **`.v-overlay`** is the foundation of every popover in the DS: `position: fixed; inset: auto` (neutralizes the UA styles of `[popover]`) + the guard `.v-overlay:not(:popover-open) { display: none }`. A panel setting its own `display` (`.v-panel` as flex, the toast stack as a column) overrides the UA `display: none` of `[popover]` (author styles > UA) and a closed panel would stay clickable at `opacity: 0` on top of the content; the guard's specificity (0,2,0) puts it out of reach of a component `display`, whatever the bundle order. **The class goes on the six panels AND on the toast stacks** (`.v-toast-stack`, which cannot carry `.v-floating`: physical coordinates, no anchor, zero margin). The transition blocks stay separate (VToaster: opacity alone at `--vectis-duration-base`; `.v-floating`: opacity + `transform` at `--vectis-duration-fast`). VDialog stays out: a `<dialog>` is not a popover, `:popover-open` does not apply to it — hence its own `.v-dialog:not([open])`.

## Size scale (controls)

Unified **xs/sm/md/lg/xl** scale (24/32/40/48/56px, tokens `--vectis-control-height-xs…xl`). The size → height/font/icon/opsz/gap mapping lives in ONE CSS incarnation: `src/styles/control-size.css`, class **`.v-control`** set on the root carrying `data-size`/`data-compact`. The `[data-size]` blocks define ONLY `--control-*` custom properties (inherited down to the children, e.g. VInput's field — no specificity conflict) + the VIcon context `--vectis-icon-size`/`--vectis-icon-opsz`.

- **Compact** = -4px of height everywhere (`--control-height` derived from `--control-height-base`).
- Mappings (literal, font contract preserved — no new tokens): icons xs→16 / sm-md→20 / lg-xl→24; opsz xs-md→20, lg-xl→24; fonts xs→xs, sm-md→sm, lg-xl→md; gap `--control-gap` xs→4px, sm-md→8px, lg-xl→12px; paddings = `--vectis-space-*` directly.
- **The full scale is not exposed everywhere**: each component restricts its TS union to the subset that makes sense for it, `control-size.css` remaining the single table (its xs/xl blocks still serve the buttons). There is deliberately **no shared `ControlSize` type** — the scales differ, a single type would be wrong.
- Adopters and subsets: VButton/VIconButton/VPagination/VTabs/VToggle (**xs–xl**); VSideNavigation (sm/md, default md — `v-control` on the `<nav>`, every sublist inherits); **every component with a text input → sm/md/lg** (32/40/48px, default md): VInput, VTextarea, VInputOTP (type bumped one or two notches), VDatePicker, VTimePicker, VCombobox (which propagates its size unchanged to its panel) — `xs` (24px) is too short for editable text and `xl` (56px) is outside the form template: do not expose them; VChip (xs/sm, default xs); VMenu (sm/md/lg, default sm — `v-control` on the panel, see next bullet); VAvatarGroup.
- **Panels carry `v-control` on the PANEL, their rows consume it**: the panel, which already carries `data-size`/`data-compact`, carries `v-control`; `.v-menu-item`/`.v-combobox-option`/`.v-combobox-state` read the inherited `--control-*` (height, `--control-padding-inline`, gap, font-size) and the icons follow without a line of CSS. **Invariant**: a VMenu subpanel does NOT take the class (`:class="{ 'v-control': !submenu }"`) — `.v-control` re-sets `--control-height` from `--control-height-base` **without** the `[data-compact]` condition, which a subpanel does not carry: it would lose the inherited compact. Same reason why `panel.css` does not set the VIcon context. The only exception to the table: row typography is composite (size from the scale, unitless `body-md` leading, regular weight) — the `control` recipe means medium/leading 1, but a row may wrap and carry a sublabel. **GROUP LABELS consume `--control-height` too** (`.v-menu-group-label`, `.v-combobox-group-label`, `.v-side-nav-group-label` — the only three in the DS): `display: flex` + `align-items: center` + `min-height`, the same recipe as the rows, so a section header does not break the list's vertical rhythm (compact included, `--control-height` already derives from it). Their typography stays outside the scale (`overline` role), hence the vertical centring. This rule is not factored into `panel.css`: it would be at equal specificity with the panels' own rules, and VSideNavigation does not share the padding anyway (indented per level).

**Internal, non-exported components** (no story and no `.mdx` — their doc lives with their consumer): `VMenu/VMenuPanel.vue`, `VCombobox/VComboboxOption.vue`, `VCombobox/VComboboxGroup.vue`, `VCombobox/VComboboxSeparator.vue`, `VToast/VToast.vue`, `VTimePicker/VTimePickerDial.vue`.

Do not refactor them into a single panel parameterized by a `role` prop: they share only the chrome (`.v-panel`) and the plumbing (`VPopover`), which is already factored out.

**`VPopover` is the shared brick for panel PLUMBING** (the `[popover]` element and its mode, the DOM ↔ `v-model:open` state bridge, anchoring, placement, optional surface) — never the ARIA role, the keyboard, the focus or the dismissal policy, which stay with each component. Adopters: VCombobox, VTooltip, VDatePicker, VTimePicker. **VMenu and VToaster stay out, deliberately**: VMenu is the only `popover="auto"` (native light dismiss, implicit anchor through `popovertarget`, submenus opened with `showPopover({ source })` forming a native stack) — moving it in would impose a 3rd anchoring strategy and a 2nd mode for no gain; VToaster has no anchor at all (physical coordinates, six permanent stacks) and already does not carry `.v-floating`.

Cross-cutting rules covered above: tone/variant (VButton = the reference), wrapper-root pattern, size scale, disabled **greyed through tokens** (never `opacity` — except `loading`, which keeps `opacity: 0.5`).

### Per-component characteristics

- **VIcon**: **the DS requires NO icon font.** Resolution, in this order: `render` prop (explicit rendering) → `src` prop → `name` (consumer resolver → **built-in registry** → ligature) → SVG slot. The order IS the contract: the resolver comes before the registry (otherwise the DS's icons would stay Material for anyone who wired their own library), and a resolver returning `undefined` hands over to the registry — which is what makes PARTIAL mappings usable. `data-icon="<name>"` is set whatever the source: a test hook and a CSS extension point. Contextual control through `--vectis-icon-size`/`--vectis-icon-opsz`; an explicit `size` prop wins — **`--vectis-icon-opsz` only affects the ligature** (a font axis; the registry is drawn at opsz 24), while the size applies to every source.
  - **Built-in registry** — `VIcon/icons.ts`, GENERATED by `pnpm icons`: the 20 icons the library renders by default, as Material Symbols Rounded paths (wght 400 · GRAD 0 · opsz 24, Apache-2.0 © Google), in the form `[outline, filled?]` — the second path is emitted only when the FILL axis really changes the geometry (7 of 20; the script does the comparison, never a human). ~2 kB gzip, **not tree-shakable** (string lookup at runtime): the accepted price of autonomy. Add a name to the script's array when a component starts rendering a new icon by default. Rendered as `<svg><path>` and not `mask-image`: a masked background disappears under Windows forced-colors, where `fill: currentcolor` survives.
  - **`setIconResolver`** (`VIcon/resolver.ts`) — hook for a third-party library, module-level global state. To be set at module level (Nuxt plugin, `main.ts`), never inside a `setup()`, never client-only (hydration mismatch). Three generic factories, one per source family, with no knowledge of any third-party lib: `ligatureIconResolver` (Material, IcoMoon — **and the way to find the opsz 20/24 axis on the DS's 20 icons**), `classIconResolver` (Font Awesome, Phosphor, Bootstrap — renders a DS `<span class="v-icon-glyph">`, not an `<i>`: the DS owns the element, so it normalizes it in one rule; `strict` by default, a registry name with no alias falls back to the built-in SVG rather than producing an empty square), `componentIconResolver` (Lucide, Untitled UI — contract: a single `<svg>` root, sizing goes through `.v-icon > svg`). No per-library preset: the alias tables live in the docs, where they can be fixed without a release.
  - **`IconSource = string | IconRender`** (`VIcon/types.ts`) — the type of EVERY icon prop in the DS. **NO heuristic**: a string is always a NAME, an image or a component is declared as an object (`{ src }`, `{ component }`, `{ path }`, `{ text }`, `{ class }`). That is what makes `mdi:close` or `fa6-solid:xmark` valid names rather than URLs. `iconName(source)` is its counterpart — a readable name for a fallback label, `undefined` on an object (VInput/VTextarea, otherwise `[object Object]` in the accessibility tree).
- **VTypography**: a text element — `variant` (13 roles, see the semantic type tokens) + `tone` (default = inherit, muted/subtle/accent/danger/success/warning/on-inverse) + `as` (free tag; defaults h1…h4/p/span/code per variant) + `truncate`. No margins (spacing belongs to the parent layout), no JS beyond deriving the tag; single root → native fallthrough (`as="label"` + `for` = a real field label). The base block re-sets `--typography-family`/`--typography-tracking` on every instance (cutting inheritance from an ancestor VTypography's `--*`). Rendered internally by VDialog (title/subtitle), VInput/VTextarea (label/hint), VAccordionItem (subtitle), VDataTable (title) — their own classes (`.v-dialog-title`…) stay in place as hooks. The VInput/VTextarea counters stay local (tabular-nums + data-over ≠ a type role). The "all variants" story uses `as="p"` (the docs page owns the heading hierarchy).
- **VPopover**: a generic floating panel and a plumbing brick (see above). Two mutually exclusive anchoring modes: the **`#trigger`** slot (standalone) → a `.v-popover` wrapper in `inline-block` carrying `anchor-name`/`anchor-scope: --popover-anchor` (a shared static name, confined per instance) + `triggerProps` (`popovertarget`/`aria-expanded`/`aria-controls`, the **disclosure** pattern: neither a role nor `aria-haspopup` is imposed); the **`anchor`** prop (internal brick) → no layout wrapper, `display: contents` — an empty `inline-block` would create a line box, hence height, for every consumer. A single declaration covers both: `position-anchor: var(--anchor-name, --popover-anchor)`. `mode` auto (default, native light dismiss) / manual. `surface` (default true) sets `.v-panel`. `v-model:open` is **bidirectional** (fed by the DOM through `usePopover`) AND `defineExpose({ show, hide, el })`: the expose is what VTooltip and `useFieldPanel` use, since their opening must be **synchronous** (the model would insert a tick, and both `useTimer`'s 0 delay and the focus `rAF` would lose their meaning). `inheritAttrs: false` + `v-bind="$attrs"` on the **panel**, class/style included — a deliberate variant of the wrapper-root pattern (the visual subject is the panel, not the anchoring wrapper), hence no `useRootAttrs`. **The CSS carries NO dimension**: `min/max-inline-size`, `max-block-size` and `overflow` vary from one consumer to the next and would be arbitrated by bundle order at equal specificity.
- **VButton**: the reference tone/variant model. Variants including `elevated`/`tonal`, tones `success`/`warning` (the `text-on-warning` token = neutral-950, since white fails AA on amber). `iconStart`/`iconEnd` (fallback slots #start/#end). Rendered as `<a>` through `href` (an inert link when disabled/loading: href removed + aria-disabled + click handlers filtered — the only JS, `inheritAttrs: false`). `compact` = -4px.
- **VIconButton**: square, width = `var(--control-height)` as set by VButton.
- **VButtonGroup**: a `role="group"` wrapper that joins VButton/VIconButton into a segmented control (merged borders `margin: -1px`, rounded corners only at the ends through logical `border-*-*-radius` properties, a `--vectis-color-border` seam between solid segments, `z-index` on hover/focus/active). CSS-only (no provide/inject): each button keeps its props; set the same variant/tone/size on the children for consistency. `orientation` horizontal (default) / vertical. Exported after VIconButton (overrides `.v-button-group > .v-button`).
- **VPagination**: **composed** — every pill is a `VButton` (the active page is always `solid` + `aria-current="page"`; inactive ones `ghost`/`outline` in `tone="neutral"`), the controls are a `VButton`/`VIconButton` (`controlsDisplay` icon/text/both, `prevIcon`/`nextIcon` through `iconProps`), and `attached` joins everything in a **VButtonGroup**. **No `<ul>`/`<li>`**: VButtonGroup only styles its direct children — which is also why the ellipsis is a disabled `VIconButton` `more_horiz` (still a `.v-button`, so the seam stays continuous) rather than a `<span>`. No state rule is redefined (everything comes from VButton); `size`/`compact` are propagated to every child; `.v-pagination-page` overrides `min-inline-size: var(--control-height)` (the VIconButton model) → **export after VButtonGroup in `index.ts`**. **Double truncation**: (1) logical — `length` (default 1) sets the page count, all rendered by default; `totalVisible` is the total number of **slots** rendered, ellipses included (clamped to a minimum of 5), first/last always kept, the window centred on the current page **shifting** at the ends instead of shrinking (constant bar width), pure derivation; (2) responsive — **100% CSS**, the nav is its own query container (`container-type: inline-size` + `container-name`), 3 `@container` steps (36/31/25rem) hide neighbours with `display: none` by decreasing `data-distance` (capped at 3), the edges (`data-edge`) and the current page carrying none and so never hidden; the middle step also folds a `both` control down to icon-only (it costs ~4× a pill). Each threshold is the width **needed to display** the level, not what is left after hiding — otherwise the row overflows for the whole interval. The containment is **reserved for responsive mode** (`.v-pagination[data-responsive]`): every `@container` depends on it, and outside responsive mode (the default) the nav regains an intrinsic width — so no `flex: 1` is needed from the parent (see the VDataTable footer). Accepted consequence when it applies: the nav is **block-level** (an `inline-flex` would collapse to zero), hence the `align` prop. Thresholds as rem literals (no `var()` in `@container`), calibrated on `md`; escape hatches `totalVisible` / `responsive: false`. No ellipsis is added to compensate for a hidden neighbour (same width as a pill, zero gain). `disabledPages`: a list **or** a predicate (the `disabledDates` convention); the controls **step over** disabled pages and disable themselves when none is left (covering the ends without a separate test). The only behavioural JS: arrow/Home/End keys on the nav, delegated to `utils/arrowNav` — whose `display` filter excludes the pills hidden by the container queries.
- **VTabs** (+ **VTab**, **VTabPanel**): **composed** — every tab is a `VButton` (active = `elevated` in the `inset` variant, `ghost` otherwise; the context `tone` when active, `neutral` when inactive), the scroll controls are `VIconButton`s. No state rule is redefined. **Composed** API with two slots: `#default` (the `VTab`s, inside the `role="tablist"`) and `#panels` (the `VTabPanel`s) — a single slot could not split them across two DOM containers; `#panels` absent = a plain bar / segmented control. A `VTabs/context.ts` context (getters, the VAccordion model) carries `value`/`select`/`tabId`/`panelId`/`hasPanels`/`variant`/`tone`/`size`/`compact`/`activation` — `size`/`compact` travel through it (and not through CSS inheritance: each VButton sets its own `v-control[data-size]`). Ids derive from a single `useId()` and are **sanitized** (`aria-controls` is a space-separated IDREF list); `hasPanels` is a getter on `slots.panels !== undefined`, **deterministic SSR/client** so there is no reactive registry and no hydration mismatch (the trade-off: `#panels` must be statically present or absent). The root uses the **wrapper-root pattern** (`inheritAttrs: false`, class/style on the root, everything else on the tablist). Variants pack **two decisions into one `data-variant`** — the track (`flat` / `inset`) and the frame (`outlined` = `flat` + a frame). `flat` (default; track `border-block-end` carried by `.v-tabs-bar` — not by the scroller, otherwise it would stop before the scroll buttons and the indicator could not cover it — plus `margin-block-end: -1px` on the list, the VButtonGroup idiom; `::after` indicator in `currentColor`, which follows both the tone AND the disabled grey, dedicated token `--vectis-control-size-tab-indicator`). On a track (`flat` as well as `outlined`) the tabs are **contiguous square-cornered segments** — `gap: 0` on the list, `border-radius: 0` on the tab: it is the indicator and the track that carve the bar, not the buttons' silhouette (the BAR's `gap` stays, it separates the scroll buttons); `outlined` alone takes `--vectis-radius-interactive` back at the **ends** of the row, on the side the track does not occupy (the VButtonGroup idiom, square internal seams; `:first-of-type`/`:last-of-type` — the edge sentinels are the list's real first and last children). `outlined`: `flat` line for line **plus** the frame from the **decoration scale shared with VAccordion and VDataTable** (`surface-raised` + a 1px border + `--vectis-radius-surface`) set on the ROOT, so around the bar AND the panels — the track becomes the separator between the two, inside the frame. Gutter `--tabs-frame-pad` (the `--table-frame-pad` idiom: `0px` when flat — a strict no-op — `--vectis-space-3` when framed), consumed by the bar (`padding-inline` + `padding-block-start`; **never the edge the track occupies**, or it would stop separating) and by `.v-tabs-panels` (full padding); **fixed, not indexed on `data-size`/`compact`** — it is a card measurement, and the `--control-*` variables live on the descendant VButtons, out of the root's reach. **No `overflow: clip`** unlike VDataTable, whose table is edge-to-edge by construction: here the gutter always leaves a band ≥ the inner radius (no box reaches a corner, so no nested `calc()` radius is needed), the list already crops its own overflow, and clipping would crop the `VTabPanel`'s **outer** focus ring, the only one leaving the component. Track and indicator are written for BOTH values with `:is([data-variant='flat'], [data-variant='outlined'])` — explicit rather than `:not([data-variant='inset'])`: a 4th frame will have to opt in by hand instead of inheriting silently, and both literals stay greppable; specificity is unchanged, `:is()` taking that of its arguments. `inset`: a hollow `surface-sunken` track on the scroller itself, so that its padding protects the shadow of the `elevated` tab; nested radius through `calc()`; never framed (it is already its own surface). `orientation` vertical: the root becomes a `row` (panels alongside), the indicator sits at the start edge in both frames — but the track **migrates** from `border-inline-start` (flat: it delimits the tab column) to `border-inline-end` (framed: that edge is already held by the frame's border; what is missing is the bar/panels boundary), and the `margin-inline-start: -1px` overlap trick is then **neutralized** — there is nothing left to overlap, and it would slide the list under the border. These overrides are at EQUAL specificity with the `:is()` rules: order decides. Without a `#panels` slot, `outlined` removes the track (it would double the frame's border, flush against it) and closes the gutter on that edge — guard `:not(:has(> .v-tabs-panels))`. None of these rules is observable in jsdom (styles not injected, no layout): the unit tests only lock `data-variant` and the mapping to the VButton variant, the rest is covered by the `Variants` and `Vertical` stories (Chromatic). `align` is set on the **bar** and not on the list (a `justify-content` on an overflowing container would make the part past the start edge unreachable) — so it is a no-op in vertical without a height. `grow` = `flex: 1 1 0` on the tabs (the label wrapped in `.v-tab-label`, since `text-overflow` does not apply to the anonymous text of a flex item); incompatible by construction with scrolling. Scrolling: list `overflow: auto` + `scrollbar-width: none` + `scroll-behavior: smooth` (so `scrollBy` **without** `behavior`, which would not respect reduced-motion). `scrollButtons` is opt-in; **the ends are measured by two `IntersectionObserver` sentinels** (a single observer for scroll + resize + tab additions, where a ResizeObserver would be a second mechanism and the repo's first; defaults `true` = buttons disabled in SSR/jsdom; `::scroll-button()` is a future target, below the Safari floor). Every VButton override is qualified **`.v-tab[data-size]`** (the VIconButton model) → the order in `index.ts` is not constraining. **Inner** focus ring (negative `outline-offset`): the scroller would crop a positive one. Panels: native `hidden` (content state preserved; fields still submitted) + a `lazy` prop; guard `.v-tabs-panel[hidden] { display: none }` **without `!important`** (the UA style is overridden by any author `display` declaration). Behavioural JS: roving tabindex + arrows/Home/End through `utils/arrowNav`, which **moves focus without activating** (`activation: 'manual'` by default; `'automatic'` = select on focus, set in `VTab.@focus` so the value does not travel through the DOM); the active tab is scrolled back into view with `scrollBy` **bounded to the list** (`scrollIntoView` would walk up every scrollable ancestor). A `disabled` tab is a `<button disabled>` (skipped by the arrows, like VPagination's pages). Contract: the `v-model` must reference an existing, activatable tab, otherwise no tab has `tabindex="0"`.

- **VSkeletonLoader**: a 100% CSS loading silhouette. - **VCombobox**: **composed** of `VInput` (the `role="combobox"` search field), `VPopover` and `VChip` (values in multiple mode). A flat `ComboboxOption[]` stays valid. Two computeds are enough, and the invariant lies in their separation: **`allOptions`** flattens (the single read of `options` for filtering, the cache, the labels and pagination — the hierarchy is invisible to them) and **`rendered`** is the only one that knows about it, each option there carrying its **index in `filtered`** (not its position in the tree) so that `optionId`/`activeIndex`/the `#option` slot stay aligned with a keyboard navigation that remains flat. A row's rendering is written twice (inside a group, at the panel root) — a Vue template has no reusable fragment: the `rowProps`/`optionSlotProps` factories reduce the duplication to one line. Scoped slots `#option`/`#chip`/`#empty`/`#loading`. **`#chip`** replaces a value's VChip in multiple mode and receives `{ value, option, label, remove, size, compact }`: `remove` (without which the value could no longer be removed) and `size`/`compact` (the "one step below the field" template, impossible to guess) are what make the slot usable without a regression. It is for it that the selection cache holds the **whole option** (`optionCache`/`optionOf`) and not just the label — otherwise a custom VChip would lose the option's icon on the first server-side filter. Trap: an option coming from the cache is a reactive proxy, so compare by `value`, never by identity (the current path, `props.options.find`, preserves the reference).
