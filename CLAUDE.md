# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Le projet

**Socle** (`@socle/ui`) : design system Vue 3 + TypeScript distribué en librairie npm, compatible Nuxt 3 (SSR). Monorepo pnpm — `packages/ui` contient tout ; `apps/` est réservé à une future app de theming temps réel qui manipulera la source des tokens programmatiquement et importera `@socle/ui` en `workspace:*`. Langue du projet : français (commentaires, stories, docs).

## Commandes

Tout se lance depuis la racine (pnpm activé via corepack) :

```bash
pnpm lint              # eslint (flat config racine)
pnpm format            # prettier --check   (format:fix pour corriger)
pnpm typecheck         # vue-tsc -r
pnpm test              # vitest run -r  → projet `unit` (jsdom) uniquement
pnpm test:stories      # play functions dans Chromium (Vitest browser mode)
pnpm build             # build lib (régénère les tokens en prebuild)
pnpm tokens            # régénère tokens.css + tokens.json depuis la source TS
pnpm storybook         # dev server port 6006
pnpm build-storybook
```

Un seul test : `pnpm --filter @socle/ui exec vitest run --project unit src/components/Button/Button.test.ts` (ou `-t 'nom du test'`).

Checkpoint avant de conclure une étape : `pnpm lint && pnpm typecheck && pnpm test && pnpm build && pnpm build-storybook` doivent tous passer. `pnpm test:stories` est **hors checkpoint** (il exige les binaires Playwright, ~115 Mo, via `pnpm --filter @socle/ui exec playwright install chromium`) : à lancer dès qu'on touche à une play function ou au comportement navigateur.

## Philosophie (non négociable — vient du cahier des charges)

1. **HTML/CSS d'abord, JS en dernier recours.** Primitives natives : `<dialog>`+`showModal()`, Popover API, CSS Anchor Positioning, `<details>`, `:user-invalid`, `:has()`, `color-mix()`, `@starting-style`… Tout JS de comportement doit être **justifié par un commentaire** dans le composant (voir MenuPanel.vue : le JS se limite au roving focus clavier et au pont v-model ↔ API impérative du popover).
2. **Zéro dépendance runtime hors Vue** (`peerDependencies: { vue }` uniquement). Pas de floating-ui : pour les flottants, anchor positioning CSS sous `@supports` + mini-fallback JS maison (~30 lignes) si nécessaire.
3. **Aucune valeur brute dans le CSS des composants** (couleur, radius, espacement, typo, ombre, durée) : uniquement des tokens sémantiques `var(--ds-*)`. Les durées dérivées passent par `calc()` sur un token. Tolérés : bordures `1px`, opacités.
4. **SSR-safe (Nuxt 3)** : aucun accès `window`/`document`/API navigateur hors `onMounted`/`watch`/handlers. Détection de support (`CSS.supports`) côté client uniquement. IDs via `useId()` de Vue.

## Architecture des tokens (cœur du projet)

Chaîne : `src/tokens/*.ts` (source de vérité typée, format DTCG `{ $value, $type, $description? }`) → `scripts/build-tokens.ts` (via `pnpm tokens`, auto-lancé en `prebuild`/`prestorybook`) → `src/styles/tokens.css` + `src/tokens/tokens.json`. Un plugin Vite inline (`vite.config.ts`) émet aussi `dist/tokens.json`.

- **Deux niveaux** : primitifs (`primitives.ts` — palettes OKLCH, échelles) et sémantiques (`semantic.ts` — seuls consommés par les composants). Les alias DTCG `{color.neutral.500}` sont résolus en `var(--ds-color-neutral-500)` au build (`css.ts`, aussi exporté via `@socle/ui/tokens` pour la future app de theming).
- **Thèmes** : `themes/dark.ts` ne peut surcharger QUE des clés sémantiques existantes (le build le vérifie et échoue sinon). Le CSS généré pose `:root` (tout) + `[data-theme='light']` et `[data-theme='dark']` (sémantiques seulement) → theming par sous-arbre DOM, surcharge runtime sans rebuild.
- **`src/styles/tokens.css` et `src/tokens/tokens.json` sont GÉNÉRÉS** : ne jamais les éditer à la main (ils sont dans .prettierignore ; toute modif passe par la source TS + `pnpm tokens`).
- **Tokens de dimension dédiés** : jamais `--ds-space-*` pour une taille de composant (track, thumb, hauteur de pastille…) — créer un token sémantique dédié. Un vrai espacement (gouttière, offset, delta compact, padding) reste légitime en `--ds-space-*`.
- **Typo sémantique** : groupe `text` dans `semantic.ts` — un rôle = une recette complète `--ds-text-<rôle>-size/weight/leading[/tracking]` (display, heading-1…4, subtitle, body-lg/md/sm, label, caption, overline, code) + `--ds-text-family`/`-family-code` + rôle technique `control` (weight/leading des étiquettes de contrôles ; la size vient de `--_control-font-size`). Le CSS des composants consomme ces recettes, jamais les primitifs `--ds-font-*` — exceptions assumées et commentées : emphases d'état en `--ds-font-weight-semibold` (th DataTable, titre Toast, initiales Avatar, sélection/aujourd'hui Calendar), échelle contextuelle d'InputOTP, contrat police d'Icon.

## Cascade CSS

`src/styles/index.css` déclare l'ordre : `@layer ds.reset, ds.tokens, ds.components, ds.utilities;`. Tout style consommateur non-layerisé gagne — c'est le mécanisme de surcharge voulu.

- Chaque SFC a un `<style>` **non-scoped** dont tout le contenu est enveloppé dans `@layer ds.components { … }`. Les tables de variables locales (tones + `[data-custom]`, tailles `data-size`/`data-compact`) y vivent aussi, juste avant les règles qui les consomment — **un seul `<style>` par SFC, jamais de fichier CSS voisin** — pas de `X.tokens.css` à côté. L'ordre interne reste significatif : `[data-custom]` après les tones, même spécificité, le dernier gagne.
- **L'ordre des exports dans `src/index.ts` fixe l'ordre du CSS bundlé** : à spécificité égale, le dernier gagne. Contraintes actuelles : IconButton après Button (surcharge padding/largeur), Slider après Input (surcharge la largeur des champs numériques `.ds-slider-field`), Toaster après Button (croix = IconButton recoloré).
- **Feuilles partagées** (`src/styles/`, importées par `index.css` dans cet ordre : reset, tokens, floating, panel, control-size, utilities) : `floating.css` (`.ds-overlay` — socle de TOUT popover ; `.ds-floating` — ancrage et placements), `panel.css` (`.ds-panel` — chrome commun des panneaux listant des rangées : Menu, Combobox ; posé par la prop `surface` de Popover), `control-size.css` (`.ds-control`), `utilities.css` (`.ds-visually-hidden` + la keyframe globale `ds-spin`, partagée par Spinner et ProgressCircular : les `@keyframes` ne sont pas arbitrées comme des déclarations, donc hors layer et déclarées une seule fois). Règle pour `.ds-panel` : n'y mettre QUE des déclarations qu'aucun panneau ne redéclare — `.ds-panel` et `.ds-menu`/`.ds-combobox-panel` sont à spécificité égale (0,1,0), toute déclaration commune serait arbitrée par l'ordre du bundle. Les dimensions (`min/max-inline-size`, `max-block-size`, `overflow`) restent donc chez chaque panneau — `position-anchor` vient de `Popover`, qui pose aussi `.ds-panel` via sa prop `surface`. **Corollaire — le panneau du cadran du TimePicker est rendu en `:surface="false"`** : il redéclarerait `gap`/`padding`/`border`/`border-radius`, sa ressemblance avec `.ds-panel` est de surface. Son panneau de LISTE, lui, prend bien `surface` (il n'a que des dimensions propres), d'où le `:surface="isList"` — un seul `Popover` sert les deux. Le DatePicker prend `surface` depuis que le Calendar a perdu son fond et son rayon propres.
- Build : un seul `dist/styles.css` (reset + tokens + composants), jamais de CSS importé par le JS émis.

## Conventions composants

- Un dossier par composant : `src/components/X/X.vue` + `X.stories.ts` + `X.test.ts` + **`X.mdx`** (doc Storybook — obligatoire, générée à chaque nouveau composant). Export nommé ajouté dans `src/index.ts`.
- Classes `.ds-<nom>` ; **variantes via `data-variant` / `data-tone` / `data-size`** (pas de prolifération de classes). Les tones définissent des variables locales `--_bg-solid`, `--_text-tinted`… que les variantes consomment (voir Button.vue, le modèle de référence).
- API : `defineProps` typées + `withDefaults`, `defineSlots` typés, `defineModel` pour v-model, `defineEmits` typés seulement s'il y a des événements non natifs. Les attributs natifs passent par fallthrough (pas de re-déclaration).
- **Pattern wrapper-root** — un composant dont la racine est un wrapper (contrôles masqués Checkbox/Radio/Switch en `<label>` englobant ; champs Input/Textarea ; Chip) : `defineOptions({ inheritAttrs: false })` + `v-bind="$attrs"` sur l'élément fonctionnel (contrôle natif / action), en gardant `class`/`style` sur la racine. Sinon `name`/`required`/`aria-*` atterrissent sur le wrapper et cassent formulaires et accessibilité. Un input masqué l'est via `opacity: 0` (reste focusable/soumis), jamais `display: none`.
- Manipuler une propriété DOM sans attribut HTML (ex. `indeterminate`) : `watchEffect(..., { flush: 'post' })` — en flush `pre`, la ref template n'est pas encore posée au premier passage.
- Focus visible : `outline: var(--ds-focus-ring-width) solid var(--ds-focus-ring-color)` + offset token. `@media (prefers-reduced-motion: reduce)` pour toute transition/animation.
- **`src/composables/` et `src/utils/`** — voir la section « Code partagé » ci-dessous. Un helper dont un composant est le PROPRIÉTAIRE naturel reste dans son dossier même s'il est importé ailleurs : `Icon/iconProps.ts` produit des props d'`Icon`, c'est Icon qui en fixe le contrat.

## Code partagé (`src/composables/`, `src/utils/`)

Deux dossiers, une frontière nette : **`composables/`** = comportement Vue (`ref`/`computed`/`watch`/cycle de vie) ; **`utils/`** = helpers sans état Vue (calcul pur et DOM impératif). Rien n'est exporté publiquement — `index.ts` n'est pas touché, ce sont des modules internes. Règle d'admission : **≥2 consommateurs ET un corps réellement commun**.

**`utils/`** — `date.ts` et `time.ts` (logique de dates et d'heures : chaînes ISO `YYYY-MM-DD` et `HH:mm` 24 h, tout en heure locale, `Intl` sur des instants de référence UTC → SSR-safe ; consommés par Calendar/DatePicker et TimePicker/TimePickerDial) ; `number.clamp(n, min, max)` (sur intervalle vide, `min` gagne : `max` peut être dérivé d'une liste vide) ; `css.px(v)` (nombre ou chaîne numérique → `12px`, sinon `undefined` plutôt qu'une custom property invalide) ; `text.normalizeText(s)` (NFD, filtrage insensible aux accents — Combobox, DataTable), `text.pad2(n)` et `text.digitsOf(s)` (helper purement lexical : les masques de saisie de DatePicker et TimePicker ne connaissent que la suite de chiffres, jamais les séparateurs, qu'ils posent eux-mêmes — d'où sa place ici plutôt que dans `date.ts`) ; `array.toggleValue(list, v)` (jamais de mutation en place : la nouvelle référence est ce qui réveille les v-model consommateurs — Toggle, Combobox, Calendar, DataTable) ; `matcher.resolveMatcher(tableau | prédicat)` (convention `disabledDates`/`disabledPages`, résolue UNE fois en `computed`, tableau → `Set`) ; `env.isDev` (garde-fous de dev, accès optionnel à `import.meta.env` pour rester inerte chez un consommateur non-Vite) ; `arrowNav` (ci-dessous).

**`utils/arrowNav.ts`** — `navigableItems(container, selector)` + `arrowNavigate(event, container, items, { vertical })`, incarnation UNIQUE de la navigation par flèches : découverte DOM (pas de registre), filtre `display !== 'none'` (un item masqué par une container query ou par le consommateur ne capte pas le focus), wrap modulo, inversion RTL sur l'axe inline seulement, `preventDefault` appliqué seulement si la touche est traitée. Contrat : **déplacer le focus, jamais activer** — l'activation au focus (Tabs `activation: 'automatic'`) est posée par le composant, dans son propre `@focus`. Adoptants : Pagination, Tabs, Toggle, et MenuPanel qui passe sa PROPRE liste (elle exclut aussi les `aria-disabled` et confine le roving au panneau courant). Restent dehors, délibérément : Calendar, Combobox, InputOTP, TimePickerDial — ils naviguent un espace de **valeurs**, pas une liste DOM, et leur bord de liste est un clamp métier.

**`composables/`**

- **`usePopover(el)`** → `{ shown, syncShown, show, hide }`, plomberie d'état d'un `[popover]` (pendant JS de `floating.css`). Deux invariants : `shown` est alimentée **par le DOM** — câbler `syncShown` sur `@beforetoggle` ET `@toggle` du panneau (le premier est synchrone et capte le light dismiss, le second est le seul émis par le stub jsdom ; les ToggleEvent ne bubblent pas, donc toujours sur l'élément popover lui-même) — et **jamais posée à la main** ; les gardes d'idempotence évitent l'`InvalidStateError` de `hidePopover()` sur un popover déjà fermé. **Tous les popovers du DS y sont passés** : MenuPanel et Toaster directement, tous les autres via le composant `Popover` (Combobox, Tooltip, DatePicker, TimePicker). Idiome : **une instance par popover** quand un composant en pilote plusieurs (Toaster : une par placement, indexée dans une `Map`, chacune portant sa propre ref d'élément).
- **`useFieldPanel({ rootEl, panelRef, fieldEl, disabled, focusInPanel, onOpen?, onClose? })`** → `{ open, openPanel, closePanel, onControlClick, onFocusout, onKeydown, onPanelMousedown }`. Coquille « champ readonly + `Popover` en `mode="manual"` » de DatePicker et TimePicker. Le panneau est **écrit impérativement** (`panelRef.show()/hide()`) et **lu par modèle** (`open`, à brancher en `v-model:open` sur le Popover, qui l'alimente depuis le DOM) : l'écriture doit rester synchrone, le `rAF` qui déplace le focus supposant le panneau déjà ouvert quand il est armé. Un popover `manual` ne fait rien seul : ni light dismiss, ni déplacement du focus, ni retour du focus au champ. `onOpen`/`onClose` portent le propre de chaque composant (brouillon et étape du TimePicker, vidage de sa live region). Le `onKeydown` garde `!event.defaultPrevented` sur ArrowDown/Entrée : **une Entrée consommée dans le panneau vient de le fermer et le rouvrirait en remontant à la racine** (couvert par un test unitaire). **`onPanelMousedown` (à câbler en `@mousedown` sur le Popover)** annule le mousedown sur les zones NON interactives du panneau : cliquer un pixel non focusable (padding, gouttière entre cellules) rend le focus au `<body>`, le `focusout` de la racine part avec un `relatedTarget` nul et ferme un panneau sur lequel on vient de cliquer — au TimePicker, cela abandonnait le brouillon en cours. Le filtre (`closest('button, a, input, select, textarea, [tabindex]')`) est essentiel : le `preventDefault` inconditionnel du Combobox, dont le focus ne quitte jamais le champ, priverait ici les jours et les flèches de navigation de leur focus et désynchroniserait le roving du Calendar. **Invisible en jsdom** (pas de focus au clic) → play functions `ClicDansLeVide` des deux composants, vérifiées rouges sans le handler.
- **`useFocusoutDismiss(root, close)`** → handler `@focusout` de racine. Un popover reste un descendant DOM même peint en top layer, donc `contains` suffit ; `relatedTarget` nul = sortie aussi. Adoptants : Combobox, et DatePicker/TimePicker via `useFieldPanel`.
- **`useRootAttrs()`** → `{ attrs, rootClass, rootStyle, forwardedAttrs }`, plomberie du **pattern wrapper-root** (7 adoptants : Input, Textarea, Tabs, Combobox, DataTable, DatePicker, TimePicker). `defineOptions({ inheritAttrs: false })` reste dans le SFC (c'est une option de compilation). `rootClass` est typée `ClassBinding` (redéclarée localement : `@vue/runtime-dom` exporte `ClassValue`, le paquet `vue` ne la réexporte pas, et `unknown` est refusé par le template).
- **`useAriaLabel(() => props.label)`** → précédence `aria-labelledby` > `aria-label` > prop `label`. Indispensable dès qu'un composant en `inheritAttrs: false` rend à la fois `v-bind="forwardedAttrs"` et `:aria-label` (Tabs, Toggle) — sans arbitrage les deux s'appliquent. Ailleurs (Pagination, Breadcrumb, Toaster, InputOTP) le fallthrough Vue fait déjà gagner l'attribut du consommateur : le composable n'y retire que le défaut devenu redondant. Ne PAS l'appliquer à Icon/IconButton, où `label` est le nom accessible d'un contrôle icône seule.
- **`useTimer()`** → `{ start(fn, delay), cancel() }`, `setTimeout` réarmable annulé au démontage ; `delay ≤ 0` exécute **synchroniquement** (convention du DS : 0 désarme le report ; `setTimeout(…, 0)` ne serait pas synchrone). Adoptants : Tooltip (délai d'apparition), MenuItem (délai d'intention du survol — UNE instance, ouverture et fermeture s'excluant), Combobox et DataTable (leurs debounces, chacun gardant sa sémantique propre : dédoublonnage par terme d'un côté, commit vers un `ref` de l'autre). Toaster reste dehors : sa `Map<id, timeout>` est une autre structure.
- **`useFieldIds(attrs, hasHint)`**, **`useIconClickHandlers({ name, iconStartLabel, iconEndLabel })`**, **`useTextLimit({ el, text, maxlength, softLimit })`** — partagés par Input et Textarea. Respectivement : ids et agrégation d'`aria-describedby` (un `id` du consommateur PRIME sur le `useId()` interne) ; détection des listeners `@click:icon-*` dans `vnode.props` (les emits déclarés sont retirés de `$attrs`) avec le garde-fou a11y ; compteur, dépassement et limite souple par `setCustomValidity`.
- **`useProgressValue(value, max)`** → `{ clamped, fraction }` (ProgressLinear, ProgressCircular).

**Fusions à ne pas tenter** (analysées, sans corps réellement commun) : un IntersectionObserver partagé Tabs/Combobox ; la fusion de `utils/date.ts` et `utils/time.ts` ; une interface partagée pour `defineExpose({ …, el })` ; `onClear()` d'Input/Textarea.

## Tests : répartition stricte

- **vitest + jsdom** (`*.test.ts`) : logique uniquement — emits, v-model, attributs ARIA, fallthrough. jsdom ne couvre pas Popover/top-layer : la Popover API est stubbée globalement dans `vitest.setup.ts` (marqueur `data-popover-open` + display inline, car `:popover-open` n'est pas évaluable en jsdom et le style UA `[popover]{display:none}` cache le panneau aux requêtes par rôle ; `hidePopover` ferme aussi les descendants `[data-popover-open]` — cascade de pile nécessaire aux sous-menus). Ne pas tester le comportement navigateur en jsdom.
- **Play functions Storybook** (`storybook/test` : `expect`, `userEvent`, `within`, `waitFor`) : comportements navigateur réels (ouverture popover, Esc, `:user-invalid`…). Les mises à jour v-model étant asynchrones, toujours passer par `waitFor` après une interaction. Elles s'exécutent **localement dans Chromium** via `@storybook/addon-vitest` (`pnpm test:stories`) — plus besoin de brûler un build Chromatic pour les valider.
- `vitest.config.ts` déclare **deux projets** : `unit` (jsdom, `src/**/*.test.ts`) et `storybook` (browser mode Playwright, alimenté par `storybookTest({ configDir: '.storybook' })`). Deux pièges : un projet Vitest **n'hérite pas** des plugins de la racine — `vue()` doit être répété dans le projet `storybook`, sinon les `.vue` importés par les stories échouent en « invalid JS syntax » ; et depuis Storybook 10.3 le plugin applique **lui-même** les annotations de `preview.ts`, donc aucun fichier de setup à écrire (un `setProjectAnnotations` manuel serait signalé comme redondant).
- `globals: true` dans vitest.config.ts est **requis** pour le cleanup automatique de @testing-library/vue — ne pas le retirer (projet `unit`).
- L'`expect` de vitest n'a PAS les matchers jest-dom (`toBeVisible`, `toHaveFocus`…) : en jsdom, asserter sur les propriétés DOM (`el.hidden`, `document.activeElement`). Ces matchers n'existent que dans `storybook/test` (play functions).

## Storybook

Storybook 10, framework `@storybook/vue3-vite`. Imports : types depuis `@storybook/vue3-vite`, utilitaires de test depuis `storybook/test`, blocks MDX depuis `@storybook/addon-docs/blocks`. Addons : `addon-docs`, `addon-a11y` et `addon-vitest` (exécution des play functions, cf. Tests). Chromatic reste piloté en CLI (`pnpm chromatic`, jeton dans `chromatic.config.json`) — pas d'addon dans l'UI.

- `.storybook/preview.ts` : decorator global de thème (toolbar System/Light/Dark — System suit `prefers-color-scheme` avec écoute des changements OS — + direction LTR/RTL). **Piège vue3** : thème et direction sont appliqués en effets de bord sur `<html>` (`data-theme`, `dir`), PAS via l'état d'un wrapper templaté — le renderer vue3 ne remonte pas l'arbre au changement d'un global du toolbar (seuls les args sont réactifs), un état capturé dans `setup()` reste figé.
- La police Material Symbols (Icon) est chargée par Storybook via `.storybook/preview-head.html` (jamais embarquée dans la lib).
- Chaque story couvre : défaut, variantes, états (disabled/loading/error), cas limites (textes longs). `src/tokens/Tokens.mdx` est généré depuis la source TS — ne jamais y dupliquer des valeurs en dur.
- **Doc `X.mdx` obligatoire par composant** (à générer avec les stories, jamais après-coup) : `import { Canvas, Controls, Meta } from '@storybook/addon-docs/blocks'` + `import * as XStories from './X.stories'` + `<Meta of={XStories} />`. Structure type (cf. `AvatarGroup.mdx`) : titre `# X`, intro courte décrivant le composant, puis une section par aspect (`<Canvas of={XStories.MaStory} />`, un `<Controls>` sur la story principale), et une section **Accessibilité** finale. Prose seulement (le rendu vient des stories) — aucune valeur de token en dur.

Vite lib mode, **ESM uniquement**, `preserveModules` (un module par fichier source → tree-shaking par composant). Exports map : `.`, `./styles.css`, `./tokens` (module typé), `./tokens.json`. `sideEffects: ["**/*.css"]`. Les d.ts sortent de vite-plugin-dts sur `tsconfig.build.json` (qui exclut stories/tests).

## Pièges connus

- **TypeScript épinglé sur ^5.9** (racine et packages/ui) : ne pas laisser pnpm résoudre TS 7 (compilateur natif), vue-tsc/vite-plugin-dts ne le supportent pas.
- Nouvelle dépendance avec postinstall : pnpm 11 la bloque → l'ajouter sous `allowBuilds:` dans `pnpm-workspace.yaml` (esbuild y est déjà).
- Prettier est séparé d'ESLint : `pnpm lint` ne vérifie pas le format, lancer `pnpm format` aussi.
- ESLint : `no-undef` est désactivé pour `.ts`/`.vue` (faux positifs sur les globals DOM, TS couvre) ; `vue/multi-word-component-names` et `vue/no-reserved-component-names` désactivés (noms simples voulus : Button, Input, Menu…).
- `corepack enable pnpm` si `pnpm` introuvable dans un nouveau shell.

## Support navigateur

Popover API, `<dialog>`, `<details name>`, `:user-invalid`, `color-mix()`, `:has()` : Baseline, utilisables sans fallback. **CSS Anchor Positioning : utilisé SANS fallback** — cible navigateurs modernes uniquement (Chrome/Edge 125+, Safari 26+ ; Firefox non supporté tant qu'anchor positioning n'y est pas stable). Ne pas ajouter de fallback JS sans demande explicite. `@starting-style`/`allow-discrete` : progressive enhancement uniquement, jamais requis.

**Patterns d'ancrage** (`src/styles/floating.css` : `.ds-overlay` + `.ds-floating` + `data-placement` → `position-area`/`position-try-fallbacks`) :

- Panneau invoqué par `popovertarget` (Menu — sous-menus compris : l'item parent est l'invocateur du panneau imbriqué) : l'invocateur est l'**ancre implicite**, aucun `anchor-name` nécessaire.
- Panneau ouvert programmatiquement (Tooltip, et `Popover` quand un `#trigger` lui est fourni) : `anchor-name` **statique partagé** sur le wrapper + `anchor-scope` (même nom) qui le confine au sous-arbre du wrapper + `position-anchor` sur le panneau. Le confinement est indispensable : un popover affiché passe en top layer et est considéré comme « après » tout le document pour la résolution d'ancre — sans `anchor-scope`, tous les panneaux se rattacheraient au dernier wrapper nommé de la page. Pas d'ID unique, pas de style inline. `anchor-scope` : Chrome/Edge 131+, Safari 26+ (léger relèvement du plancher Chrome 125 assumé). Range vertical par `writing-mode` (Slider) : Chrome/Edge 129+, Safari 18.1+ (même logique de relèvement assumé).
- Placements alignés (`top-start`, `bottom-end`…) : la marge inline du côté aligné est annulée dans floating.css (`[data-placement$='-start']`/`[$='-end']`), sinon le `margin` d'écart décale le panneau du bord du trigger. Placements latéraux (sous-menus, `right-start`) : axe inversé, la marge inline est restaurée (l'écart est inline, l'alignement block).
- Panneau dont le consommateur possède déjà racine et contrôle (Combobox, DatePicker, TimePicker, et Tooltip qui garde son wrapper pour y attacher pointer/focus) : il pose lui-même `anchor-scope`/`anchor-name` et transmet le seul nom à `Popover` par la prop **`anchor`** (dashed-ident) → `position-anchor: var(--_anchor)`. C'est la voie obligée dès que le contrôle est un `<input>` texte, sur lequel `popovertarget` est invalide.
- Les triggers sont fournis par slots scopés : `#trigger="{ triggerProps }"` + `v-bind="triggerProps"` (popovertarget, aria-*). Tooltip suit le même pattern (slot default scopé) : c'est le consommateur qui pose `aria-describedby`, jamais un pont JS automatique au mount.
- **`.ds-overlay`** est le socle de tout popover du DS : `position: fixed; inset: auto` (neutralise les styles UA de `[popover]`) + le garde-fou `.ds-overlay:not(:popover-open) { display: none }`. Un panneau qui pose son propre `display` (`.ds-panel` en flex, la pile de toasts en colonne) écrase le `display: none` UA de `[popover]` (styles auteur > UA) et le panneau fermé resterait cliquable en `opacity: 0` par-dessus le contenu ; la spécificité (0,2,0) du garde-fou le met hors de portée d'un `display` de composant, quel que soit l'ordre du bundle. **La classe se pose sur les six panneaux ET sur les piles de toasts** (`.ds-toast-stack`, qui redéclarait ce bloc mot pour mot mais ne peut pas porter `.ds-floating` : coordonnées physiques, pas d'ancre, marge nulle). Les blocs de transition restent séparés (Toaster : opacité seule en `--ds-duration-base` ; `.ds-floating` : opacité + `transform` en `--ds-duration-fast`). Dialog reste dehors : `<dialog>` n'est pas un popover, `:popover-open` ne s'y applique pas — d'où son `.ds-dialog:not([open])` propre.

## Échelle de tailles (contrôles)

Échelle unifiée **xs/sm/md/lg/xl** (24/32/40/48/56px, tokens `--ds-control-height-xs…xl`). Le mapping taille → hauteur/font/icône/opsz/gap vit en UNE incarnation CSS : `src/styles/control-size.css`, classe **`.ds-control`** posée sur la racine porteuse de `data-size`/`data-compact`. Les blocs `[data-size]` ne définissent QUE des custom properties `--_control-*` (héritées jusqu'aux enfants, ex. le field d'Input — aucun conflit de spécificité) + le contexte Icon `--ds-icon-size`/`--ds-icon-opsz`.

- **Compact** = -4px de hauteur partout (`--_control-height` dérivée de `--_control-height-base`).
- Mappings (littéraux, contrat police maintenu — pas de nouveaux tokens) : icônes xs→16 / sm-md→20 / lg-xl→24 ; opsz xs-md→20, lg-xl→24 ; fonts xs→xs, sm-md→sm, lg-xl→md ; gap `--_control-gap` xs→4px, sm-md→8px, lg-xl→12px ; paddings = `--ds-space-*` directs.
- **L'échelle complète n'est pas exposée partout** : chaque composant restreint son union TS au sous-ensemble qui a du sens pour lui, `control-size.css` restant la table unique (ses blocs xs/xl servent toujours aux boutons). Il n'existe volontairement **aucun type `ControlSize` partagé** — les échelles diffèrent, un type unique serait faux.
- Adoptants et sous-ensembles : Button/IconButton/Pagination/Tabs/Toggle (**xs–xl**) ; **tout composant à champ de saisie → sm/md/lg** (32/40/48px, défaut md) : Input, Textarea, InputOTP (typo majorée d'un à deux crans), DatePicker, TimePicker, Combobox (qui propage sa taille telle quelle à son panneau) — `xs` (24px) est trop bas pour du texte saisissable et `xl` (56px) hors gabarit formulaire : ne pas les exposer ; Chip (xs/sm, défaut xs) ; Menu (sm/md/lg, défaut sm — `ds-control` sur le panneau, cf. puce suivante) ; AvatarGroup.
- **Les panneaux portent `ds-control` sur le PANNEAU, leurs rangées consomment** : le panneau, qui porte déjà `data-size`/`data-compact`, porte `ds-control` ; `.ds-menu-item`/`.ds-combobox-option`/`.ds-combobox-state` lisent les `--_control-*` hérités (hauteur, `--_control-padding-inline`, gap, font-size) et les icônes suivent sans une ligne de CSS. **Invariant** : un sous-panneau de Menu ne prend PAS la classe (`:class="{ 'ds-control': !submenu }"`) — `.ds-control` repose `--_control-height` depuis `--_control-height-base` **sans** la condition `[data-compact]`, qu'un sous-panneau ne porte pas : il perdrait le compact hérité. Même raison pour laquelle `panel.css` ne pose plus le contexte Icon. Seule exception à la table : la typo des rangées est composite (taille de l'échelle, leading `body-md` unitless, poids regular) — la recette `control` vaut medium/leading 1, or une rangée peut passer à la ligne et porter un sous-libellé.

## Composants

Inventaire (exportés depuis `src/index.ts` — l'ordre y fixe la cascade CSS) : **Icon, Typography, Popover, Button, IconButton, ButtonGroup, Pagination, Tabs** (+ Tab/TabPanel)**, Toggle** (+ ToggleItem)**, Input, Textarea, Checkbox, Radio, Switch, Tooltip, Menu** (+ MenuItem/MenuGroup/MenuSeparator)**, Accordion** (+ AccordionItem)**, Toaster** (+ `toast()`/`dismissToast`)**, Badge, Avatar, Spinner, Combobox, Breadcrumb, Chip, DataTable, InputOTP, ProgressLinear, ProgressCircular, Slider, Dialog** (+ DialogAlert)**, Calendar, DatePicker, TimePicker**. Typography doit rester en tête (avant tout composant qui le rend en interne : Input, Textarea, Dialog, Accordion, DataTable — leurs classes surchargent `.ds-typography` à spécificité égale) ; **Popover aussi**, pour la même raison (Tooltip, Combobox, DatePicker, TimePicker posent leur classe de panneau sur le MÊME élément que `.ds-popover-panel`).

La Popover API native est utilisée par Popover (donc Combobox/Tooltip/DatePicker/TimePicker), Menu et Toast.

**Composants internes non exportés** (pas de story ni de `.mdx` — leur doc vit chez leur consommateur) : `Menu/MenuPanel.vue`, `Combobox/ComboboxOption.vue`, `Combobox/ComboboxGroup.vue`, `Combobox/ComboboxSeparator.vue`, `Toast/Toast.vue`, `TimePicker/TimePickerDial.vue`.

**Menu et la liste du Combobox restent deux choses distinctes** : **Menu** est un composant public qui porte tout le pattern ARIA menu (roving focus, sous-menus, pile de popovers) ; la liste du Combobox est un panneau `role="listbox"` **sans aucune autonomie**, rendu par le Combobox lui-même et piloté depuis le champ. Ne pas les refondre en un panneau unique paramétré par une prop `role` : ils ne partagent que le chrome (`.ds-panel`) et la plomberie (`Popover`), ce qui est déjà mutualisé. Il a existé un composant interne `Listbox` : vidé de sa substance par `Popover`, il n'avait plus qu'un consommateur et a été rapatrié dans Combobox.

**`Popover` est la brique commune de la PLOMBERIE des panneaux** (élément `[popover]` et son mode, pont d'état DOM ↔ `v-model:open`, ancrage, placement, surface optionnelle) — jamais du rôle ARIA, du clavier, du focus ni de la politique de fermeture, qui restent chez chaque composant. Adoptants : Combobox, Tooltip, DatePicker, TimePicker. **Menu et Toaster restent dehors, délibérément** : Menu est le seul `popover="auto"` (light dismiss natif, ancre implicite par `popovertarget`, sous-menus ouverts par `showPopover({ source })` formant une pile native) — l'y faire passer imposerait une 3e stratégie d'ancrage et un 2d mode pour un gain nul ; Toaster n'a aucune ancre (coordonnées physiques, six piles permanentes) et ne porte déjà pas `.ds-floating`.

Règles transverses déjà couvertes plus haut : tone/variant (Button = référence), pattern wrapper-root, échelle de tailles, disabled **gris par tokens** (jamais `opacity` — sauf `loading` qui garde `opacity: 0.5`).

### Caractéristiques par composant

- **Icon** : 3 sources — ligature Material Symbols Rounded / image / SVG inline. La police est chargée par le **consommateur** (jamais embarquée). Pilotage contextuel `--ds-icon-size`/`--ds-icon-opsz` ; la prop `size` explicite prime. Helper `Icon/iconProps.ts` : distingue nom Material vs URL par regex `[./:]` (un nom Material n'en contient jamais) — réutilisé partout où une prop accepte « nom OU URL ».
- **Typography** : élément de texte — `variant` (13 rôles, cf. tokens typo sémantiques) + `tone` (default = héritage, muted/subtle/accent/danger/success/warning/on-inverse) + `as` (balise libre ; défauts h1…h4/p/span/code par variante) + `truncate`. Aucune marge (l'espacement appartient au layout parent), aucun JS hors dérivation de balise ; racine unique → fallthrough natif (`as="label"` + `for` = vrai label de champ). Le bloc de base re-pose `--_family`/`--_tracking` sur chaque instance (coupe l'héritage des `--_*` d'un Typography ancêtre). Rendu en interne par Dialog (titre/sous-titre), Input/Textarea (label/hint), AccordionItem (sous-titre), DataTable (titre) — leurs classes propres (`.ds-dialog-title`…) restent posées comme points d'accroche. Les compteurs Input/Textarea restent locaux (tabular-nums + data-over ≠ rôle typo). Story « toutes les variantes » en `as="p"` (hiérarchie de titres de la page docs).
- **Popover** : panneau flottant générique et brique de plomberie (cf. ci-dessus). Deux modes d'ancrage exclusifs : slot **`#trigger`** (standalone) → wrapper `.ds-popover` en `inline-block` portant `anchor-name`/`anchor-scope: --ds-popover-anchor` (nom statique partagé, confiné par instance) + `triggerProps` (`popovertarget`/`aria-expanded`/`aria-controls`, pattern **disclosure** : ni rôle ni `aria-haspopup` imposés) ; prop **`anchor`** (brique interne) → aucun wrapper de layout, `display: contents` — un `inline-block` vide créerait une line box, donc de la hauteur, chez tous les consommateurs. Une seule déclaration couvre les deux : `position-anchor: var(--_anchor, --ds-popover-anchor)`. `mode` auto (défaut, light dismiss natif) / manual. `surface` (défaut true) pose `.ds-panel`. `v-model:open` **bidirectionnel** (alimenté par le DOM via `usePopover`) ET `defineExpose({ show, hide, el })` : l'expose est ce qu'utilisent Tooltip et `useFieldPanel`, dont l'ouverture doit être **synchrone** (le modèle intercalerait un tick, et le délai 0 de `useTimer` comme le `rAF` de focus perdraient leur sens). `inheritAttrs: false` + `v-bind="$attrs"` sur le **panneau**, class/style comprises — variante assumée du pattern wrapper-root (le sujet visuel est le panneau, pas le wrapper d'ancrage), donc pas de `useRootAttrs`. **Le CSS ne porte AUCUNE dimension** : `min/max-inline-size`, `max-block-size` et `overflow` varient d'un consommateur à l'autre et seraient arbitrés par l'ordre du bundle à spécificité égale.
- **Button** : modèle tone/variant de référence. Variants dont `elevated`/`tonal`, tones `success`/`warning` (token `text-on-warning` = neutral-950, le blanc échoue AA sur amber). `iconStart`/`iconEnd` (fallback slots #start/#end). Rendu `<a>` via `href` (lien inerte si disabled/loading : href retiré + aria-disabled + onClick filtré — seul JS, `inheritAttrs: false`). `compact` = -4px.
- **IconButton** : carré, largeur = `var(--_control-height)` posée par Button.
- **ButtonGroup** : wrapper `role="group"` qui rattache des Button/IconButton en contrôle segmenté (bordures fusionnées `margin: -1px`, coins arrondis aux seules extrémités via propriétés logiques `border-*-*-radius`, couture `--ds-color-border` entre segments pleins, `z-index` au hover/focus/active). CSS-only (aucun provide/inject) : chaque bouton garde ses props ; poser les mêmes variant/tone/size sur les enfants pour la cohérence. `orientation` horizontal (défaut) / vertical. Exporté après IconButton (surcharge `.ds-button-group > .ds-button`).
- **Pagination** : **composée** — chaque pastille est un `Button` (page active toujours `solid` + `aria-current="page"` ; inactives `ghost`/`outline` en `tone="neutral"`), les contrôles un `Button`/`IconButton` (`controlsDisplay` icon/text/both, `prevIcon`/`nextIcon` via `iconProps`), `attached` rattache tout dans un **ButtonGroup**. **Pas de `<ul>`/`<li>`** : ButtonGroup ne stylise que ses enfants directs — d'où aussi l'ellipse rendue en `IconButton` disabled `more_horiz` (reste un `.ds-button`, couture continue) plutôt qu'en `<span>`. Aucune règle d'état redéfinie (tout vient de Button) ; `size`/`compact` propagés à tous les enfants ; `.ds-pagination-page` surcharge `min-inline-size: var(--_control-height)` (modèle IconButton) → **export après ButtonGroup dans `index.ts`**. **Double troncature** : (1) logique — `length` (défaut 1) fixe le nombre de pages, toutes rendues par défaut ; `totalVisible` = nombre total d'**emplacements** rendus, ellipses comprises (clampé à un minimum de 5), première/dernière toujours conservées, fenêtre centrée sur la courante qui se **décale** aux extrémités au lieu de rétrécir (largeur de barre constante), pure dérivation ; (2) responsive — **100 % CSS**, la nav est son propre conteneur de requête (`container-type: inline-size` + `container-name`), 3 paliers `@container` (36/31/25rem) masquent en `display: none` les voisines par `data-distance` décroissant (plafonné à 3), les bornes (`data-edge`) et la courante n'en portant pas ne sont jamais masquées ; le palier médian replie aussi un contrôle `both` en icône seule (il coûte ~4× une pastille). Chaque seuil est la largeur **nécessaire pour afficher** le niveau, pas celle qui reste après masquage — sinon la rangée déborde pendant tout l'intervalle. Le confinement est **réservé au mode responsive** (`.ds-pagination[data-responsive]`) : toutes les `@container` en dépendent, et hors responsive (le défaut) la nav retrouve une largeur intrinsèque — donc pas de `flex: 1` à prévoir chez le parent (cf. footer DataTable). Conséquence assumée quand il s'applique : la nav est **block-level** (une `inline-flex` se réduirait à zéro), d'où la prop `align`. Seuils en littéraux rem (pas de `var()` en `@container`, précédent DataTable), calibrés sur `md` ; échappatoire `totalVisible` / `responsive: false`. Aucune ellipse ajoutée en compensation d'une voisine masquée (même largeur qu'une pastille, gain nul). `disabledPages` : liste **ou** prédicat (convention `disabledDates` de Calendar) ; les contrôles **enjambent** les pages désactivées et se désactivent quand il n'en reste aucune (couvre les butées sans test séparé). Seul JS de comportement : le clavier flèches/Home/End sur la nav, délégué à `utils/arrowNav` — dont le filtre `display` écarte les pastilles masquées par les container queries.
- **Tabs** (+ **Tab**, **TabPanel**) : **composé** — chaque onglet est un `Button` (actif = `elevated` en variante `inset`, sinon `ghost` ; `tone` du contexte à l'actif, `neutral` aux inactifs), les contrôles de défilement des `IconButton`. Aucune règle d'état redéfinie. API **composée** avec deux slots : `#default` (les `Tab`, dans le `role="tablist"`) et `#panels` (les `TabPanel`) — un slot unique ne permettrait pas de les répartir dans deux conteneurs DOM ; `#panels` absent = simple barre / contrôle segmenté. Contexte `Tabs/context.ts` (getters, modèle Accordion) portant `value`/`select`/`tabId`/`panelId`/`hasPanels`/`variant`/`tone`/`size`/`compact`/`activation` — `size`/`compact` y transitent (et non par héritage CSS : chaque Button pose son propre `ds-control[data-size]`). Ids dérivés d'un `useId()` unique + **assainis** (`aria-controls` est une liste d'IDREF séparée par des espaces) ; `hasPanels` = getter sur `slots.panels !== undefined`, **déterministe SSR/client** donc pas de registre réactif ni de mismatch d'hydratation (contrepartie : `#panels` doit être statiquement présent ou absent). Racine en **pattern wrapper-root** (`inheritAttrs: false`, class/style sur la racine, tout le reste sur la tablist). Variantes : `line` (défaut ; piste `border-block-end` portée par `.ds-tabs-bar` — pas par le scroller, sinon elle s'arrête avant les boutons de défilement et l'indicateur ne peut pas la recouvrir — + `margin-block-end: -1px` sur la liste, idiome ButtonGroup ; indicateur `::after` en `currentColor`, qui suit le tone ET le gris disabled, token dédié `--ds-control-size-tab-indicator`) et `inset` (piste creuse `surface-sunken` sur le scroller lui-même, pour que son padding protège l'ombre de l'onglet `elevated` ; rayon emboîté en `calc()`). `orientation` vertical : racine en `row` (panneaux à côté), piste en `border-inline-start`, indicateur au bord de départ. `align` posé sur la **barre** et non sur la liste (un `justify-content` sur un conteneur qui déborde rendrait la partie dépassant du côté start inatteignable) — donc no-op en vertical sans hauteur. `grow` = `flex: 1 1 0` sur les onglets (libellé enveloppé dans `.ds-tab-label`, `text-overflow` ne s'appliquant pas au texte anonyme d'un flex) ; incompatible par construction avec le défilement. Défilement : liste `overflow: auto` + `scrollbar-width: none` + `scroll-behavior: smooth` (donc `scrollBy` **sans** `behavior`, qui ne respecte pas reduced-motion). `scrollButtons` opt-in ; **butées mesurées par deux sentinelles `IntersectionObserver`** (un seul observateur pour scroll + resize + ajout d'onglets, là où un ResizeObserver serait un second mécanisme et le premier du repo ; défauts `true` = boutons désactivés en SSR/jsdom ; `::scroll-button()` visé plus tard, hors plancher Safari). Toutes les surcharges de Button qualifiées **`.ds-tab[data-size]`** (modèle IconButton) → l'ordre dans `index.ts` n'est pas contraignant. Anneau de focus **intérieur** (`outline-offset` négatif) : le scroller rognerait un décalage positif. Panneaux : `hidden` natif (état du contenu préservé ; champs toujours soumis) + prop `lazy` ; garde-fou `.ds-tabs-panel[hidden] { display: none }` **sans `!important`** (le style UA est écrasé par toute déclaration `display` d'auteur). JS de comportement : roving tabindex + flèches/Home/End via `utils/arrowNav`, qui **déplace le focus sans activer** (`activation: 'manual'` par défaut ; `'automatic'` = sélection au focus, posée dans `Tab.@focus` pour ne pas faire transiter la valeur par le DOM) ; recadrage de l'onglet actif par `scrollBy` **borné à la liste** (`scrollIntoView` remonterait tous les ancêtres défilants). Onglet `disabled` = `<button disabled>` (sauté par les flèches, comme les pages de Pagination). Contrat : le `v-model` doit référencer un onglet existant et activable, sinon aucun onglet n'a `tabindex="0"`.
- **Toggle** (+ **ToggleItem**) : **composé** — groupe de boutons sélectionnables via un seul v-model ; chaque item est un `Button` (sélectionné = toujours `solid` au `tone` du groupe ; non sélectionnés `ghost`/`outline` via prop `variant`, en `tone="neutral"` — modèle Pagination), `attached` (défaut **true**) rattache le tout dans un **ButtonGroup** (le Button est la **racine** de ToggleItem : enfant direct exigé par la couture `> .ds-button`), sinon div + gap. Aucune règle d'état redéfinie. Contexte `Toggle/context.ts` (getters, modèle Tabs) : `isSelected` (et non un getter `value` brut : en `multiple` la comparaison vit côté racine)/`select`/`variant`/`tone`/`size`/`compact`/`disabled`/`selectedIconFilled` — pas d'ids/`useId` (aucun aria-controls) ni de registre → SSR trivial. v-model : `string|number|null` en simple (re-clic = désélection), tableau en `multiple` (jamais muté en place ; null/scalaire normalisé en `[]`) ; `mandatory` = pure **garde à la désélection** de la dernière valeur (ne force aucune sélection initiale, ≠ Vuetify `force`). `selectedIconFilled` (groupe) : l'icône de l'item sélectionné passe en FILL 1 — `filled` posé **directement sur Icon** dans le slot `#start` (la prop `iconFilled` de Button est sans effet sur les slots) ; inerte sur une icône URL. ARIA : `role="group"` nommé (prop `label`, précédence aria-labelledby > aria-label > label reprise de Tabs) + **`aria-pressed` toujours posé** même à 'false' (couvre simple ET multiple sans bifurcation ; pas de radiogroup, qui imposerait roving + ARIA conditionnel). Clavier via `utils/arrowNav` (pas de roving : chaque item visible est un arrêt de tabulation ; les disabled sont sautés) ; `event.currentTarget` au lieu d'une ref template (sur `<component :is>` elle serait tantôt élément, tantôt instance). `orientation`/`data-orientation` bindés **en miroir** selon `attached` (ButtonGroup pose data-orientation depuis sa prop ; le div détaché reçoit l'attribut). Surcharges qualifiées (`.ds-toggle-item[data-size]` icône seule carrée ; `.ds-toggle:not(.ds-button-group)` — indispensable : en attached la racine porte les deux classes, `align-items` entrerait sinon en conflit d'ordre avec ButtonGroup) → ordre d'export libre.
- **Input / Textarea** : wrappers (label + field + hint/meta), contrôle natif = `.ds-*-control` (wrapper-root). `label`, `hint`, `iconStart`/`iconEnd` (+ slots ; icône cliquable → `<button>`, détection `@click:icon-*` dans vnode.props, libellé via `icon*Label`), `counter`, `maxlength` + `softLimit` (dépassement via `setCustomValidity` → `:user-invalid`, jamais d'event maison), `loading`, `clearable`, `readonly` (fond sunken). Focus « bordure 2px » = bordure 1px + `box-shadow 0 0 0 1px` sur le field (`:focus-within`), rouge si invalide. Textarea auto-grow via `field-sizing: content` (porté par le field) ; regex `pattern` : Input seulement (attribut natif), pas d'émulation Textarea. **v-model d'Input = `string | number`** (Textarea reste `string`) : sur `type="number"`, Vue caste d'office la valeur en nombre (`vModelText` dès que `el.type === 'number'`), un modèle typé string seul renvoyait donc un nombre au consommateur qui le repassait en prop → « Invalid prop » en dev. Toutes les mesures de longueur (compteur, `softLimit`, visibilité de la croix) passent par la projection `modelText` — un nombre n'a pas de `.length`. Corollaire côté Slider : ses champs sont typés `string | number` (une saisie vide ou intermédiaire reste une chaîne) et le commit fait `Number.parseFloat(String(raw))`, `parseFloat` rendant NaN sur chaîne vide là où `Number('')` vaudrait 0.
- **Checkbox / Radio / Switch** : wrapper-root `<label>`, input masqué `opacity: 0`. Checkbox `indeterminate` via `watchEffect({ flush: 'post' })`. Radio = groupe natif par `name`. Switch `role="switch"`, taille unique 40×20px (tokens `--ds-control-size-switch-w/h`, pas de prop `size`), `labelPosition` start/end + `spread`.
- **Tooltip** : `Popover` en `mode="manual"` + délai. Ancrage par `anchor-name` statique partagé + `anchor-scope` (cf. Patterns d'ancrage) : le wrapper reste chez Tooltip (il porte pointerenter/leave/focusin/focusout/keydown) et le nom passe en prop `anchor` — le `#trigger` de Popover n'est PAS utilisé, un déclencheur d'infobulle n'étant pas un invocateur `popovertarget` (il serait basculé au clic) mais un élément **décrit** par le panneau. Popover est piloté impérativement (`show`/`hide`, pas de `v-model`) : le focus clavier doit ouvrir synchronement, et le tooltip ne publie aucun état. Trigger en slot scopé, `aria-describedby` posé explicitement par le consommateur.
- **Menu** (+ MenuItem/MenuGroup/MenuSeparator) : menu d'actions ARIA (`role="menu"`/`menuitem`), Popover API + ancre implicite. Panneau interne partagé `MenuPanel.vue` (racine + sous-menus), roving focus **confiné au panneau courant** (`closest('[role="menu"]') === panel` — les keydown des sous-panneaux bubblent) : le déplacement lui-même passe par `utils/arrowNav`, mais sur la liste PROPRE au panneau (elle exclut aussi les `aria-disabled`). Sous-menus récursifs via slot `#submenu` : le sous-panneau est rendu **frère de l'item, dans le panneau parent** → pile native de popovers (light dismiss total, branche sœur fermée, cascade). **Piège** : les ouvertures programmatiques (clavier, survol) DOIVENT passer `showPopover({ source: item })` (cast `PopoverWithSource` dans `usePopover`, option absente de lib.dom TS 5.9) sinon le panneau n'a pas d'ancre implicite. Délai d'intention survol 150 ms (`SUBMENU_HOVER_DELAY`, via `useTimer`). Ordre des champs, séparateur et gabarit du placeholder sont **dérivés de la locale** par les helpers purs de `utils/date.ts` (`dateMaskFor`/`formatDateMask`/`isoToMask`/`parseDateMask`/`caretAfterDigits`/`maskPlaceholder`) — `formatToParts` y force `calendar: 'gregory'` + `numberingSystem: 'latn'` (sinon fa-IR renvoie une année persane, ar-EG des chiffres arabes-indiens) et le séparateur est pris **entre deux champs** puis nettoyé de ses marques bidi (hu-HU formate « 2021. 11. 22. »). `displayFormat` n'a pas cours en saisie (warn dev) ; commit dès que la date est complète ET acceptable (bornes + `disabledDates`), **revert silencieux** au `change`/`blur` sinon ; année à 2 chiffres étendue au blur seulement (pivot FIXE 2000 — un pivot glissant rendrait les helpers impurs). Trois pièges, chacun verrouillé par un test qui rougit sans son correctif : (1) **`v-model` et non `:model-value` sur l'Input** — sans écouteur `onUpdate:modelValue`, `useModel` recopie en interne le texte BRUT tapé et le réécrit au patch suivant, effaçant le masque dès qu'il ne change pas lui-même (9e chiffre, caractère refusé) ; (2) **verrou de refocus** — le `focus()` rendu au champ par `closePanel(true)` rouvrirait le panneau, qui s'ouvre AU FOCUS : toute fermeture avec refocus passe par `closeAndFocus()` ; (3) **`endIconLabel` toujours défini** même sans icône rendue — `useIconClickHandlers` avertit AU SETUP dès qu'un `@click:icon-end` est attaché sans libellé, sans savoir si une icône existe. `useFieldPanel` gagne pour l'occasion `focusOnOpen` (ouvrir sans happer le curseur ; TimePicker inchangé).
  **`showCalendar`** (booléen, défaut **false**) : en saisie le calendrier est **opt-in** — sans lui, ni icône, ni panneau monté, ni raccourci d'ouverture (un popover à chaque focus est du bruit dans un formulaire dense) ; la croix de `clearable` reste, elle. Sans effet en lecture seule, où le calendrier est le seul chemin. Point de coupure **unique** : `disabled: () => props.disabled || !hasPanel.value` passé à `useFieldPanel`, dont `disabled()` garde à la fois `openPanel` et `onControlClick` — donc clic, focus, ArrowDown, Entrée et icône deviennent inertes d'une ligne, sans garde répétée dans chaque handler. `aria-haspopup`/`-expanded`/`-controls` disparaissent avec le panneau (un `aria-controls` orphelin sinon).
- **TimePicker** : même coquille que le DatePicker, partagée via `composables/useFieldPanel` (champ `Input` + `Popover` en `mode="manual"` ancré `--ds-timepicker-anchor`, focusout + Échap ; brouillon et live region par les crochets `onOpen`/`onClose`) ; v-model `'HH:mm' | null` **24 h canonique** quel que soit l'affichage. **Trois modes de CHAMP, prop `mode`** (BREAKING : `TimePickerMode` valait `'dial' | 'input'`, d'où le repli runtime sur `readonly` + warn citant l'ancienne API) : `readonly` (défaut, comportement historique — le cadran est le seul chemin, `showDial` y est **forcé**), `input` (champ masqué, cadran optionnel) et `list`. **`showDial`** (défaut `undefined`, PAS `false` : c'est ce qui distingue « non fournie » d'un `false` explicite et évite d'avertir la configuration par défaut) suit `showCalendar` du DatePicker — ignoré en `list` + warn. Même point de coupure unique : `disabled: () => props.disabled || !hasPanel.value`.
  **Cadran** (brouillon commité par OK seulement ; Annuler/Échap/focusout abandonnent) : **`role="slider"` unique** (flèches ±1 h / ±`minuteStep` min, PageUp/Down ±5, Entrée arrête l'étape heure → minutes → commit), chiffres `aria-hidden` positionnés par **`sin()`/`cos()` CSS** sur fraction de tour inline `--_turn` (idiome `--_f` Slider), aiguille en `rotate` **sans transition** (le wrap 55→0 min interpolerait par le grand tour), `left`/`top` **physiques délibérés** (une horloge ne se miroite jamais en RTL ; le groupe HH:MM force `direction: ltr`), 24 h = double anneau extérieur 12,1–11 / intérieur 00,13–23, géométrie pointeur **pure dans `utils/time.ts`** (`angleToIndex`/`DIAL_INNER_THRESHOLD` couplé aux tokens du cadran, testable — jsdom ne mesure rien ; ne toucher ni au seuil ni aux tokens sans l'autre), `setPointerCapture` sous try/catch, `touch-action: none`. Les deux grosses cellules HH/MM sont des **`Button` `size="lg"` `variant="tonal"`** dont le `tone` passe neutral → accent selon l'étape : `--_bg-soft`/`--_text-tinted` reproduisent EXACTEMENT l'ancien couple surface-muted/text ↔ accent-surface/accent-text, la surcharge locale se limitant au gabarit « grand chiffre » (`[data-size]`, modèle IconButton/Tabs). Le focus du panneau vise le slider par **requête DOM** (`TimePickerDial` n'a aucun `defineExpose` et n'a pas à en gagner un). Pas de caption, pas de bascule de mode dans le pied.
  **Saisie** : décalque du DatePicker `entry="input"` (masque, caret, revert silencieux, verrou `refocusing`, `v-model` obligatoire sur l'Input, `endIconLabel` toujours défini) — mais le séparateur `:` est **universel**, d'où une forme CLOSE (`timeCaret`) au lieu du `caretAfterDigits` balayant de `date.ts`.
  **Liste** : `Popover` en `surface` + `.ds-timepicker-list ds-control` + `role="listbox"`, rangées `<button role="option" tabindex="-1">` locales (surtout pas `ComboboxOption`, interne à Combobox), **focus DOM dans le panneau** (modèle Menu/Calendar, pas `aria-activedescendant`) → `utils/arrowNav` adoptable, avec liste PROPRE et non `navigableItems` (qui appelle `getComputedStyle` par élément — inacceptable sur des dizaines de rangées). Défilement à l'ouverture par `scrollIntoView?.({block:'center'})` + `focus({preventScroll:true})`. **Commit direct + fermeture** (ni brouillon ni pied) ; piège : l'Entrée doit faire `preventDefault` ET commiter explicitement, sinon le clic natif du `<button>` ferme puis la racine rouvre (la garde `defaultPrevented` de `useFieldPanel` ne jouerait pas) — couvert par un test qui rougit sans lui.
  Format 12 h/24 h dérivé de la locale (`resolvedOptions().hourCycle`), surchargeable par `format` ; **AM/PM = `Toggle mandatory` posé À CÔTÉ DU CHAMP** (hors du popover, donc utile aux trois modes) qui écrit le v-model — et non plus le brouillon ; sans valeur le choix est mémorisé dans `pendingMeridiem` ('AM' en dur : déterministe donc SSR-safe), et cadran ouvert le brouillon est resynchronisé sinon OK réécrirait l'ancien méridien. Son alignement sur le CHAMP (et non sur le bloc Input, qui empile label/champ/hint) passe par une compensation en marges dérivées des tokens de typo sous `:has(.ds-input-label)` / `:has(.ds-input-hint)`. Étape annoncée par live region polie. Icône fin `close` ↔ `expand_more` (liste, convention Combobox) ↔ `schedule` ↔ **`undefined`** (saisie sans cadran). Tokens `--ds-control-size-timepicker-*` (le `-cell-h` est mort : la hauteur vient de `--_control-height`) ; `TimePickerDial.vue` interne non exporté.
