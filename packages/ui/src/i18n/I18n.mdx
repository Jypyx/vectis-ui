# Internationalization

No user-facing text is hardcoded in the components: it all comes from a dictionary. The design
system is **English by default** and ships French; any other language is added on the consumer
side.

Two things are settled separately, and that is deliberate:

- the **words** (button labels, accessible names, empty states) come from the dictionary;
- the **formats** (month and day names, date field order, 12/24 h cycle, first day of the week)
  are derived from `Intl` using the locale tag — they are never translated by hand.

Consequence: setting a locale with no matching dictionary already yields correct dates and
times, with the labels left in English. That is a coherent degraded state, not a bug.

## Switching the design system to French

`setLocale` and `registerMessages` are **global configuration**: call them at module level
(`main.ts`, a Nuxt plugin), never inside a `setup()`.

```ts
// main.ts, or plugins/vectis.ts in Nuxt
import { fr, registerMessages, setLocale } from '@vectis/ui'

registerMessages('fr', fr)
setLocale('fr-FR')
```

French is **opt-in**: it only enters your bundle if you import it. An English-speaking project
therefore pays nothing for it.

Pass a **complete** BCP 47 tag. `Intl` accepts `'fr'`, but applies the language's default
conventions to it — a bare tag will not give you the regional settings of `'fr-CA'`.

## Adjusting a few words

An override is **partial**: whatever you do not write stays unchanged. Successive calls on the
same language accumulate.

```ts
import { registerMessages } from '@vectis/ui'

registerMessages('en', {
  dataTable: { empty: 'Nothing to show' },
  common: { close: 'Dismiss' },
})
```

## Adding a language that is not shipped

This is exactly the same gesture as enabling French — there are no two categories of
dictionary. Whatever you do not write falls back to English, never to an empty string: a
partial dictionary is usable from its very first key.

```ts
import { registerMessages, setLocale, type VectisMessagesInput } from '@vectis/ui'

const de: VectisMessagesInput = {
  common: { loading: 'Wird geladen…', close: 'Schließen' },
  pagination: { previous: 'Vorherige Seite', next: 'Nächste Seite', page: (p) => `Seite ${p}` },
}

registerMessages('de', de)
setLocale('de-DE')
```

Type the constant as `VectisMessagesInput` to get key autocompletion and signature checking. To
make the compiler demand **total** coverage, type it `VectisMessages`: it will then reject any
missing key.

The dictionary is indexed by **language subtag**: `registerMessages('de', …)` covers `de-DE`,
`de-AT` and `de-CH`, which share their words. What distinguishes them comes from `Intl`.

Below, `setLocale('de-DE')` WITHOUT a German dictionary: the months and the first day of the
week are already German (they come from `Intl`), while the labels stay English.

## Parameterized messages

An entry that depends on a value is a **TypeScript function**, not a string with placeholders.
So there is no plural engine and no ICU syntax to learn: each language writes its own rule, and
the typing of the arguments is the contract.

```ts
registerMessages('fr', {
  dataTable: {
    selection: (count) =>
      `${count} élément${count > 1 ? 's' : ''} sélectionné${count > 1 ? 's' : ''}`,
    range: ({ start, end, total }) => `${start}–${end} sur ${total}`,
  },
})
```

## Precedence

A text prop set on a component stays **authoritative** over the dictionary: a global
translation only changes the defaults. For the accessible names of containers, the full chain
is:

`aria-labelledby` › `aria-label` › `label` prop › dictionary › English

## Dates and times

`VCalendar`, `VDatePicker` and `VTimePicker` keep their `locale` prop, which stays
authoritative. Without it, they follow the global locale — one setting for the whole
application, with the option of forcing a calendar case by case.

```jsx
<VDatePicker />                  {/* global locale */}
<VDatePicker locale="ja-JP" />   {/* forced */}
```

## Known limit: one locale per process

The configuration lives at module level, like the icon configuration. That is correct for
configuration, but it means **one locale per process**: a server-rendered site serving `/en` and
`/fr` from the same Node process cannot rely on it to vary the language per request — it must
pass the text props explicitly.

Beware of client-only too: a `setLocale` placed in a `plugins/*.client.ts` makes the server and
client renders diverge, hence a hydration mismatch.

## What is not translatable

Deliberately outside the dictionary:

- whatever `Intl` already derives from the locale tag (month and day names, date field order,
  date separator, hour cycle);
- whatever is made only of digits and universal punctuation: VBadge's `99+`, VAvatarGroup's
  `+N`, the `N/M` counter of the fields, the `:` of a time. These components expose a slot when
  a rephrasing is needed;
- **developer** messages (`[Component] …`), which address the integrator.
