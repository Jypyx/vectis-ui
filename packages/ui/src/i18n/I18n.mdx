# Internationalisation

Aucun texte utilisateur n'est en dur dans les composants : tout vient d'un dictionnaire.
Le design system est **français par défaut** et fournit l'anglais ; toute autre langue
s'ajoute côté consommateur.

Deux choses se règlent séparément, et c'est volontaire :

- les **mots** (libellés de boutons, noms accessibles, états vides) viennent du dictionnaire ;
- les **formats** (noms de mois et de jours, ordre des champs de date, cycle horaire 12/24 h,
  premier jour de la semaine) sont dérivés d'`Intl` à partir de la balise de locale — ils ne
  sont jamais traduits à la main.

Conséquence : poser une locale sans dictionnaire correspondant donne déjà des dates et des
heures correctes, avec des libellés restés en français. C'est un état dégradé cohérent, pas
un bug.

## Passer le design system en anglais

`setLocale` et `registerMessages` sont de la **configuration globale** : à appeler au niveau
module (`main.ts`, un plugin Nuxt), jamais dans un `setup()`.

```ts
// main.ts, ou plugins/vectis.ts en Nuxt
import { en, registerMessages, setLocale } from '@vectis/ui'

registerMessages('en', en)
setLocale('en-GB')
```

L'anglais est **opt-in** : il n'entre dans votre bundle que si vous l'importez. Un projet
francophone ne paie donc rien pour lui.

Posez une balise BCP 47 **complète**. `Intl` accepte `'en'`, mais lui applique les conventions
par défaut de la langue — `'en'` signifie 12 h et semaine commençant le dimanche, ce qui n'est
pas `'en-GB'`.

## Ajuster quelques mots

Une surcharge est **partielle** : ce que vous n'écrivez pas reste inchangé. Les appels
successifs sur une même langue se cumulent.

```ts
import { registerMessages } from '@vectis/ui'

registerMessages('fr', {
  dataTable: { empty: 'Rien à afficher' },
  common: { close: 'Quitter' },
})
```

## Ajouter une langue non fournie

C'est exactement le même geste que d'activer l'anglais — il n'y a pas deux catégories de
dictionnaires. Ce que vous n'écrivez pas retombe sur le français, jamais sur une chaîne vide :
un dictionnaire partiel est utilisable dès la première clé.

```ts
import { registerMessages, setLocale, type DsMessagesInput } from '@vectis/ui'

const de: DsMessagesInput = {
  common: { loading: 'Wird geladen…', close: 'Schließen' },
  pagination: { previous: 'Vorherige Seite', next: 'Nächste Seite', page: (p) => `Seite ${p}` },
}

registerMessages('de', de)
setLocale('de-DE')
```

Typez la constante `DsMessagesInput` pour obtenir l'autocomplétion des clés et le contrôle des
signatures. Pour exiger du compilateur une couverture **totale**, typez-la `DsMessages` :
il refusera alors toute clé manquante.

Le dictionnaire est indexé par **sous-balise de langue** : `registerMessages('de', …)` couvre
`de-DE`, `de-AT` et `de-CH`, qui partagent leurs mots. Ce qui les distingue vient d'`Intl`.

Ci-dessous, `setLocale('de-DE')` SANS dictionnaire allemand : les mois et le premier
jour de semaine sont déjà allemands (ils viennent d'`Intl`), les libellés restent français.

## Messages paramétrés

Une entrée qui dépend d'une valeur est une **fonction TypeScript**, pas une chaîne à
placeholders. Il n'y a donc ni moteur de pluriel, ni syntaxe ICU à apprendre : chaque langue
écrit sa propre règle, et le typage des arguments est le contrat.

```ts
registerMessages('en', {
  dataTable: {
    selection: (count) => `${count} item${count === 1 ? '' : 's'} selected`,
    range: ({ start, end, total }) => `${start}–${end} of ${total}`,
  },
})
```

## Précédence

Une prop texte posée sur un composant reste **prioritaire** sur le dictionnaire : la
traduction globale ne change que les défauts. Pour les noms accessibles de conteneurs, la
chaîne complète est :

`aria-labelledby` › `aria-label` › prop `label` › dictionnaire › français

## Dates et heures

`Calendar`, `DatePicker` et `TimePicker` gardent leur prop `locale`, qui reste prioritaire.
Sans elle, ils suivent désormais la locale globale — un seul réglage pour toute l'application,
avec la possibilité de forcer un calendrier au cas par cas.

```jsx
<DatePicker />                  {/* locale globale */}
<DatePicker locale="ja-JP" />   {/* forcé */}
```

## Limite connue : une locale par processus

La configuration vit au niveau module, comme celle des icônes. C'est correct pour de la
configuration, mais cela signifie **une seule locale par processus** : un site rendu côté
serveur qui sert `/fr` et `/en` depuis le même processus Node ne peut pas s'appuyer dessus
pour varier la langue par requête — il doit passer les props texte explicitement.

Attention également au client-only : `setLocale` posé dans un `plugins/*.client.ts` fait
diverger le rendu serveur et le rendu client, donc un mismatch d'hydratation.

## Ce qui n'est pas traduisible

Délibérément hors du dictionnaire :

- ce qu'`Intl` dérive déjà de la balise de locale (noms de mois et de jours, ordre des champs
  de date, séparateur de date, cycle horaire) ;
- ce qui n'est fait que de chiffres et de ponctuation universelle : le `99+` du Badge, le `+N`
  d'AvatarGroup, le compteur `N/M` des champs, le `:` de l'heure. Ces composants exposent un
  slot quand une reformulation est nécessaire ;
- les messages **développeur** (`[Composant] …`), qui s'adressent à l'intégrateur.
